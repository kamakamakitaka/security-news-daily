# バラバラな本人確認システムがデジタル注入攻撃に弱い理由

**元記事**: [Why Fragmented Identity Pipelines Fail Against Digital Injections](https://inl03.netline.com/ltr6/?_m=3n.009a.3993.sp0ao46r89.31nu)
**解説日**: 2025年7月14日

---

## 背景知識

まず、この記事を理解するために必要な基礎知識をわかりやすく整理します。

### 🪪 本人確認（Identity Verification）とは？
銀行口座の開設や、スマホアプリの登録で「顔写真を撮ってください」「免許証を写してください」と求められた経験はありませんか？あれが**本人確認（eKYC）**です。オンラインで本人かどうかを確認する仕組みで、最近はほぼすべての金融サービスやフィンテック系アプリで使われています。

### 🤖 ディープフェイク（Deepfake）とは？
AIを使って人の顔や声を本物そっくりに合成した偽の映像・画像のことです。「自分の顔の代わりに他人の顔を動かして見せる」ことができるため、顔認証を騙すために悪用されることがあります。

### 🔌 APIとは？
**API（Application Programming Interface）** とは、異なるソフトウェア同士が「会話する」ための窓口のようなものです。たとえば天気アプリが気象サービスのAPIを呼び出して天気情報を取得する、といったイメージです。

### 🏗️ 本人確認のパイプラインとは？
本人確認は、実は一つのシステムが全部やっているわけではなく、複数の工程が「パイプ（管）」のようにつながって処理されています。

```
📷 顔撮影 → 📄 書類スキャン → 👁️ 生体確認 → 🔍 詐欺チェック → ✅/❌ 判定
```

この各工程を**別々の会社のサービス（API）**で組み合わせているケースが多く、これを「**フラグメント（断片化）された本人確認パイプライン**」と呼びます。

### 💉 デジタル注入攻撃（Digital Injection Attack）とは？
カメラで実際に顔を撮影する代わりに、**偽の映像データ（ディープフェイクなど）をシステムに直接"注入（インジェクション）"する**攻撃です。本物のカメラを通さずに、偽の顔データをAPIに送りつけます。SQLインジェクション（データベースに不正命令を送る攻撃）と同じ「注入」という概念です。

## 何が起きたのか

この記事は「特定の事件が起きた」というニュースではなく、**オンライン本人確認システムの構造的な欠陥を指摘した技術解説記事**です。

### ポイントをひとことで言うと：

> 「バラバラなパーツを組み合わせて作った本人確認システムは、途中で重要な情報が抜け落ちてしまい、攻撃者に悪用されやすい」

多くの企業が「早く製品を出したい」という理由から、複数の外部サービスをAPIでつなぎ合わせて本人確認システムを作っています。しかし、この**「つなぎ合わせ」こそが危険の温床**だと、この記事は指摘しています。

## 技術的な詳細

### 🧩 なぜバラバラな構成になるのか？

本人確認システムを一から全部自社で作るのは、非常にコストがかかります。

| やること | 必要なもの |
|---|---|
| 顔認識 | AI・機械学習の専門家 |
| 書類スキャン | OCR技術 |
| 生体確認（ライブネス） | 特殊なカメラ処理 |
| 詐欺チェック | 大量のデータとノウハウ |

そこで多くの企業は「それぞれの専門会社のAPIを買って組み合わせよう！」という選択をします。確かに**素早く製品を作れて、機能も豊富に見えます**。

### ⚠️ しかし、ここに落とし穴がある

データがA社→B社→C社と流れる中で、**重要な「文脈情報（コンテキスト）」が削ぎ落とされていきます**。

#### 失われる情報の例：

```
📷 カメラ撮影時に存在していた情報
├── カメラのハードウェア固有情報（本物のカメラか？）
├── ネットワークの通信タイミング（不自然な遅延はないか？）
├── デバイスの状態（改造・脱獄されていないか？）
└── 仮想環境で動いていないか？（エミュレーターの痕跡）
         ↓ APIを通るたびに...
    ✅ or ❌ だけの単純な結果に圧縮される
```

最終的にセキュリティシステムが受け取るのは「合格・不合格」の二択だけ。**「なぜその判定になったか」という証拠が消えてしまいます。**

### 🥷 攻撃者はこの「隙間」を狙う

デジタル注入攻撃の攻撃者は、このことをよく理解しています。

```
通常の本物ユーザー：
スマホのカメラ → 本人の顔映像 → API → 判定

攻撃者：
偽の顔映像データ(AI生成) → API に直接送信 → 判定
         ↑
   カメラの「本物証明」が最初からない
   でも途中のAPIは気づかない
```

本来なら「このデータは本物のカメラから来たものか？」を確認すべきですが、バラバラなシステムでは**その確認情報が最初の工程で消えてしまっている**ため、後工程では判断できません。

### 🏢 責任の分散問題

もう一つの深刻な問題は**「誰が責任を取るのかわからなくなる」**こと。

```
A社（撮影）→ B社（書類確認）→ C社（顔認証）→ D社（詐欺チェック）
                        ↑
               何か問題が起きたとき、
               どの会社の責任？
```

不正が起きても、各社が「うちのシステムは正常でした」と言い合い、原因究明が非常に困難になります。

## なぜ重要なのか

### 影響を受ける場面

この問題は私たちの身近な場面に直結しています。

| サービス | 影響 |
|---|---|
| 銀行・証券口座開設 | 他人になりすました口座が作られる |
| フィンテックアプリ | 不正送金・資産窃盗 |
| 本人確認が必要なサービス全般 | なりすましによる不正利用 |

### 数字で見る深刻さ

ディープフェイクを使った本人確認への攻撃は年々急増しており、金融業界では**デジタル注入攻撃が生体認証攻撃全体の大半を占める**とも言われています。

### 🎯 「本物らしく見える」だけでは防げない

従来のセキュリティは「偽の顔が本物らしく見えるか」の精度向上に注力してきました。しかし今回の記事が指摘するのは、**「そもそも映像の出所を確認できない構造」**が問題だということ。どれだけ高精度なAIを使っても、入力データ自体の信頼性が担保されなければ意味がないのです。

## 対策・今後の展望

### ✅ 技術的な対策

#### 1. ハードウェア証明（Hardware Attestation）の導入
「このデータは本物のデバイスの本物のカメラから来た」ということを**暗号技術で証明する仕組み**を作ること。スマホのセキュアチップを活用します。

#### 2. エンドツーエンドの一貫した設計
バラバラなAPIをつなぐのではなく、**最初から最後まで一つの設計思想でシステムを構築**し、情報が途中で失われない構造にすること。

#### 3. リッチな文脈情報の保持
「合格・不合格」だけでなく、**判定に至るまでの証拠（ログ・メタデータ）を保存・伝達する仕組み**を義務付けること。

#### 4. ベンダー評価の厳格化
複数のAPIを組み合わせる際、**各ベンダーのセキュリティ基準を統一的に審査**し、「弱いリンク」を作らないようにすること。

### 🔮 今後の動向

- **規制の強化**：金融庁などの規制当局が「本人確認システムの構成要件」を定める方向に進む可能性
- **統合型プラットフォームへの移行**：バラバラなAPIより「一社が全工程を担保する」モデルが見直される
- **デバイス証明技術の普及**：スマホメーカー（Apple・Googleなど）のセキュアエンクレーブを活用した認証が標準化

## 過去記事との関連

今回の記事は「ディープフェイクがすごい精度になった」という話ではなく、**システムの「設計」に問題がある**という、一歩進んだ視点の記事です。

もし以前にディープフェイクや顔認証の基本についての解説を読んだことがある方は、「AIの精度を上げるだけでは解決しない、より根本的な構造問題がある」という文脈でこの記事を読むとより理解が深まります。

## 用語解説

| 用語 | わかりやすい説明 |
|---|---|
| **eKYC（本人確認）** | オンラインで「あなたが本人かどうか」を確認すること |
| **ディープフェイク** | AIで作った本物そっくりの偽の顔画像・動画 |
| **API** | 異なるシステムが情報をやり取りするための「窓口」 |
| **デジタル注入攻撃** | 偽のデータをシステムに直接送り込む攻撃 |
| **ライブネス検知** | 「生きている本物の人間か、写真や映像ではないか」を判定する技術 |
| **パイプライン** | データが順番に処理されていく一連の流れ（パイプ＝管のイメージ） |
| **ハードウェア証明** | 「このデータは本物のデバイスから来た」と暗号で証明する技術 |
| **フラグメント化** | バラバラに断片化されること |
| **オーケストレーション** | 複数のAPIやシステムを指揮して連携させること |
| **メタデータ** | データ本体ではなく、「いつ・どこで・どんな条件で作られたか」という付随情報 |
| **サブプロセッサー** | 業務を委託された外部の処理業者 |

---

> 💡 **まとめ**: 「早く作りたい」という理由で複数サービスを組み合わせた本人確認システムは、継ぎ目の部分で重要情報が抜け落ち、攻撃者に悪用されやすい構造になっています。セキュリティは「見た目の精度」だけでなく、**システム全体の設計から考える**必要があります。
