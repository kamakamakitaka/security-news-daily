**解説日**: 2026年6月12日

## 背景知識

まず、このニュースを理解するために必要な基礎知識をおさえておきましょう。

### 📦 npm（エヌピーエム）って何？
**npm（Node Package Manager）** とは、JavaScriptのプログラムを作るときに使う「部品の自動インストールツール」です。

料理に例えると、「このレシピを作るのに必要な食材を全部自動で買ってきてくれる買い出し係」のようなものです。プログラマーは `npm install` というコマンドを打つだけで、必要なプログラムの部品（パッケージ）を何十個・何百個と自動でダウンロードできます。GitHubが運営しており、世界中の開発者が毎日使っています。

### 🔗 依存関係（Dependency）って何？
あなたが作るプログラム（A）が、他の誰かが作った部品（B）を使っているとき、「AはBに依存している」と言います。さらにBがC、CがDを使っていることもあります。これを**依存関係のツリー（木構造）**と呼びます。

```
あなたのプログラム（A）
  └─ 部品B（信頼している）
       └─ 部品C（知らないかも）
            └─ 部品D（全然知らない！）← ここが悪意ある部品に！
```

### ⚠️ サプライチェーン攻撃って何？
**サプライチェーン攻撃**とは、あなたが直接使っているものではなく、「その材料を作っている工場」を狙う攻撃です。

食品で例えると、スーパーのお弁当に毒を入れるのではなく、そのお弁当に使われている調味料の製造元に毒を混ぜる攻撃です。スーパーも消費者も「まさか調味料が汚染されているとは思わない」ので、被害が広がりやすいのが特徴です。

### 🔐 インストールスクリプトって何？
npm でパッケージをインストールするとき、そのパッケージの作者が「インストール時に自動で実行するプログラム（スクリプト）」を仕込むことができます。これを**インストールスクリプト**と呼びます。便利な反面、悪意ある作者が使うと、インストールするだけでマルウェアを動かされてしまう危険があります。

## 何が起きたのか

GitHubは、npm のバージョン12（来月リリース予定）において、**インストールスクリプトをデフォルトで無効化する**という大きな変更を発表しました。

具体的には、以下の3つの変更が行われます：

| 変更内容 | 現在（v11以前） | v12以降 |
|---|---|---|
| インストール時のスクリプト実行 | ✅ 自動で実行される | ❌ デフォルトで止まる（許可が必要） |
| Gitリポジトリからの依存解決 | ✅ 自動で許可 | ❌ `--allow-git` フラグが必要 |
| リモートURL（https等）からの依存解決 | ✅ 自動で許可 | ❌ `--allow-remote` フラグが必要 |

つまり、**「勝手に動く」から「あなたが許可したものだけ動く」**へと、考え方が根本から変わります。

## 技術的な詳細

### 🎯 攻撃の仕組み（今まで何が危なかったのか）

```
開発者が npm install を実行
         ↓
パッケージAをインストール（信頼している）
         ↓
パッケージAが依存するパッケージBも自動インストール
         ↓
パッケージBの中に悪意あるスクリプトが！
         ↓
😱 開発者のパソコンで勝手に悪意あるコードが実行される！
```

これが「**インストールスクリプトを悪用したサプライチェーン攻撃**」です。GitHubはこれを「npmエコシステム最大のコード実行リスク」と表現しています。

### 🛡️ v12でどう変わるのか

v12では、スクリプトの実行が**「デフォルト拒否・明示的な許可が必要」**になります。

```
開発者が npm install を実行
         ↓
パッケージBにスクリプトあり！→ 🛑 自動では実行しない
         ↓
「このパッケージのスクリプトを実行しますか？」と警告を表示
         ↓
開発者が信頼するものだけ npm approve-scripts で許可
         ↓
✅ 許可したスクリプトだけ実行される
```

### 🔧 さらに細かい変更点

**Gitリポジトリ依存のブロック**  
これまで、`.npmrc`という設定ファイルを悪用して、Gitの実行ファイルそのものを別のものにすり替えるという高度な攻撃方法がありました。v12ではGitからの依存関係はデフォルトでブロックされます。

**ネイティブビルド（node-gypなど）もブロック対象**  
C++などで書かれたネイティブモジュールをビルドする際に使う`node-gyp`も、明示的に許可しないとブロックされます。これは「install スクリプトを書いていないから安全」というつもりでいた開発者にも影響します。

## なぜ重要なのか

### 🌍 影響の大きさ
- npmは世界最大のパッケージレジストリで、**登録パッケージ数は300万以上**
- 毎日数十億回以上ダウンロードが行われている
- 世界中のWebサービス・アプリ・企業のシステムで使われている

つまり、ここに脆弱性があると、**世界中の開発者のパソコンや企業のシステムが一度に危険にさらされる**可能性があるのです。

### 💥 過去の実際の被害例（参考）
以前、`event-stream`というnpmパッケージが乗っ取られ、そのパッケージに依存していた多数のアプリから仮想通貨が盗まれるという事件が起きました。まさに「依存関係のツリーを通じた攻撃」でした。

### 👩‍💻 開発者への影響
- **良い面**: セキュリティが大幅に向上する。知らないうちにマルウェアが動くリスクが激減する
- **注意点**: これまで普通に動いていたパッケージが急に動かなくなる可能性がある（「breaking changes（破壊的変更）」と呼ばれる所以）

## 対策・今後の展望

### ✅ 開発者がいますべきこと

GitHubは以下の手順を推奨しています：

**ステップ1: まず npm を最新版に更新する**
```bash
npm install -g npm@latest
# npm 11.16.0 以上にアップグレードする
```

**ステップ2: 通常通りインストールして警告を確認する**
```bash
npm install
# 「このパッケージにスクリプトがあります」という警告が表示される
```

**ステップ3: 信頼できるパッケージのスクリプトを承認する**
```bash
npm approve-scripts --allow-scripts-pending
# どのパッケージにスクリプトがあるか確認し、信頼できるものだけ許可
```

**ステップ4: 設定をコミット（保存）する**
```bash
# 承認した設定をpackage.jsonに保存し、チームで共有する
```

### 🔮 今後の展望
GitHubはセキュリティ強化の取り組みを継続しており、今年の初めにも「新しく公開されたパッケージは指定した日数が経つまで拒否できる（min-release-age）」という機能を追加しています。npm v12の変更はその流れの一環であり、今後もサプライチェーン攻撃への対策が強化されていくでしょう。

## 過去記事との関連

以前、「**AIによる攻撃の加速と、正しい対策の優先順位**」について解説しました。その記事では「攻撃手法が高度化・自動化する中で、本当に重要なリスクに集中することが大切」というメッセージがありました。

今回のnpmの変更はまさにその実践例と言えます。サプライチェーン攻撃は**自動化・大規模化しやすい攻撃の典型**であり、AIを使って悪意あるパッケージを大量生成・配布する手口も現実のものとなっています。GitHubが「デフォルト安全」の方向へ舵を切ったのは、こうした攻撃トレンドへの現実的な対応と言えるでしょう。

## 用語解説

| 用語 | 読み方 | 意味 |
|---|---|---|
| **npm** | エヌピーエム | Node Package Manager。JavaScriptの部品を管理・インストールするツール |
| **パッケージ** | ぱっけーじ | プログラムの部品。他の人が作ったコードのまとまり |
| **依存関係（Dependency）** | いぞんかんけい | あるパッケージが別のパッケージを必要としている関係 |
| **サプライチェーン攻撃** | さぷらいちぇーんこうげき | 直接の標的ではなく、その材料や部品の供給経路を狙う攻撃 |
