# LangGraphの脆弱性チェーンが、自己ホスト型AIエージェントをリモートコード実行の危険にさらす

**元記事**: [LangGraph Flaw Chain Exposes Self-Hosted AI Agents to Remote Code Execution](https://inl03.netline.com/ltr6/?_m=3n.009a.4002.sp0ao46r89.31zo)
**解説日**: 2025年7月

---

## 背景知識

このニュースを理解するために、まずいくつかのキーワードを説明します。

### 🤖 LangGraphって何？

最近、「ChatGPT」のようなAIが話題ですよね。LangGraphは、そういったAIを使った**複雑なアプリ（AIエージェント）を作るための土台（フレームワーク）**です。「LangChain」という会社が作ったオープンソース（誰でも無料で使える）のツールで、複数のAIが連携して動くようなシステムを構築できます。

たとえば「自動でリサーチして、まとめて、メールを送るAIアシスタント」のような複雑な処理を実現するのに使われます。

### 🗄️ チェックポイントって何？

AIエージェントが「今どこまで作業したか」を記録・保存する仕組みです。人間で言うと、ゲームのセーブデータのようなものです。LangGraphでは、このチェックポイントをSQLiteやRedisというデータベースに保存します。

### 🔓 今回のキーワード：脆弱性（ぜいじゃくせい）

システムの「弱点・穴」のことです。攻撃者はこの穴を突いて、悪いことをしようとします。

---

## 何が起きたのか

セキュリティ研究者のYarden Porat氏が、LangGraphに**3つの脆弱性**を発見しました。その中でも特に危険なのは、**2つの脆弱性を組み合わせることで、攻撃者がサーバーを完全に乗っ取れる**というものです。

この問題は現在すでに修正済み（パッチ適用済み）ですが、まだ古いバージョンを使っているシステムは危険な状態です。

### 発見された3つの脆弱性

| 脆弱性ID | 危険度スコア | 内容 | 影響を受けるバージョン |
|---|---|---|---|
| CVE-2025-67644 | 7.3（高） | SQLインジェクション | langgraph-checkpoint-sqlite 3.0.1より前 |
| CVE-2026-28277 | 6.8（中〜高） | 安全でないデシリアライズ | langgraph 1.0.10より前 |
| CVE-2026-27022 | 6.5（中〜高） | Redisクエリインジェクション | @langchain/langgraph-checkpoint-redis 1.0.1より前 |

## 技術的な詳細

### 🏹 攻撃の仕組みをわかりやすく解説

今回の攻撃は、**2つの脆弱性をチェーン（鎖）のようにつなげる**ことで成立します。お菓子の工場に例えて考えてみましょう。

---

**🏭 工場（サーバー）の仕組み**
- 工場には「作業記録ノート（チェックポイント）」があります
- 訪問者（ユーザー）は「どの記録を見たいか（フィルターパラメータ）」を指定できます
- 工場は指定された記録を倉庫（データベース）から取り出して見せます

---

**🦹 攻撃のステップ（4段階）**

**Step 1：爆弾を作る**
> 攻撃者は、「悪意のある指令書（msgpackペイロード）」を準備します。これはサーバーに好き勝手な命令を実行させるためのデータです。

**Step 2：偽の記録を差し込む（SQLインジェクション）**
> 攻撃者は「記録を見せて」という検索条件に、**こっそり不正な命令を混ぜ込みます**。これが「SQLインジェクション」です。
> 
> たとえるなら、図書館員に「『ハリーポッター』を取ってきて。あ、あと金庫も開けておいて」と、普通のお願いの中に不正な命令を紛れ込ませる感じです。
> 
> その結果、データベースは「偽の作業記録（偽チェックポイント）」を返し、その中に**Step 1で作った爆弾データが含まれています**。

**Step 3：偽データを読み込ませる**
> サーバーは「正規のデータが返ってきた」と思い込み、偽チェックポイントのデータを読み込もうとします。

**Step 4：爆弾が爆発する（安全でないデシリアライズ）**
> サーバーがデータを解読（デシリアライズ）する際に、**中に仕込まれた悪意のある命令が実行されてしまいます**。これで攻撃者はサーバーを完全に操れるようになります（リモートコード実行）。

---

**📦 「デシリアライズ」って何？**

データを保存するとき、複雑な情報を「圧縮・変換」して保存します（シリアライズ）。読み込む時は逆に「元に戻す」作業をします（デシリアライズ）。
もし「戻す」作業をするデータが攻撃者に書き換えられていたら、元に戻す過程で悪意のある命令が実行されてしまいます。

## なぜ重要なのか

### 🎯 AIエージェントは「特別な権限」を持っている

普通のWebサービスと違い、AIエージェントは多くの場合：
- 他のサービスのAPIキー（パスワードのようなもの）を持っている
- データベースやファイルへのアクセス権限がある
- 他のシステムと連携している

つまり、AIエージェントのサーバーを乗っ取られると、**その先にある多くのシステムにも侵入できてしまう**可能性があります。

### 🌍 影響範囲

- **自己ホスト型のLangGraph**（自分のサーバーで動かしているもの）が対象
- LangChainが提供するクラウドサービス（LangSmith）は影響なし
- SQLiteまたはRedisをチェックポイントに使っていて、**ユーザーからの入力をフィルターに使っている**場合に危険

### ⚠️ セキュリティ研究者のコメント

Check Point（セキュリティ企業）は「SQLインジェクションのような古典的な攻撃手法でも、AIフレームワーク内で使われると、より強力で危険になる」と指摘しています。AIの普及に伴い、AIを使ったシステムのセキュリティがますます重要になっています。

## 対策・今後の展望

### ✅ すぐやるべき対策

1. **アップデート！（最優先）**
   - `langgraph-checkpoint-sqlite` → **3.0.1以上**にアップデート
   - `langgraph` → **1.0.10以上**にアップデート
   - `@langchain/langgraph-checkpoint-redis` → **1.0.1以上**にアップデート

2. **認証を設定する**
   - 自己ホスト型のLangGraphサーバーには、必ず「ログイン認証」を設けましょう
   - 誰でもアクセスできる状態にしない

3. **長期間使い続けるパスワード（静的シークレット）を避ける**
   - APIキーなどは定期的に変更する

4. **ネットワークの分離（セグメンテーション）**
   - AIエージェントのサーバーが、他の重要なシステムに直接アクセスできないようにネットワークを分ける

5. **最小権限の原則（PoLP）を守る**
   - AIエージェントには「必要最低限のアクセス権限だけ」を与える
   - 「なんでもできる」状態にしない

### 🔮 今後の展望

AI技術が急速に普及する中、AIシステムへのセキュリティ攻撃も増えていくと予想されます。今回のような「古い攻撃手法 × 新しいAI技術」の組み合わせは、今後も多く登場すると考えられます。

## 過去記事との関連

今回の記事では特定の過去記事との直接の関連はありませんが、**SQLインジェクションは非常に古典的な攻撃手法**で、Webセキュリティの世界では長年にわたって問題になり続けています。「新しいAI技術でも、古典的な攻撃が有効」という点は、セキュリティの世界では重要な教訓です。新しい技術を導入する際には、新しいセキュリティリスクだけでなく、古くから知られているリスクにも気を付けることが大切です。

## 用語解説

| 用語 | 説明 |
|---|---|
| **LangGraph** | AIエージェント（自律的に動くAI）を作るためのフレームワーク（土台ツール） |
| **AIエージェント** | 人間の指示なしに自律的にタスクをこなすAIシステム |
| **チェックポイント** | AIの作業の進捗状況を保存するセーブデータのようなもの |
| **脆弱性（CVE）** | システムのセキュリティ上の弱点・穴。CVEは脆弱性に付けられる国際的な識別番号 |
| **SQLインジェクション** | データベースへの問い合わせ（SQL文）に不正な命令を混ぜ込む攻撃手法 |
| **デシリアライズ** | 保存・通信用に変換されたデータを元の形式に戻す処理 |
| **リモートコード実行（RCE）** | 攻撃者が遠隔からサーバー上で任意のプログラムを実行できる状態 |
| **msgpack** | データを効率よく保存・通信するための形式（フォーマット） |
| **SQLite / Redis** | データベースの種類。LangGraphではチェックポイントの保存に使われる |
| **自己ホスト型** | クラウドサービスを使わず、自分のサーバーで動かす形式 |
| **最小権限の原則（PoLP）** | システムやユーザーには「必要最低限の権限だけ」を与えるというセキュリティの基本原則 |
| **CVSS スコア** | 脆弱性の危険度を0〜10の数値で表したもの。7以上は「高」リスク |
| **ネットワークセグメンテーション** | ネットワークを区切り、重要なシステムへの不正アクセスを防ぐ手法 |
