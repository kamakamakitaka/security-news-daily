# LangGraphの脆弱性チェーンにより、自己ホスト型AIエージェントがリモートコード実行の危険にさらされる

**元記事**: [LangGraph Flaw Chain Exposes Self-Hosted AI Agents to Remote Code Execution](https://inl03.netline.com/ltr6/?_m=3n.009a.4003.sp0ao46r89.321w)
**解説日**: 2025年6月14日

---

## 背景知識

このニュースを理解するために、まずいくつかの基本的な概念を押さえておきましょう。

### 🤖 AIエージェントって何？
「AIエージェント」とは、人間がいちいち指示を出さなくても、自分で考えて複数の作業を自律的にこなせるAIのことです。たとえば「市場調査レポートを作って」と頼むと、自分でWebを検索し、データを整理し、文書にまとめるところまでやってくれるイメージです。

### 🧩 LangGraphって何？
**LangGraph**は、そういった「複数のAIエージェントが連携して動く複雑なシステム」を作るためのオープンソースのフレームワーク（道具箱）です。LangChainという会社が作っており、企業が自社のAIシステムを構築する際によく使われています。

### 💾 チェックポイントって何？
LangGraphには「チェックポイント」という仕組みがあります。これはゲームのセーブデータのようなもので、AIエージェントが途中まで処理した「状態」を保存しておく機能です。後で「どこまでやったか」を確認したり、続きから再開したりするために使います。

### 🏠 自己ホスト型とは？
自社のサーバーにソフトウェアをインストールして動かすことを「自己ホスト型（セルフホスト）」と言います。クラウドサービスをそのまま使うのではなく、「自分たちで管理する」形態です。

---

## 何が起きたのか

セキュリティ研究者たちが、**LangGraphに3つの脆弱性（セキュリティ上の弱点）** を発見しました。

特に深刻なのは、そのうちの**2つを組み合わせる（チェーンする）ことで、攻撃者がサーバーを完全に乗っ取れる**という点です。この攻撃が「リモートコード実行（RCE）」と呼ばれるもので、インターネット経由で悪意あるプログラムを実行されてしまう、非常に危険な攻撃です。

幸いなことに、現時点ではすでに修正パッチ（直し）が提供されています。

---

## 技術的な詳細

### 発見された3つの脆弱性

| 脆弱性ID | 深刻度スコア | 内容 |
|---|---|---|
| CVE-2025-67644 | 7.3（高） | SQLインジェクション |
| CVE-2026-28277 | 6.8（中〜高） | 安全でないデシリアライゼーション |
| CVE-2026-27022 | 6.5（中） | Redisクエリインジェクション |

### 🔗 攻撃チェーンの仕組み（わかりやすく解説）

CVE-2025-67644とCVE-2026-28277を組み合わせると、次のような攻撃が可能になります。

```
【攻撃の流れ】

1. 攻撃者が「爆弾入りの荷物（悪意あるデータ）」を準備する
         ↓
2. SQLインジェクションを使って、データベースに
   「偽のチェックポイント（セーブデータ）」を混入させる
         ↓
3. システムがチェックポイントを読み込もうとする
         ↓
4. 「爆弾」が爆発！悪意あるプログラムが実行される
         ↓
5. 攻撃者がサーバーを完全にコントロール！
```

#### 具体的な例え話🏦
銀行のATMに例えると…

- **SQLインジェクション** → 「偽の通帳データ」をATMのシステムに混入させる
- **デシリアライゼーション** → ATMが「偽の通帳」を本物と信じて読み込む
- **結果** → 攻撃者がATMを自由に操作できてしまう

### 攻撃の入口（`get_state_history()`エンドポイント）
攻撃者は`get_state_history()`という機能（過去のチェックポイント履歴を取得する機能）を通じて、悪意あるデータをシステムに送り込みます。

## なぜ重要なのか

### 🎯 影響を受けるのはこんな環境
- **自社サーバーでLangGraphを動かしている**すべての組織
- SQLiteまたはRedisのチェックポイント機能を使っているシステム
- ユーザーからの入力をフィルタリングに使っているシステム

> ⚠️ ただし、LangChainが提供する**クラウド管理版（LangSmith）には影響しない**とのことです。

### 💥 攻撃が成功するとどうなる？
- サーバー上に保存された**機密データ（APIキーやパスワードなど）の漏えい**
- サーバーを踏み台にした**他のシステムへの不正アクセス**
- AIエージェントが持つ**高い権限を悪用した横断的な攻撃**

### 🔍 なぜAIフレームワークの脆弱性は特に危険？
普通のWebアプリとは違い、AIエージェントは：
- 多くのシステムやデータに**高い権限でアクセス**できる
- 複数のサービスと連携しているため、**一つの侵入が広範囲に波及**しやすい
- 「信頼できるもの」として扱われるため、**不審な動作が気づかれにくい**

## 対策・今後の展望

### ✅ 今すぐやるべきこと

1. **パッチを当てる（最優先！）**
   - `langgraph-checkpoint-sqlite` → **バージョン3.0.1以降**に更新
   - `langgraph` → **バージョン1.0.10以降**に更新
   - `@langchain/langgraph-checkpoint-redis` → **バージョン1.0.1以降**に更新

2. **認証を設定する**
   - 自己ホスト型のLangGraphサーバーには必ず認証（ログイン機能）を設定する
   - 「鍵のかかっていないドア」は危険です！

3. **長期間使い回すパスワード・キーを避ける**
   - 同じ認証情報をずっと使い続けないようにする

4. **ネットワークを分離する**
   - AIサーバーを他のシステムから隔離し、必要な通信だけ許可する

5. **最小権限の原則を守る**
   - AIエージェントには「仕事に必要な最低限の権限」だけを与える
   - 「なんでもできる管理者権限」を与えない！

### 🔮 今後の展望
AIエージェントの普及が加速する中、このような「AIフレームワーク自体を狙った攻撃」は今後増えていくと考えられます。AIを使う側も、「便利なツール」であると同時に「高い権限を持つセキュリティリスク」として扱う意識が必要です。

## 過去記事との関連

以前、**「AIコーディングエージェントを乗っ取る『Agentjacking攻撃』」** についての記事を解説しました。あの記事では、悪意あるコードをAIに実行させる攻撃手法が取り上げられていましたが、今回のLangGraphの脆弱性も本質は同じ方向性の問題です。

つまり「AIエージェントが便利になればなるほど、それを悪用しようとする攻撃者も増える」というトレンドが続いています。AIが複数のシステムにまたがって動作する以上、**AIそのものをセキュリティの観点から管理する**という新しい考え方が、業界全体で求められています。

## 用語解説

| 用語 | 意味 |
|---|---|
| **脆弱性（ぜいじゃくせい）** | ソフトウェアのセキュリティ上の弱点・欠陥 |
| **リモートコード実行（RCE）** | ネットワーク経由で、攻撃者が自分のプログラムを他人のサーバーで実行できる攻撃 |
| **SQLインジェクション** | データベースへの命令文（SQL）に悪意ある命令を混ぜ込む攻撃手法 |
| **デシリアライゼーション** | 保存されたデータを元のオブジェクト（プログラムが使えるデータ形式）に戻す処理。不正なデータを処理すると危険 |
| **msgpack** | データを効率よく保存・転送するためのデータ形式の一種 |
| **チェックポイント** | AIエージェントの処理状態を保存したデータ（ゲームのセーブデータのようなもの） |
| **CVE** | 公式に登録・管理されている脆弱性の識別番号 |
| **CVSSスコア** | 脆弱性の深刻度を0〜10で数値化したもの（10が最も危険） |
| **オープンソース** | ソースコード（設計図）が公開されており、誰でも使えるソフトウェア |
| **最小権限の原則（PoLP）** | システムやユーザーには、必要最低限の権限だけを与えるべきというセキュリティの基本原則 |
| **ネットワークセグメンテーション** | ネットワークを複数の区画に分けて、不正アクセスの被害が広がりにくくする設計 |
| **エンドポイント** | ネットワーク上でデータのやり取りをする「窓口」となるURL・アドレス |
