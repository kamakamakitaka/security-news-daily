# あなたのネットショップの決済ページにあるスクリプトが、今やPCIセキュリティ基準の問題になっている

**元記事**: [The Scripts on Your Checkout Page Are Now a PCI DSS Problem](https://inl03.netline.com/ltr6/?_m=3n.009a.4007.sp0ao46r89.326m)
**解説日**: 2025年6月19日

---

## 背景知識

このニュースを理解するために、まずいくつかの基本的な仕組みを説明します。

### 🛒 ネットショップの「決済ページ」って何？
オンラインショッピングで最後にクレジットカードの番号を入力する画面のことです。あの画面、実はとても複雑な仕組みで動いています。

### 📜 「スクリプト」って何？
Webページを動かすための小さなプログラムのことです。例えば、「アクセス数を計測するツール」「チャットサポートのポップアップ」「Googleタグマネージャー」など、1つのページに数十種類ものスクリプトが読み込まれています。そのほとんどは**外部の会社（サードパーティ）が作ったもの**です。

> 🏠 **例え話**: あなたの家に友人が遊びに来ると思ってください。でも、その友人が「友人の知り合い」も連れてきて、さらに「その知り合いの知り合い」も来た…という状況です。あなたは全員を完全には信頼できませんよね？

### 💳 PCI DSS って何？
**PCI DSS（Payment Card Industry Data Security Standard）** とは、クレジットカード情報を扱うすべての企業が守らなければならない「セキュリティのルール集」です。VisaやMasterCardなどのカード会社が共同で作ったもので、「このルールを守らないとカード決済を使わせませんよ」という強制力があります。

### 🐛 「Magecart（マジカート）」攻撃って何？
決済ページに**スキマー（情報を盗み取る仕掛け）**を仕込む攻撃手法です。スーパーのセルフレジに誰かがこっそりカードリーダーを偽物にすり替えるイメージです。

---

## 何が起きたのか

### 問題の核心：信頼していたスクリプトが「武器」に変わる

決済ページには外部スクリプトが数十個も動いていますが、**攻撃者はそのうちの1つを乗っ取ります**。

重要なのは、**「新しい怪しいスクリプトが追加される」のではなく、「もともと使っていたスクリプトの中身がこっそり書き換えられる」**という点です。これが非常に厄介な理由です。

```
通常の流れ:
ユーザー → 決済ページ → 正規のスクリプト → カード情報を安全に処理

攻撃後:
ユーザー → 決済ページ → 改ざんされたスクリプト → カード情報を攻撃者へ送信
                                                   ↓
                                              さらに正規処理へ（気づかれない）
```

### 被害の実例
- **2018年 ブリティッシュ・エアウェイズ（英国航空）の情報漏洩**
  - **38万件**のクレジットカード情報が盗まれた
  - 罰金は当初**1億8,300万ポンド（約280億円！）**から始まった

- **世界で10万以上のサイト**がこの「Webスキミング攻撃」の被害を受けている

## 技術的な詳細

### 新しいPCI DSS v4.0.1のルール

2025年から、以下の2つのルールが**完全に義務化**されました。

| ルール番号 | 内容 | わかりやすく言うと |
|-----------|------|-----------------|
| **6.4.3** | 決済ページのすべてのスクリプトを一覧化し、承認し、改ざんされていないか確認する | 「どのスクリプトが動いているか全部把握して、変わってないか確認してね」 |
| **11.6.1** | ページの内容やHTTPヘッダーの改ざんをブラウザ側でリアルタイムに検知する | 「ユーザーのブラウザに届く時点での変化も見張ってね」 |

### なぜ手作業では無理なのか？
Reflectizという会社の調査によると、**決済ページのスクリプトの約30%は2週間以内に変化する**ことがわかっています。

> 📊 100個のスクリプトがあれば、2週間で約30個が何らかの形で変わる計算です。これを人間が手作業で全部チェックするのは現実的に不可能です。

### 「ハッシュチェック」だけでは不十分な理由

**ハッシュ（hash）**とは、ファイルの「指紋」のようなものです。ファイルが1文字でも変わると全く違う値になります。従来はこれでチェックしていました。

しかし問題があります：
- **サーバー側でこっそり書き換えられた場合**、チェック対象のハッシュ値も更新されてしまうため、「変わった」ことに気づけません
- これを「サイレントベンダースワップ（気づかれないすり替え）」と言います

## なぜ重要なのか

### ショップオーナー・企業にとって
1. **ルール違反 = 巨額の罰金＋カード決済停止** の可能性
2. 顧客の信頼を失い、ブランドイメージが壊滅的なダメージを受ける
3. 「自分でコードを書いてない」は言い訳にならない（外部スクリプトの管理責任も企業にある）

### 一般ユーザー（私たち）にとって
- ネットショッピングをするたびに、気づかないうちにカード情報が盗まれるリスクがある
- 見た目は全く普通の有名サイトでも被害に遭う可能性がある

### 「SAQ A」という抜け道と落とし穴
**SAQ A**とは、小規模な事業者向けの「簡易チェックリスト」のようなもので、条件を満たせば6.4.3と11.6.1を免除されます。

ただし、**iframeで決済画面を埋め込んでいる場合は要注意**です：

```
❌ 危険なケース（iframeを使っている場合）:
親ページ（自分のサイト）
    ↓ ここにスクリプトが乗っている
  [iframe：安全な決済画面]
    ↓
親ページのスクリプトがiframeの前に動いて情報を盗める！
```

「決済処理は外部に任せてるから安全」とは言い切れないのです。

## 対策・今後の展望

### 企業・ショップ運営者向けの対策

1. **決済ページで動いているスクリプトを全部把握する**
   - ブラウザの開発者ツール（F12キー）でも確認できます

2. **スクリプトの「振る舞い」を監視するツールを導入する**
   - ファイルの一致確認だけでなく、「カード情報に触れようとしているか」を検知することが重要

3. **PCI DSS v4.0.1への対応を急ぐ**
   - すでに完全義務化されており、対応が遅れるほどリスクが高まります

4. **iframeを使っている場合は特に注意**
   - SAQ Aの免除を主張するには「スクリプト攻撃に対して脆弱でない」ことを証明する必要があります

### 一般ユーザーができること
- 見覚えのないカード請求がないか定期的に確認する
- クレジットカードの利用通知をオンにしておく
- 怪しいと思ったら即座にカード会社に連絡する

## 用語解説

| 用語 | 意味 |
|------|------|
| **PCI DSS** | クレジットカード情報を扱う企業が守るべきセキュリティ基準。国際的なルール。 |
| **スクリプト** | Webページを動かす小さなプログラム。JavaScriptが代表的。 |
| **サードパーティスクリプト** | 自社ではなく外部の会社が提供するスクリプト（Googleアナリティクスなど）。 |
| **Magecart（マジカート）** | 決済ページにスキマーを仕込む攻撃グループ・手法の総称。 |
| **スキマー** | カード情報を盗み取る仕掛け。実店舗のカードリーダー偽装がネット版に。 |
| **ハッシュ（hash）** | ファイルの「指紋」。ファイルが変わると値も変わるが、更新されると意味がない。 |
| **iframe** | Webページの中に別のWebページを埋め込む仕組み。 |
| **SAQ A** | PCI DSSの簡易チェックリスト。小規模事業者向けで一部要件が免除される。 |
| **QSA** | PCI DSSの審査を行う資格を持つ認定審査機関・担当者。 |
| **サプライチェーン攻撃** | 直接攻撃せず、信頼されている外部のサービスを経由して侵入する攻撃手法。 |
| **Webスキミング** | Webサイト上でカード情報を盗み取る攻撃の総称。 |

---

> 💡 **まとめ**: ネットショップの決済ページは「自分のコード」だけで動いているわけではありません。外部スクリプトを通じた攻撃は今や当たり前になっており、PCI DSSも対応を義務化しました。「外部に任せているから安心」という時代は終わり、**「何が動いているか、それが何をしているか」を常に把握する**ことが求められています。
