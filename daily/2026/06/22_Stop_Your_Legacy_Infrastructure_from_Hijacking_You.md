# 古いITシステムがAIアシスタントを乗っ取る！？レガシーインフラの落とし穴

**元記事**: [Stop Your Legacy Infrastructure from Hijacking Your AI Agents](https://inl03.netline.com/ltr6/?_m=3n.009a.4010.sp0ao46r89.32am)
**解説日**: 2025年6月

---

## 背景知識

まず、この記事を理解するためにいくつかのキーワードを押さえておきましょう。

### 🤖 AIエージェントって何？
最近よく聞く「AIエージェント」とは、人間の指示を受けて**自律的にタスクをこなすAI**のことです。たとえば「この顧客データをまとめて、メールを送って」という指示を受けると、データを検索→整理→メール送信まで自分で判断して動く、賢いアシスタントのようなものです。ChatGPTがさらに進化して、実際にパソコン操作や社内システムの操作をできるようにしたイメージです。

### 🏚️ レガシーインフラって何？
「レガシー（legacy）」は「遺産・古い」という意味です。IT業界では、**長年使い続けている古いシステムやサーバー**のことを指します。例えば、10年前から使っているサーバーや、昔設定したままのパスワード管理システムなどが該当します。

### 🔑 関連する重要なシステム
| 用語 | 意味 | 身近な例え |
|------|------|-----------|
| **Active Directory** | 会社内のID・パスワード管理システム | 学校の生徒名簿＆鍵の管理室 |
| **IAMロール** | クラウド上での「誰が何にアクセスできるか」の権限設定 | 図書館の「教師カード」「生徒カード」の区別 |
| **S3バケット** | Amazonのクラウド上のデータ保管庫 | ネット上のロッカー |
| **Lambda関数** | クラウド上で自動実行される小さなプログラム | 自動で動く機械仕掛けの仕事係 |
| **CVE** | 発見されたセキュリティの脆弱性（弱点）に付けられる番号 | セキュリティ界の「欠陥品番号」 |

## 何が起きたのか

### 📢 ガートナーのセキュリティ会議での発表

セキュリティの世界的な調査会社「ガートナー」が主催する大きなセミナーで、あるセキュリティ専門家がとても重要な警告を発しました。

> **「AIそのものを攻撃しなくても、AIが繋がっている古いシステムを攻撃すれば、AIを乗っ取れる！」**

### 📊 現状の数字で見てみると

```
企業の71%  → AIエージェントを試験導入中
企業の31%  → 実際の業務でAIエージェントを使用中
```

つまり、多くの企業がAIを業務に組み込み始めているのに、その**足元にある古いシステムのセキュリティ対策が追いついていない**という問題が浮き彫りになりました。

## 技術的な詳細

### 🔗 AIエージェントは「既存のシステム」に頼っている

AIエージェントは最新技術に見えますが、実は動くためには**既存の古いシステムを使い回している**のです。

```
AIエージェントが使っているもの
├── 認証システム（ログイン管理）→ 既存のActive Directory
├── データ保管         → 既存のS3バケット
├── 自動処理           → 既存のLambda関数
└── アクセス権限       → 既存のIAMロール
```

これはちょうど、**新しいスマートな秘書を雇ったけど、その秘書が使う鍵束や金庫は古くて錆びかけている**ようなものです。

### ⚠️ さらに問題を深刻にしているのが「過剰な権限」

調査によると、**70%の企業がAIシステムに人間より広い権限を与えている**という驚きの事実があります。

> 例え話：学校で新しい優秀な助手（AI）を雇ったら、なぜか全生徒の成績・家庭情報・先生の給与データまで見られる権限を与えてしまっている状態

この結果：
- 過剰な権限を与えたAIを持つ企業 → **76%がセキュリティインシデントを経験**
- 最小限の権限しか与えなかった企業 → **17%にとどまる**

### 🎯 具体的な攻撃シナリオ（段階別）

記事では、実際の企業環境でモデル化した攻撃の流れが紹介されています。

```
【架空の事例】
ある会社では「顧客対応AIアシスタント（Co-Pilot）」を使用
・AWS Bedrockというサービス上で動作
・Salesforceから顧客データをS3バケットに書き出して使用
・Lambdaで自動処理
・開発者のJohnがメンテナンス担当
```

**【第1段階】S3バケットへの過剰なアクセス権限**
- 顧客データを入れたS3バケットに、不必要に多くの人がアクセスできる状態
- 開発者のJohnも本来不要な本番データへのアクセス権を持っている
- 🚪「鍵を持つべきでない人が鍵を持っている」状態

**【第2段階】古いサーバーの脆弱性が入口になる**
- 外部からアクセスできる場所に、セキュリティパッチ（修正プログラム）が当たっていない古いサーバーがある
- 攻撃者はここから侵入
- 🚪「裏口の鍵が壊れたまま放置されている」状態

**【その後の連鎖】**
```
古いサーバーに侵入
    ↓
開発者Johnの認証情報（パスワード等）を盗む
    ↓
JohnのS3アクセス権を使って顧客データにアクセス
    ↓
さらにLambda関数やAIの知識ベースにもアクセス
    ↓
AIエージェントそのものを制御・悪用
```

**ポイントは「AIを直接攻撃しなかった」こと！**
古いインフラを踏み台にして、AIが「信頼している」システムから忍び込んだのです。

## なぜ重要なのか

### 🌍 影響の大きさ

1. **攻撃が見えにくい**
   AIへの直接攻撃ではないため、「AI用のセキュリティ対策」だけでは検知できません。

2. **被害が広範囲に及ぶ**
   AIエージェントは多くのシステムと連携しているため、一か所から侵入されると芋づる式に被害が広がります。

3. **古い問題が新しい形で爆発する**
   何年も放置されていた小さなセキュリティの問題が、AI導入によって急に大きなリスクになります。

### 💡 わかりやすく言うと...

> 「新しい高性能な金庫（AI）を設置したのに、その金庫への通路（古いインフラ）の扉が壊れたまま」
> という状態です。泥棒（攻撃者）は金庫を直接破る必要がなく、壊れた扉から入るだけでOKです。

## 対策・今後の展望

### ✅ セキュリティチームがやるべきこと

**1. 最小権限の原則を徹底する**
> AIエージェントには「必要最低限の権限だけ」を与える
> 学校で言えば「助手には職員室の鍵だけ。保健室や校長室の鍵は渡さない」

**2. レガシーインフラの棚卸しをする**
> 古いサーバーや設定をリストアップし、セキュリティパッチを当てる
> 「何年も使っている古い鍵や錠前がないか確認する」

**3. AIエージェントが繋がるシステムを把握する**
> AIが「どのシステムと連携しているか」を可視化する
> 「新入りの秘書がどの部屋に入れるか、全部把握する」

**4. 認証情報の管理を強化する**
> 開発者のパスワードや認証トークンがどこに保存されているか確認
> 「合鍵がどこにあるか、誰が持っているか管理する」

**5. 攻撃経路（アタックパス）を事前に把握する**
> 攻撃者の視点で「どこから入れるか」をシミュレーションする
> 「泥棒目線で自分の家の弱点を探す」

### 🔮 今後の展望

AI技術の普及スピードはとても速く、セキュリティ対策が追いついていないのが現状です。専門家たちは「AIのセキュリティ対策はAI自体だけでなく、その周辺のインフラも含めた全体的な視点が必要」と訴えています。今後、AI時代のセキュリティ基準やガイドラインの整備が急務となるでしょう。

## 用語解説

| 用語 | 解説 |
|------|------|
| **AIエージェント** | 自律的にタスクをこなすAI。指示を受けて自分でシステムを操作する |
| **レガシーインフラ** | 古くから使い続けているITシステムや機器 |
| **Active Directory** | 会社内の社員のID・パスワード・アクセス権を一元管理するシステム |
| **IAMロール** | クラウド上でのアクセス権限の設定。誰が何にアクセスできるかを決める |
| **S3バケット** | AWSのデータ保管サービス。「クラウド上のUSBメモリ」的なもの |
| **Lambda関数** | AWSのサーバーレス実行環境。自動でプログラムを動かす仕組み |
| **CVE** | Common Vulnerabilities and Exposures。発見されたセキュリティ脆弱性の管理番号 |
| **最小権限の原則** | 必要最低限の権限だけを与えるセキュリティの基本ルール |
| **セキュリティパッチ** | ソフトウェアの脆弱性を修正するための更新プログラム |
| **プロンプトインジェクション** | AIへの入力に悪意ある命令を混ぜ込む攻撃手法 |
| **モデルポイズニング** | AIの学習データに悪意あるデータを混入させてAIの動作を狂わせる攻撃 |
| **サービスアカウント** | 人間ではなくプログラムが使うためのシステムアカウント |
| **アタックパス（攻撃経路）** | 攻撃者がシステムに侵入するために辿るルート |
| **AWS Bedrock** | AmazonのAI基盤サービス。AIエージェントを作るためのプラットフォーム |
