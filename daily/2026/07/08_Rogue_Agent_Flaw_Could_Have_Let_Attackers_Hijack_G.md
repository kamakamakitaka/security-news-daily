# 不正エージェントの欠陥でGoogleのAIチャットボットが乗っ取られる可能性があった件

**元記事**: [Rogue Agent Flaw Could Have Let Attackers Hijack Google Dialogflow CX Chatbots](https://inl03.netline.com/ltr6/?_m=3n.009a.4024.sp0ao46r89.32v8)
**解説日**: 2025年7月9日

---

## 背景知識

まず、今回の記事を理解するために必要な言葉を整理しましょう。

### 🤖 Dialogflow CX（ダイアログフロー CX）とは？
GoogleがAIチャットボット（自動応答ロボット）を作るためのツールです。企業がWebサイトやアプリに「問い合わせ対応ボット」を設置するときに使います。例えば、銀行のサイトで「残高を確認したい」と入力すると自動で返事してくれるあのボットを作れるシステムです。

### ☁️ Google Cloud とは？
Googleが提供するクラウド（インターネット上のコンピューター）サービスです。企業はここでプログラムを動かしたり、データを保存したりします。

### 🧩 コードブロック（Code Blocks）とは？
Dialogflow CX の中で、開発者が「Python（パイソン）」というプログラミング言語を使って、ボットの動作をカスタマイズできる機能のことです。

### 🧪 サンドボックスとは？
プログラムを「安全な箱の中」で動かす仕組みです。危ないことが起きても、その箱の外に影響が出ないようにするためのものです。

### 🔐 脆弱性（ぜいじゃくせい）とは？
システムやソフトウェアに存在する「セキュリティ上の穴」のことです。攻撃者に悪用されると、本来できないことができてしまいます。

---

## 何が起きたのか

セキュリティ企業「**Varonis（バロニス）**」が、Googleのチャットボット作成ツール「**Dialogflow CX**」に深刻な脆弱性を発見しました。この脆弱性は「**Rogue Agent（ローグ・エージェント）＝不正エージェント**」と名付けられました。

### 簡単に言うと…

> 🏢 ある企業が複数のAIチャットボットを運営していたとします。
> もしも攻撃者がそのうち**1つのボットの編集権限**を持っていたとしたら、
> **同じGoogle Cloudプロジェクト内のすべてのボット**を乗っ取れてしまう、というバグです。

乗っ取られると…
- 利用者の**会話内容がすべて盗み見られる**
- ユーザーが入力した**個人情報が盗まれる**
- ボットが**攻撃者の書いたメッセージを送信**できる（例：「パスワードをもう一度入力してください」という偽のメッセージなど）

---

## 技術的な詳細

少し細かい話になりますが、なるべくわかりやすく説明します！

### 🔑 問題の根本：「共有の部屋に鍵がかかっていなかった」

Dialogflow CX のコードブロック機能は、同じGoogle Cloudプロジェクト内のすべてのボットが「**1つの共有環境（部屋）**」でプログラムを動かしています。

この「部屋」の中に、`code_execution_env.py`（コード実行環境ファイル）という**ボット全員が使う重要なファイル**がありました。

そして、このファイルは**誰でも上書きできる状態**になっていました。

### 🪜 攻撃のステップをわかりやすく

```
① 攻撃者が1つのボットの「編集権限」を持つ
   （悪意のある社員や、ハッキングされた開発者アカウントなど）
   
② そのボットに「悪意のあるコードブロック」を仕込む

③ コードブロックが実行されると、共有ファイルを
   「攻撃者が用意した悪意のあるファイル」に上書きする

④ 以降、同じ部屋を使う全ボットが「汚染されたファイル」で動く

⑤ すべてのボットの会話が攻撃者のサーバーに筒抜けに！
```

### 🎣 フィッシング攻撃も可能だった
攻撃者は「ボットに偽のメッセージを送らせる」こともできました。例えば…

> 「セキュリティ確認のため、もう一度パスワードを入力してください」

これは「**フィッシング詐欺**」と呼ばれる手口で、ユーザーがだまされてパスワードを入力してしまう危険があります。

### 🕵️ 証拠も消せた
さらに問題なのは、攻撃後に元のコードブロックを管理画面上で「元に戻す」操作をすると、**画面上は正常に見えるが、裏では悪意のあるファイルが動き続ける**という隠蔽が可能でした。まるで「現場の証拠だけ消してカメラを仕掛けたまま立ち去る」ようなイメージです。

### 🌐 おまけの問題：インターネットへの無制限アクセス
本来、安全なサンドボックス環境は外部への通信を制限すべきですが、このコードブロック環境は**外部のサーバーに自由に通信できる状態**でした。

Googleのセキュリティ機能「VPC Service Controls（外部へのデータ流出を防ぐ壁）」をすり抜けられることも判明しています。

## なぜ重要なのか

### 📊 影響を受ける人たち

| 対象 | リスク |
|------|--------|
| チャットボットを利用する一般ユーザー | 会話内容・個人情報の漏洩 |
| チャットボットを運営する企業 | 信頼失墜・情報流出 |
| Dialogflow CX を使う開発者 | 自分のアカウントが悪用される可能性 |

### ⚠️ ただし、条件は限られていた
この攻撃を実行するには「**1つのボットの編集権限**」が必要でした。つまり、まったく関係のない見知らぬ人物が外からいきなり攻撃することはできません。現実的な攻撃者は…

- 悪意のある**内部の社員**（インサイダー）
- ハッキングされた**開発者アカウント**

…に限られます。それでも、一度侵入されると被害がプロジェクト全体に広がるため、非常に危険です。

## 対策・今後の展望

### ✅ Googleはすでに修正済み
Googleはこの脆弱性をすでに修正しました。VarisとGoogleの両社は「この脆弱性が実際の攻撃に使われた形跡はない」と発表しています。

### 🛡️ 私たちができること・企業が学ぶべきこと

1. **権限管理を徹底する**
   - 「最小権限の原則」＝必要最低限の権限しか与えないことが大切。誰でも編集できる状態にしてはいけない。

2. **サンドボックスの分離を確認する**
   - 複数のシステムが「同じ部屋」を共有しているなら、きちんと仕切りがあるか確認が必要。

3. **重要なファイルには書き込み禁止を設定する**
   - 今回のような「誰でも上書きできるファイル」があるのは設計上の欠陥。

4. **外部通信を制限する**
   - コードが実行される環境からは、不要なインターネット接続を遮断すべき。

## 過去記事との関連

以前「**GhostLock（幽霊の鍵穴）**」という15年間発見されなかったLinuxの脆弱性について解説しましたが、今回の件と共通するテーマがあります。

それは「**信頼された環境の内側に潜む穴**」という点です。

- GhostLockは「Linuxというみんなが信頼するOSの内部」に穴があった
- 今回は「Googleが管理する安全なはずのクラウド環境の内部」に穴があった

また、**GitHub Copilot**の記事でも触れましたが、「AIやクラウドツールの新機能には、まだ発見されていないリスクが潜んでいる」ことを改めて示す事例と言えます。AIチャットボットや開発支援ツールが普及するほど、こうした「新しい攻撃面」が増えていくことを覚えておきましょう。

## 用語解説

| 用語 | 説明 |
|------|------|
| **Dialogflow CX** | GoogleのAIチャットボット作成ツール |
| **コードブロック（Code Blocks）** | チャットボットにPythonプログラムを追加できる機能 |
| **脆弱性** | システムのセキュリティ上の「穴」 |
| **サンドボックス** | プログラムを安全な隔離環境で動かす仕組み |
| **フィッシング** | 偽のメッセージでパスワードなどをだまし取る攻撃 |
| **インサイダー攻撃** | 内部の人間による攻撃 |
| **VPC Service Controls** | Googleのデータ流出防止機能 |
| **IMDS（Instance Metadata Service）** | クラウド上のサーバーが使う内部的な情報サービス。本来は外部から触れてはいけない |
| **Cloud Run** | Googleのプログラム実行環境（サービス） |
| **最小権限の原則** | 必要な権限だけを与えてリスクを最小化するセキュリティの考え方 |
| **exec()関数** | Pythonでプログラムコードをそのまま実行する関数。使い方を誤るとリスクが高い |

> 💡 **まとめ**
> 「Googleが管理しているから安全」と思っていたクラウド環境に、実は「共有の部屋の鍵がかかっていない」という問題がありました。今回は悪用された証拠はなく、すでに修正済みです。しかし、便利な新機能を使うほど、「その裏にどんなリスクがあるか」を考える習慣が大切だと改めて教えてくれる事例でした。
