# 1万7千から110万台へ：ルーメン・テクノロジーズが「自社の資産管理」を作り直した話

**元記事**: [From 17,000 to 1.1 Million Assets: How Lumen Technologies Rebuilt Exposure Management at Scale](https://inl03.netline.com/ltr6/?_m=3n.009a.4026.sp0ao46r89.32x0)
**解説日**: 2025年7月11日

---

## 背景知識

まず、この記事を理解するために必要な基本的な考え方を説明します。

### 🏫 学校で例えると…

学校のパソコンを管理している先生を想像してください。

- 「うちの学校にパソコンは何台ある？」と聞かれたとき、正確に答えられますか？
- 教室のPC、先生用のノートPC、図書室のタブレット、体育館のプロジェクター、サーバー室の機器…
- それぞれを「理科の先生」「情報の先生」「図書室の司書」がバラバラに管理していたら、全体像はわかりませんよね？

企業のIT管理も、まったく同じ問題が起きています。

### 📋 「資産管理（アセットインベントリ）」とは？

**資産管理（アセットインベントリ）** とは、「自社が持っているIT機器やシステムをすべてリスト化して把握すること」です。

- パソコン、サーバー、スマートフォン、ネットワーク機器など
- これが正確でないと、「どこにセキュリティの穴があるか」が把握できません

### 🔓 「露出管理（エクスポージャー管理）」とは？

**露出管理（Exposure Management）** とは、「自社のどのシステムが外部からの攻撃にさらされているか（露出しているか）を把握して管理すること」です。

- 鍵のかかっていない窓を探すようなイメージです
- 家の中に窓が何枚あるかわからないと、全部鍵をかけられないですよね？

### 🏢 ルーメン・テクノロジーズとは？

**ルーメン・テクノロジーズ（Lumen Technologies）** は、アメリカの大手通信会社です。創業から約100年の歴史を持ち、インターネット回線や通信インフラを企業向けに提供しています。日本でいうとNTTやKDDIのようなイメージです。

## 何が起きたのか

### 📊 驚きの発見：知らない間に機器が60倍に！

ルーメン・テクノロジーズのセキュリティチームが、自社のIT機器を正確に数えようとしたところ、衝撃的な事実が判明しました。

| 段階 | 把握していた機器数 |
|------|------------------|
| 調査前（もともとの認識） | 約**1万7千台** |
| 最初の調査後 | 約**50万台** |
| 現在の正確な数 | 約**110万台** |

**なんと、もともと把握していた数の約60倍もの機器が存在していたのです！**

### 🤯 なぜこんなことが起きたのか？

ルーメン・テクノロジーズでは、**40以上もの異なる管理ツール**がそれぞれバラバラに機器を管理していました。

- ツールAは「このサーバーは存在する」と言う
- ツールBは「そのサーバーは知らない」と言う
- ツールCは「別のサーバーがある」と言う

…まるで、複数の地図アプリがそれぞれ違う道を示しているような状態です。

セキュリティ部門のディレクター、ジェフ・クラン氏はこう語っています。

> 「セキュリティインシデント対応の電話をしているとき、誰が何を管理しているのか、まったくわからない状態でした」

## 技術的な詳細

### 🔧 どうやって問題を解決したのか？

ルーメンのチームは **Axonius（アクソニウス）** というツールを使いました。

**Axoniusとは？**
「資産インテリジェンス・プラットフォーム」と呼ばれるツールで、バラバラに存在する複数の管理システムのデータを一か所に集めて、矛盾を整理し、「信頼できる一つの正確なリスト」を作るものです。

#### 具体的なイメージ

```
[ツール1のデータ]  ─┐
[ツール2のデータ]  ─┤
[ツール3のデータ]  ─┼──→ Axonius ──→ 【正確な一覧表】
        ⋮          ─┤        （40以上のツールを統合）
[ツール40のデータ] ─┘
```

### ⚡ 正確なリストができると何ができるのか？

**① ゼロデイ脆弱性への素早い対応**

**ゼロデイ脆弱性（Zero-day vulnerability）** とは、「発見されたばかりで、まだ修正パッチ（修理プログラム）が存在しないセキュリティの穴」のことです。

> 例：「新種の鍵穴破り工具が出回った！」という情報が入ったとき、自分の家の鍵穴が同じ型かどうか、すぐに確認できますか？

ルーメンでは今や、**数分以内に**「どの機器が影響を受けるか」「外部からアクセスできる状態か」「担当者は誰か」がわかるようになりました。チャットボット（自動メッセージプログラム）でエンジニアに即座に通知も送れます。

**② アプリケーション単位でのリスク管理**

以前は「このサーバーは安全か？」しかわかりませんでした。
今では「このサーバーが支えているアプリは何か？そのアプリがやられたら、どのくらいの売上に影響が出るか？」まで把握できます。

**③ 「スキャンしてばらまく」からの卒業**

以前のやり方（業界では **"scan and spam"（スキャン＆スパム）** と皮肉られています）は、こんな感じでした：

```
① 全システムをスキャンして脆弱性を発見
② 結果を大量にリストにして担当者にメール
③ 担当者は山積みのリストを見て途方に暮れる
④ 本当に危険なものが埋もれる
⑤ 結果的に何も直らない
```

今のやり方は：

```
① 機器の正確なリスト × 脆弱性の深刻さ × 業務への影響
② 「今すぐ直すべき本当に危険なもの」だけを厳選して提示
③ 担当者が効率よく対応できる
```

### 📏 CVSSスコアの問題点

**CVSSスコア（Common Vulnerability Scoring System）** とは、脆弱性の深刻さを0〜10点で表す世界共通の指標です。

- 10点に近いほど危険
- しかし！「理論上は危険」でも「自社の環境では実際には使われていないシステム」なら優先度は低くていいはずです

調査によると、**56%の組織がまだCVSSスコアだけを頼りに対応順位を決めています**が、これでは「自社にとって本当に危険なもの」が見極められません。

## なぜ重要なのか

### 🌍 これは他人事じゃない

この記事で紹介されている調査（600人以上のセキュリティ責任者が対象）によると：

- **55%の組織**は、資産情報と脆弱性情報を一か所にまとめられていない
- つまり、多くの会社が「自社に何台の機器があるか正確に把握できていない」状態

### 💡 セキュリティの基本原則

> **「守れないものは管理できない。管理できないものは守れない。」**

自分の家の窓が何枚あるかわからないと、全部に鍵をかけられません。企業のセキュリティも同じです。

### 📈 経営的な影響

クラン氏はこう語っています。

> 「自社の責任範囲がどれほど大きいかを数字で示せたことで、経営層からの支持と予算を得られるようになりました」

セキュリティは「お金がかかるだけ」と思われがちですが、正確なデータがあれば「どこにいくら投資すべきか」を説得力を持って示せます。

## 対策・今後の展望

### ✅ 企業・組織がすべきこと

| やること | 内容 |
|---------|------|
| **資産の棚卸し** | 「うちには何台の機器があるか」を正確に把握する |
| **ツールの統合** | バラバラの管理ツールのデータを一元化する |
| **リスクの優先順位付け** | CVSSスコアだけでなく、業務への影響も考慮する |
| **担当者の明確化** | 各機器・システムの「責任者」を明確にしておく |

### 🔮 今後の方向性

ルーメン・テクノロジーズは今後、セキュリティの露出状況を**自社が販売している製品・サービスの売上リスクと直接連動させる**計画です。

> 「このシステムがやられたら、年間〇〇億円の売上に影響が出る」

このように、セキュリティをビジネスの言葉で語れるようになることが、次世代のセキュリティ管理の姿です。

## 過去記事との関連

今回は特定の過去記事との関連はありませんが、この記事は **「セキュリティの基礎中の基礎」** に関わる話です。

よく「最新の攻撃手法」や「高度なハッキング」が話題になりますが、実は多くの企業が「自分の家に窓が何枚あるかわからない」という、もっと根本的な問題を抱えています。華やかな攻撃手法の話の前に、**「自分たちが守るべきものを正確に把握する」** という基本が、いかに重要かを示す好例です。

## 用語解説

| 用語 | 読み方 | 意味 |
|------|--------|------|
| **アセットインベントリ** | Asset Inventory | IT機器やシステムの一覧表・棚卸し |
| **エクスポージャー管理** | Exposure Management | 外部からの攻撃にさらされているリスクを管理すること |
| **ゼロデイ脆弱性** | Zero-day Vulnerability | 発見されたばかりで修正パッチがない、セキュリティの穴 |
| **EDR** | Endpoint Detection and Response | PC・サーバーへの不正アクセスを検知・対応するセキュリティツール |
| **CVSS** | Common Vulnerability Scoring System | 脆弱性の深刻さを0〜10点で示す世界共通の指標 |
| **CMDB** | Configuration Management Database | ITシステムの構成情報を管理するデータベース |
| **パッチ** | Patch | ソフトウェアの不具合やセキュリティの穴を修正するプログラム |
| **スキャン＆スパム** | Scan and Spam | 脆弱性を大量に検出して、整理せず大量に通知するだけの古いやり方（批判的な表現） |
| **チャットボット** | Chatbot | 自動でメッセージを送受信するプログラム |
| **インシデント対応** | Incident Response | セキュリティ事故が起きたときの対処活動 |
