# Injective Labs のGitHubが乗っ取られ、暗号資産ウォレットの秘密鍵を盗む悪意のあるパッケージが公開された事件

**元記事**: [Injective Labs GitHub Compromise Pushes Wallet-Key-Stealing npm Packages](https://inl03.netline.com/ltr6/?_m=3n.009a.4027.sp0ao46r89.32yq)
**解説日**: 2026年7月14日

---

## 背景知識

今回のニュースを理解するために、まずいくつかのキーワードを押さえておきましょう。

### 🪙 暗号資産（仮想通貨）ウォレットとは？
ビットコインやイーサリアムなどの暗号資産（仮想通貨）を管理するための「財布」のようなものです。銀行口座に似ていますが、管理するのは銀行ではなく本人です。

### 🔑 秘密鍵・ニーモニックフレーズとは？
- **秘密鍵（プライベートキー）**：ウォレットの「パスワード」にあたる長い文字列です。これを知っている人は、そのウォレットの暗号資産を自由に動かせます。
- **ニーモニックフレーズ（シードフレーズ）**：秘密鍵を12〜24個の英単語で表したものです。「abandon apple banana...」のような形式で、ウォレット全体の「マスターキー」とも言えます。これが漏れると、ウォレットの中身をすべて盗まれる可能性があります。

### 📦 npmとは？
**npm（Node Package Manager）** とは、プログラマーが使う「プログラム部品の配布サービス」です。料理に例えると、「レシピ本」ではなく「調理済み食材を宅配するサービス」のようなものです。プログラマーはコマンド1つで世界中の開発者が作った「部品（パッケージ）」を自分のプロジェクトに組み込めます。

### 🏢 Injective Labs とは？
ブロックチェーン（分散型台帳技術）を使った金融プラットフォームを開発している企業です。その開発キット（SDK）は、多くの開発者が暗号資産アプリを作るときに利用しています。

### 🏗️ GitHubとは？
プログラムのソースコード（設計図）を保存・共有する場所です。多くのオープンソースプロジェクト（誰でも中身を見られるプログラム）がここで管理されています。

### 📡 ソフトウェアサプライチェーン攻撃とは？
製品そのものではなく、製品を作るための「部品・材料の流通ルート」を狙う攻撃です。スーパーの食材に製造元で毒を混入するようなイメージです。開発者が信頼して使っている部品を汚染することで、その部品を使った大量のアプリに被害を広げられます。

## 何が起きたのか

2026年7月8日、**Injective LabsのGitHubリポジトリ（プログラム保管庫）が何者かに乗っ取られ**、悪意のある「改ざん済みパッケージ」がnpmに公開されました。

具体的には以下のことが起きました：

1. 攻撃者が、**以前からそのプロジェクトに貢献していた開発者のGitHubアカウント**を乗っ取った（または悪用した）
2. そのアカウントを使って、信頼されているコードに「こっそり盗聴コードを埋め込んだ」
3. **`@injectivelabs/sdk-ts` バージョン1.20.21** という名前でnpmに公開した
4. さらに、このパッケージに依存する **17個の関連パッケージ**にも同じバージョンを展開した
5. これらのパッケージを使っている開発者・アプリのユーザーが影響を受けた

現在は問題のバージョンは「非推奨」とマークされていますが、GitHubからは**まだダウンロードできる状態**とのことです。

## 技術的な詳細

### 🎭 巧妙な偽装：「分析機能」に見せかけた盗聴コード

攻撃者が特に巧みだったのは、**悪意のあるコードを「テレメトリ機能（利用状況の分析）」として偽装した**点です。

テレメトリとは、スマホアプリが「どの機能がよく使われているか」を開発者に送信する機能のことです。多くのアプリに普通に搭載されています。

悪意のあるコードは **`trackKeyDerivation()`** という関数名で追加されました。その説明文には、こう書かれていました：

> 「どのキー生成方式が使われているか（hexかmnemonicか）を追跡し、タイミングパターンを分析してSDKチームがパフォーマンスのボトルネックを特定できるようにします。すべての指標は非同期で送信され、キー生成を妨げることはありません。」

一見すると、まったく無害な「開発改善のための分析機能」に見えます。しかし実際には…

```
【本当に送っていたもの】
秘密鍵を生成するためのニーモニックフレーズ（マスターキー）
      ↓
外部の攻撃者サーバーへHTTPS通信で送信
```

### 🕵️ なぜ発見されにくかったのか？

通常、悪意のあるパッケージは「インストール時」に怪しい動作をするため発見されやすいです。しかし今回のマルウェアは：

- **インストール時には動かない**（インストール後、実際に使われるときだけ動く）
- **実在する開発者アカウント**から投稿されていた（信頼済みの人物に見える）
- **公式の自動リリース手順（OIDC パイプライン）** を通じて公開された（正規の手順を踏んでいる）
- **複数のリクエストを2秒間まとめて1回で送信**することで、不審な大量通信を避けた

これらの工夫により、セキュリティツールや人間の目をくぐり抜けようとしていました。

### 📬 データはどこに送られたか？

盗んだ情報は以下のサーバーに送られていました：

```
testnet.archival.chain.grpc-web.injective[.]network
```

このドメイン名は、**本物のInjective Labsのサービスに見えるよう巧妙に作られています**。「injective」という名前が入っているため、怪しいURLだと気づきにくい設計です。

## なぜ重要なのか

### 💰 直接的な被害：暗号資産の盗難リスク

ニーモニックフレーズや秘密鍵が漏れると、**攻撃者はウォレットの暗号資産をすべて盗むことができます**。しかも暗号資産の取引は原則として取り消せません。銀行のように「被害を届け出れば返ってくる」という仕組みがないのです。

### 🔗 サプライチェーン攻撃の広がり

今回は直接このパッケージを使っていない人も危険にさらされました。なぜなら、問題のパッケージに**依存している17個の別パッケージ**にも同じバージョンが展開されたからです。

例えば：
```
あなたのアプリ
  └─ @injectivelabs/wallet-core（直接使用）
        └─ @injectivelabs/sdk-ts@1.20.21（悪意のある版）← 気づかずに使ってしまう
```

このような「間接的な依存関係」を通じた被害を**トランジティブ依存の汚染**と呼びます。

### 🏭 信頼されたインフラが悪用された

- 信頼された開発者のアカウント
- 公式のリリースパイプライン
- 有名プロジェクトの公式リポジトリ

これらすべてが悪用されたことで、**「信頼できる場所から来たコード」という前提が崩れた**ことになります。これはソフトウェア開発の世界全体への警告でもあります。

## 対策・今後の展望

### ⚡ 今すぐやるべきこと（影響を受けた開発者向け）

1. **パッケージを最新版（1.20.23）に更新する**
   ```bash
   npm install @injectivelabs/sdk-ts@1.20.23
   ```

2. **秘密鍵・ニーモニックフレーズをすぐに「ローテーション（更新）」する**
   - 問題のバージョンを使ったことがあるなら、そのウォレットの秘密鍵は「漏れた」と考えて、**新しいウォレットを作り、資産を移す**必要があります

3. **間接的な依存関係も確認する**
   - 自分が直接使っていないパッケージも、依存関係をたどって確認しましょう

### 🛡️ 一般的な教訓

| 教訓 | 具体的な対策 |
|------|-------------|
| パッケージの更新は慎重に | 自動更新より、変更内容を確認してから更新する |
| 有名プロジェクトでも油断しない | 「公式だから安全」は通用しない時代 |
| 秘密鍵の管理を厳重に | ハードウェアウォレットや安全なキー管理システムを使う |
| 依存関係の監査ツールを使う | Socket、StepSecurityのようなツールで定期的にチェック |

## 用語解説

| 用語 | 説明 |
|------|------|
| **npm** | JavaScriptのプログラム部品を配布・管理するサービス。世界最大のパッケージレジストリ |
| **GitHub** | プログラムのソースコードを保存・共有するプラットフォーム |
| **SDK（ソフトウェア開発キット）** | 特定のサービス用のアプリを作るための道具一式 |
| **秘密鍵（プライベートキー）** | 暗号資産ウォレットを操作するためのパスワードにあたる文字列 |
| **ニーモニックフレーズ** | 秘密鍵を12〜24の英単語で表したもの。ウォレットのマスターキー |
| **テレメトリ** | アプリの利用状況データを自動送信する機能。今回は偽装に使われた |
| **サプライチェーン攻撃** | ソフトウェアの部品・流通経路を汚染する攻撃手法 |
| **トランジティブ依存** | 直接使っていないが、使っているパッケージが間接的に使っている依存関係 |
| **OIDC パイプライン** | ソフトウェアを自動的にビルド・公開する信頼済みの手順 |
| **HTTPS POST** | インターネット上でデータを送信する通信方式の一つ |
| **非推奨（deprecated）** | 「使わないでください」と警告されている状態。ただし削除はされていない |
| **リポジトリ** | GitHubなどでプログラムのファイルを管理している保管場所 |
