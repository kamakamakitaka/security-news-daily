# Grok BuildがGitリポジトリ全体をxAIのサーバーにこっそり送信していた問題

**元記事**: [Grok Build Uploaded Entire Git Repositories to xAI Storage, Not Just Files It Read](https://inl03.netline.com/ltr6/?_m=3n.009a.4029.sp0ao46r89.331o)
**解説日**: 2025年7月15日

---

## 背景知識

まず、この記事を理解するためのキーワードを説明します。

### 🤖 Grok Build とは？
**Grok**は、イーロン・マスク氏が設立した「xAI」という会社が作ったAIアシスタントです。「Grok Build」はその中でも、**プログラマーのコーディング（プログラムを書く作業）を手伝う専用のツール**（CLIツール）です。ChatGPTのGitHub Copilotや、ClaudeのClaude Codeのような「AIコーディングアシスタント」の一種です。

### 📁 Gitリポジトリとは？
**Git（ギット）**は、プログラマーが「コードの変更履歴」を管理するためのシステムです。たとえるなら、**Wordの「変更履歴の追跡」機能の超強力版**です。

**リポジトリ（repo）**とは、そのGitで管理されているプロジェクトのフォルダ全体のことです。リポジトリには以下のものが含まれます：
- 現在のすべてのプログラムファイル
- **過去のすべての変更履歴**（「昨日削除したコード」も残っています！）
- 設定ファイルや、場合によっては**パスワードや秘密の鍵**

### ☁️ クラウドストレージとは？
Google Driveのような、インターネット上にデータを保存できるサービスのことです。今回はxAIが「Google Cloud Storage」というサービス上に専用のバケット（保存場所）を持っていました。

### 🔑 APIキーとは？
外部サービスを使うための「合言葉（パスワードのようなもの）」です。たとえば「このAPIキーを持っている人だけがこのサービスを使える」という仕組みです。流出すると**サービスの不正利用や課金被害**につながります。

## 何が起きたのか

### 🔍 研究者が発見した驚くべき事実

セキュリティ研究者（cereblabというハンドルネームの人物）が、Grok BuildというAIコーディングツールの**通信を調査**したところ、**衝撃的な事実**が発覚しました。

> **Grok Buildは、AIが作業に必要なファイルだけでなく、Gitリポジトリ（プロジェクトフォルダ）の全データを丸ごとxAIのサーバーに送信していた**

### 📊 どれくらいの量？

この差がどれだけ大きいか、数字で見てみましょう：

| 送信先 | 内容 | データ量 |
|--------|------|---------|
| AIモデル本体 | 実際に作業で使ったデータ | 約192KB（はがき数枚分） |
| **xAIのストレージ** | **リポジトリ全体** | **約5.10GB（映画1本分以上）** |

その差はなんと**約27,800倍**！ AIが実際に読んだデータと、実際に送信されたデータの量が27,800倍も違ったのです。

### 🕵️ 「絶対に開かないで」と言ったファイルまで送られた

研究者は実験として、`never_read_canary.txt`（「絶対に読まないカナリア」という名前）というファイルを作り、**Grokに「このファイルを開いてはいけない」と明示的に指示しました。**

AIはそのファイルを実際には読みませんでした。しかし——**送信されたリポジトリの中にそのファイルは含まれていました。**

> 📌 「カナリア（Canary）」とは、セキュリティ分野でよく使われる「罠」のことです。炭鉱でガス漏れを検知するためにカナリア（鳥）を使っていた歴史から来ています。「このファイルが外に出たら、何かがおかしい」という目印として使われます。

## 技術的な詳細

### 📡 2つの通信チャンネル

Grok Buildは実は**2つの別々の通信経路**を使っていました：

```
あなたのPC
 ├── [チャンネル①] /v1/responses  → AIモデル本体（質問への回答）
 └── [チャンネル②] /v1/storage   → xAIのストレージ（リポジトリ丸ごと！）
```

チャンネル①は「AIと会話するための通信」なので、必要なファイルだけ送るのは理解できます。しかしチャンネル②は**ユーザーに知らされていなかった、こっそりした別の通信**でした。

### 📦 どうやって送っていたか

リポジトリは**73個の塊（チャンク）**に分割され、それぞれ約75MBずつ送信されていました。すべて正常に受信された（HTTP 200 = 「受け取りました」）という応答が返ってきていました。

送り先のバケット名は `grok-code-session-traces`（「Grokコードセッションの記録」）という名前で、**Grokのプログラムの中にハードコード**（直接書き込み）されていました。

### 🔐 パスワードも丸ごと送信

さらに深刻だったのが、`.env`ファイル（環境設定ファイル）の扱いです。

`.env`ファイルとは、パスワードやAPIキーを書いておくファイルで、**本来は絶対に外部に送ってはいけない**ものです。

研究者が偽のパスワード（`API_KEY`と`DB_PASSWORD`）を入れた`.env`ファイルを用意したところ：

1. AIがそのファイルを読む → **ファイルの内容がAIへの通信に含まれた（マスキングなし）**
2. さらに `session_state`（セッション状態）として → **ストレージにも保存された**

実際のパスワードではなかったので今回は被害はありませんでしたが、**本物のパスワードだったら完全に流出していた**ことになります。

### ⚙️ 「設定をオフにしても意味がなかった」

ユーザーが「モデル改善のためのデータ提供をオフ」にする設定があります。多くの開発者はこれをオフにすれば「データが送られない」と思うでしょう。

しかし実際には：

```
「モデル改善」設定オフ → 学習には使われない（かも）
                      → でもアップロード自体は止まらない！
```

サーバーの応答を確認すると、設定をオフにしても `trace_upload_enabled: true`（「記録のアップロードは有効」）のままでした。

**学習に使うかどうかと、送信するかどうかは、全く別の設定だった**のです。ユーザーに見えていたのは学習設定だけで、送信設定はユーザーが触れない場所にありました。

## なぜ重要なのか

### 💼 企業の機密情報が危険にさらされる

Gitリポジトリには、過去の変更履歴が**すべて**含まれています。つまり：

- 「あ、このパスワード、コードに書いちゃった。削除しよう」と削除しても——**Gitの履歴には残っている！**
- 社内の内部URLやシステム構成図
- 顧客のデータ
- 競合他社に知られたくない独自アルゴリズム

これらがすべて、ユーザーの知らないうちにxAIのサーバーに送られていた可能性があります。

### 🆚 他のAIツールとの比較

研究者が他のAIコーディングツールも同様にテストした結果：

| ツール | リポジトリ全体の送信 |
|--------|------------------|
| Grok Build | **あり（全体送信）** |
| Claude Code | なし |
| Codex | なし |
| Gemini | なし（テスト中） |

**Grok Buildだけが突出して多くのデータを送信していました。**

ただし、「だから他のツールは安全」とは言い切れません。どのツールも「開いたファイルはサーバーに送る」という点では同じです。

### 🚨 「送信 = 学習に使われた」ではない

記事では明確に述べられていますが、今回判明したのは：
- ✅ データが**送信された**こと
- ✅ データが**受け取られ、保存された**こと
- ❌ **学習に使われたかどうかは不明**（そこまでは証明されていない）

## 対策・今後の展望

### 🛡️ xAIの対応

2025年7月13日、研究者が同じバージョン（0.2.93）でテストしたところ、突然ストレージへのアップロードが止まりました。

サーバーの応答が変わっていました：
- `disable_codebase_upload: true`（「コードベースのアップロード無効」）
- `trace_upload_enabled: false`（「トレースアップロード無効」）

**クライアント（ユーザー側のアプリ）はバージョンが変わっていないのに、動作が変わった**ことから、これは**サーバー側でこっそり変更した「スイッチ」**であることがわかります。

ただし：
- すべてのユーザーに適用されたかは不明
- 永続的な変更かどうかも不明
- **正式なセキュリティアドバイザリーや変更ログは発表されていない**（X（旧Twitter）への投稿だけ）

### 👤 ユーザーとしての対策

もしGrok Buildを使っていた方へのアドバイスです：

1. **機密リポジトリには使わない**
   - 顧客情報、社内システム、パスワードが含まれるリポジトリでのAIツール使用は慎重に

2. **`.env`ファイルを確認する**
   - AIツールに読ませるディレクトリに本物のパスワードが入ったファイルがないか確認

3. **通信内容を把握する**
   - どのAIツールも「何かをサーバーに送っている」という意識を持つ

4. **企業の場合はゼロデータリテンション契約を確認**
   - xAIはエンタープライズ（企業向け）プランでは「ゼロデータリテンション（データを保存しない）」オプションがあると説明しています

### 📋 今後望まれること

- 送信されるデータの範囲を明確にした**透明性のある公式ドキュメント**
- パスワードなど機密情報の**自動マスキング機能**
- ユーザーが「送信範囲」を細かく制御できる**設定UI**
- 独立した第三者機関による**セキュリティ監査**

## 過去記事との関連

今回の件は、**AIコーディングツール全般のプライバシー問題**という大きなトレンドの一部です。GitHub CopilotやClaude Code、Geminiなど、多くのAIコーディングアシスタントが登場する中で、「AIを使うと何がサーバーに送られるのか」という問いは、エンジニアにとって避けられない重要なテーマになっています。

特に企業での利用においては、「便利だから使う」だけでなく、「何が送られているか把握して使う」というリテラシーが今まで以上に求められています。

## 用語解説

| 用語 | 説明 |
|------|------|
| **CLI** | Command Line Interface。マウスを使わず、文字を入力して操作するツールのこと |
| **Gitリポジトリ** | Gitで管理されているプロジェクトのフォルダ。変更履歴がすべて含まれる |
| **コミット履歴** | Gitに保存された「過去のすべての変更記録」。削除したファイルも残る |
| **Google Cloud Storage** | Googleが提供するクラウド上のデータ保存サービス |
| **バケット** | クラウドストレージ上の「フォルダ」のようなもの |
| **API** | Application Programming Interface。サービスと外部プログラムをつなぐ仕組み |
| **APIキー** | APIを使うための「合言葉（パスワード）」 |
| **`.env`ファイル** | パスワードやAPIキーを書いておく設定ファイル。外部に漏れてはいけない |
| **HTTP 200** | 「正常に受信しました」というサーバーからの応答 |
| **カナリア（Canary）** | セキュリティテストで使う「罠」となるファイルやデータ |
| **ハードコード** | プログラムのソースコードに直接値を書き込むこと |
| **ゼロデータリテンション** | 「データを一切保存しない」という契約・設定 |
| **セキュリティアドバイザリー** | セキュリティ問題に関する公式の注意喚起・報告書 |
| **マスキング** | パスワードなどを「＊＊＊」のように隠す処理 |

---

> 💡 **まとめると**：便利なAIコーディングツールが、必要以上のデータ（プロジェクト全体の歴史）をこっそり送信していました。開発者は「モデル改善設定をオフにすれば安全」と思っていましたが、実は別の経路でデータが送られていました。現在は修正されたようですが、透明性の問題は残っています。AIツールを使う際は「何がどこに送られているか」を意識することが大切です。
