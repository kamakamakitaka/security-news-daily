# OAuthクライアントIDのなりすましで盗まれたMicrosoft認証情報が検証される攻撃が発覚

**元記事**: [OAuth Client ID Spoofing Lets Attackers Validate Stolen Microsoft Entra Credentials](https://inl03.netline.com/ltr6/?_m=3n.009a.4029.sp0ao46r89.331i)
**解説日**: 2025年7月14日

---

## 背景知識

まず、今回の記事を理解するために必要な基本的な知識を整理しましょう。

### 🏢 Microsoft Entra ID（エントラ ID）とは？

**Microsoft Entra ID**（旧名：Azure Active Directory）は、企業が使う「デジタルの社員証管理システム」のようなものです。

> **例え話**: 会社の入館ゲートをイメージしてください。社員証（アカウント）をかざすと「この人は○○部署の△△さんだ」と識別して、入れる部屋と入れない部屋を管理します。Entra IDはそれをクラウド（インターネット上）でやっています。

### 🔑 OAuth（オーオース）とは？

**OAuth**は「許可の仕組み」です。

> **例え話**: Googleアカウントで別のサービスにログインする「Googleでログイン」ボタンを使ったことはありませんか？あれがOAuthです。「Googleが認めたアプリだよ」という証明書を使って、パスワードを直接渡さなくてもログインできる仕組みです。

### 🪪 クライアントID（Client ID）とは？

OAuthを使うアプリには、それぞれ固有の「アプリの身分証明書番号」が割り当てられています。これが**クライアントID**です。例えば「123e4567-e89b-12d3-a456-426614174000」のような文字列で表されます。

### 📋 サインインログとは？

誰かがログインするたびに記録される「入退室記録」のようなものです。不審なログインがあったときに、セキュリティ担当者がこの記録を見て「おかしいな」と気づきます。

## 何が起きたのか

### 事件の概要

セキュリティ企業**Proofpoint（プルーフポイント）**が、攻撃者たちが使う**新しいズル賢い手口**を発見しました。

この手口を使うと、攻撃者は以下のことができてしまいます：

1. 🔍 **アカウントが実在するか確認できる**（アカウント列挙）
2. 🔓 **盗んだパスワードが正しいか確認できる**（認証情報の検証）
3. 👻 **しかもログインの記録がほぼ残らない！**（検知回避）

> **例え話**: 泥棒が家の鍵穴に色々な鍵を試しているのに、防犯カメラには一切映らない、という状況です。守る側は「誰かが侵入しようとしている」と気づけないわけです。

### 発見された攻撃グループ

記事では2つの大規模な攻撃グループが特定されています：

| 攻撃グループ名 | 活動期間 | 規模 |
|---|---|---|
| **UNK_pyreq2323** | 2026年1月〜3月 | 70万個以上の偽クライアントIDを使用、約100万アカウントを標的 |
| **UNK_OutFlareAZ** | 2025年12月〜 | 370万個の偽アプリIDを使用、200万人以上のユーザーを標的 |

## 技術的な詳細

### 攻撃の仕組みをわかりやすく解説

#### ステップ1：普通のログインの場合

通常、アプリがMicrosoftにログインを要求するとき、こんな情報を送ります：

```
ユーザー名: taro@example.com
パスワード: ●●●●●●
クライアントID: （本物のアプリのID）
```

Microsoftは「このアプリは登録済みの正規アプリだ」と確認してからログインを処理し、**ログインの記録を残します**。

#### ステップ2：攻撃者がやっていること

攻撃者は「クライアントID」の部分に**存在しない偽のIDを入れて**送ります：

```
ユーザー名: taro@example.com
パスワード: ●●●●●●
クライアントID: （でっち上げた偽のID）← ここがポイント！
```

#### ステップ3：Microsoftの返答で情報を盗み取る

Microsoftは偽のIDに対して**エラーメッセージを返します**が、そのエラーの種類が状況によって違うのです：

| 状況 | Microsoftからの返答（エラーコード） |
|---|---|
| ユーザー名が存在しない | エラーA「そのユーザーはいません」 |
| ユーザー名は存在するがパスワードが違う | エラーB「パスワードが間違っています」 |
| ユーザー名もパスワードも正しい | エラーC「クライアントIDが無効です」 |

> **例え話**: 銀行のATMで、「カードが無効です」「暗証番号が違います」「その口座は存在しません」と、エラーメッセージが細かく分かれているようなイメージです。攻撃者はこのメッセージの違いを読み取るだけで、「この口座は実在する」「このパスワードは正しい」と判断できてしまいます。

#### ステップ4：ログに記録が残らない

さらに厄介なのは、**偽のクライアントIDを使うとログインのアプリ名欄が空白になる**ことです。セキュリティ担当者が「怪しいアプリからの大量ログイン試行がある」と検知するシステムを使っていても、アプリ名が空白なので**警告が発動しない**のです。

### ROPC フロー（難しいけど一言で）

攻撃者は**ROPC（Resource Owner Password Credentials）フロー**という、少し古いタイプの認証方式を悪用しています。これはユーザー名とパスワードを直接送る方式で、現在はセキュリティ上の理由から推奨されていませんが、まだ使えてしまう環境が多く存在します。

## なぜ重要なのか

### 影響の大きさ

```
📊 攻撃規模のまとめ
・標的となったアカウント数：合計 約300万以上
・影響を受けたテナント数：約4,000（テナント＝企業や組織の単位）
・UNK_pyreq2323 による アカウントロックアウト：標的の約28%
```

> **テナントとは？**: Microsoft 365などを使っている「○○株式会社」という単位のことです。4,000テナントということは、約4,000社・4,000組織が影響を受けた可能性があります。

### 特に怖いポイント3つ

#### 😱 怖いポイント① 検知が非常に難しい
ログにはなりすましたIDの番号だけ残り、アプリ名は空白。既存のセキュリティツールが見落としやすい構造になっています。

#### 😱 怖いポイント② 大規模な認証情報の検証に悪用できる
「漏洩したアカウントリスト」を持っている攻撃者が、どのアカウントが今も有効かを**ばれずに一気に確認**できます。

#### 😱 怖いポイント③ 攻撃者の間で急速に普及している
2025年12月末から2つの独立した攻撃グループが同時期に使い始めており、攻撃者コミュニティでこの手法が広まっている可能性があります。

## 対策・今後の展望

### 企業・組織の管理者ができること

#### ✅ 対策1：ROPC フローを無効化する
古い認証方式（ROPC）を使えないよう設定を変更することで、この攻撃の手口そのものを封じることができます。

#### ✅ 対策2：ログの監視を強化する
- アプリケーション名が**空白のサインインログ**を特別に監視する
- 短時間に大量の認証エラーが発生していないかチェックする

#### ✅ 対策3：多要素認証（MFA）の導入
パスワードが知られてしまっても、**スマホへの確認通知などの第2の確認**があれば不正ログインを防げます。

> **MFAとは？**: 「パスワード＋スマホへのSMS認証コード」のように、2つ以上の確認方法を組み合わせる仕組みです。

#### ✅ 対策4：条件付きアクセスポリシーの設定
「特定の国や地域以外からのログインは拒否する」「登録していないデバイスからはログインできない」といったルールを設定します。

### 今後の展望

Proofpointは今回の発見をMicrosoftに報告しており、Microsoftが今後この「エラーメッセージの差異」という設計上の問題を修正することが期待されます。ただし、修正されるまでの間は引き続き注意が必要です。

## 過去記事との関連

今回の記事では、以前から知られていた攻撃グループ **UNK_CustomCloak** の手法（廃止されたMicrosoftアプリ「Windows Live Custom Domains」を悪用してログイン制限を回避する手法）が出発点として触れられています。

今回の攻撃はその**進化版**と言えます。以前は「廃止されたアプリを悪用する」という手口でしたが、今回は「クライアントIDそのものを偽造する」という新しいレイヤーが加わり、より検知が難しくなっています。

## 用語解説

| 用語 | 読み方 | 意味 |
|---|---|---|
| **Microsoft Entra ID** | エントラ アイディー | Microsoftが提供する企業向けアカウント管理サービス（旧Azure AD） |
| **OAuth** | オーオース | アプリがユーザーの代わりに別サービスにアクセスする際の「許可の仕組み」 |
| **クライアントID** | ― | OAuthを使うアプリに割り当てられた固有の識別番号 |
| **スプーフィング（Spoofing）** | スプーフィング | 正規のものになりすますこと。「偽装」とも言う |
| **テレメトリ** | ― | システムが自動的に収集する動作ログや統計データ |
| **サインインログ** | ― | 誰がいつどこからログインしたかの記録 |
| **アカウント列挙** | ― | 「このメールアドレスは実在するか」を大量に確認する攻撃 |
| **パスワードスプレー** | ― | 多数のアカウントに対して同じパスワードを試す攻撃 |
| **ROPC フロー** | ― | ユーザー名・パスワードを直接送る古い認証方式 |
| **MFA** | エムエフエー | 多要素認証。パスワード以外の確認手段も使うログイン方法 |
| **テナント** | ― | Microsoft 365などを使う企業・組織の単位 |
| **GUID / UUIDv4** | グイド / ユーユーアイディー | 世界で一意になるよう設計された識別番号の形式 |
| **AADSTS エラーコード** | ― | Microsoftの認証システムが返すエラー番号。状況によって番号が異なる |
| **Proofpoint** | プルーフポイント | 今回の脆弱性を発見・報告したセキュリティ企業 |

---

> 💡 **まとめ**: 今回の攻撃は「エラーメッセージの微妙な違い」を利用してログイン記録を残さずに不正アクセスを試みる、非常に巧妙な手口です。企業側は「多要素認証の導入」と「ログ監視の強化」で対抗することが重要です。個人レベルでも、パスワードの使い回しをやめること・MFAを設定することが自衛策になります！
