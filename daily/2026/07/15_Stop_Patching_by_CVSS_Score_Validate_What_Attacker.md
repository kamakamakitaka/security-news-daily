# CVSSスコアだけでパッチを当てるのをやめよう。攻撃者が本当に悪用できるものを見極めよう

**元記事**: [Stop Patching by CVSS Score. Validate What Attackers Can Actually Exploit](https://inl03.netline.com/ltr6/?_m=3n.009a.4030.sp0ao46r89.332q)
**解説日**: 2025年7月15日

---

## 背景知識

このニュースを理解するために、まずいくつかの基本的な概念を押さえておきましょう。

### 🔢 CVSSスコアって何？

**CVSS（Common Vulnerability Scoring System）** とは、「共通脆弱性評価システム」のことです。
ソフトウェアやシステムの弱点（脆弱性）がどれくらい危険かを、**0〜10点の数字で表す評価システム**です。

| スコア | 危険度 |
|--------|--------|
| 9.0〜10.0 | 緊急（Critical） |
| 7.0〜8.9 | 重要（High） |
| 4.0〜6.9 | 警告（Medium） |
| 0.1〜3.9 | 注意（Low） |

たとえると、学校のテストの点数のようなもの。**点数が高いほど危険**という目安になっています。

### 🩹 パッチって何？

**パッチ**とは、ソフトウェアの欠陥（バグや脆弱性）を修正するための「プログラムの部品」です。
「破れた服に当てる継ぎ当て（patch）」からきている言葉で、**ソフトウェアのアップデートや修正プログラム**のことを指します。

### 🏢 企業のセキュリティ担当者の日常

大きな企業のシステムには、毎月何百・何千もの脆弱性が見つかります。セキュリティ担当者は「どれから先に直すか」を決めなければなりません。これが非常に大変な仕事です。

---

## 何が起きたのか

今回の記事は、セキュリティの世界で長年続いている**「間違ったパッチ適用の優先順位付け」**の問題を指摘しています。

### 問題の核心

多くの企業では、脆弱性が見つかったとき、**CVSSスコアが高いもの順に修正（パッチ適用）**していきます。
一見合理的に聞こえますが、実はこれには大きな落とし穴があります。

> 💡 **ポイント**: CVSSスコアが高くても、**実際には攻撃者が悪用できない脆弱性**がたくさんあります！

### 具体的な例え話

🏠 **泥棒対策にたとえると…**

- 家に「玄関の鍵が古い（危険度9点）」と「2階の窓が壊れている（危険度9点）」という問題があるとします
- CVSSスコアだけ見ると両方同じ優先度です
- でも、**玄関前に常に警備員がいる**なら、泥棒は実際には玄関から入れません
- 一方、**2階の窓は外から梯子で簡単に届く**場所にあるなら、こちらが本当の脅威です

つまり、「スコアが高い＝今すぐ攻撃される」とは限らないのです。

## 技術的な詳細

### CVSSスコアの「盲点」

CVSSスコアは**脆弱性そのものの危険性**を評価していますが、以下のような「実際の環境」は考慮していません。

```
CVSSが考慮しないこと
├── その脆弱性を持つシステムがインターネットに公開されているか？
├── 攻撃に必要な認証（ログイン）が別途必要か？
├── 攻撃ツール（エクスプロイト）が実際に存在するか？
├── 自社の防御システム（ファイアウォールなど）で防げるか？
└── 実際の攻撃者がこの脆弱性を狙っているか？
```

### 「攻撃可能性の検証（Exploitability Validation）」とは

記事が推奨しているのは、**「この脆弱性は本当に攻撃者が使えるのか？」を実際に検証する**アプローチです。

🔍 **検証の手順イメージ**

```
ステップ1: 脆弱性を発見する
    ↓
ステップ2: CVSSスコアを確認する（参考程度に）
    ↓
ステップ3: 自分たちの環境で本当に悪用できるか試す
    ↓
ステップ4: 実際に悪用可能なものを優先して修正する
```

### なぜCVSSだけでは不十分なのか

| 状況 | CVSSの評価 | 実際の危険度 |
|------|-----------|------------|
| スコア9.8だが、攻撃ツールが存在しない | 緊急 | 実は低い |
| スコア5.0だが、すでに攻撃コードが出回っている | 警告 | 実は非常に高い |
| スコア8.0だが、インターネットから隔離されている | 重要 | 実は低い |
| スコア6.0だが、外部公開サーバーに存在する | 警告 | 実は高い |

## なぜ重要なのか

### 😰 セキュリティ担当者の「疲弊」問題

CVSSスコア順に機械的にパッチを当て続けると…

- **時間と人員が無限に必要**になる
- 本当に危険な脆弱性への対応が後回しになる
- 「やってもやっても終わらない」状態でチームが疲弊する
- 結果的に**本当の攻撃を見逃す**リスクが高まる

### 📊 実態を示す数字（業界調査より）

セキュリティ業界の調査では、以下のような事実が指摘されています：

- 発見された脆弱性のうち、**実際に攻撃者に悪用されるのは5〜10%程度**
- つまり、CVSSスコア順に全部直そうとすると、**90%以上は「急がなくてよい」もの**かもしれない

### 🎯 攻撃者の視点

攻撃者は「CVSSスコアが高いから狙おう」とは考えません。
攻撃者が考えるのは：

1. **簡単に攻撃できるか？（攻撃ツールがあるか）**
2. **成功したときの利益が大きいか？**
3. **見つかりにくいか？**

## 対策・今後の展望

### ✅ 推奨されるアプローチ

#### 1. 文脈（コンテキスト）を加えた評価

CVSSスコアに加えて、以下の情報も組み合わせましょう：

- **EPSS（Exploit Prediction Scoring System）**: 実際に悪用される確率を予測するスコア
- **KEV（Known Exploited Vulnerabilities）**: アメリカのサイバーセキュリティ機関CISAが公開する「実際に攻撃に使われている脆弱性リスト」

#### 2. 自社環境での検証

```
チェックリスト
□ この脆弱性のあるサービスは外部公開されているか？
□ 攻撃を実行するための条件（認証など）はどれくらい厳しいか？
□ 既知の攻撃コード（PoC）は存在するか？
□ 自社の防御層（WAF、EDRなど）で検知・防御できるか？
□ 実際に攻撃された事例はあるか？
```

#### 3. リスクベースの優先順位付け

| 優先度 | 条件 |
|--------|------|
| 🔴 最優先 | 実際に攻撃されている + 外部公開 |
| 🟠 高優先 | 攻撃ツールが存在 + 外部公開 |
| 🟡 中優先 | 攻撃ツールが存在 + 内部のみ |
| 🟢 低優先 | 理論的な脆弱性のみ + 内部のみ |

### 🔮 今後の展望

セキュリティ業界では、「**リスクベース脆弱性管理（RBVM: Risk-Based Vulnerability Management）**」という考え方が広まりつつあります。AIや機械学習を使って、より精度の高い優先順位付けを自動化しようという動きも加速しています。

## 過去記事との関連

以前、「**Windowsのゼロデイ脆弱性が、Microsoftのパッチ公開直後に研究者によって公開された**」という記事を解説しました。

今回の記事はその話と深く関連しています：

- あの記事では、**パッチが出てもすぐに新たな攻撃コードが公開される**という「パッチ競争」の現実を見ました
- 今回の記事は、その状況を踏まえて「**どのパッチを本当に急いで当てるべきか**」という優先順位の問題を扱っています

つまり：
> **「パッチを当てるスピード」より「正しいパッチを正しい順番で当てること」の方が重要**

という考え方です。ゼロデイ脆弱性のように「攻撃ツールがすでに存在する」ものこそ、CVSSスコアに関係なく最優先で対応すべき、ということがよくわかりますね。

## 用語解説

| 用語 | 読み方 | 意味 |
|------|--------|------|
| **CVSS** | シーブイエスエス | 脆弱性の危険度を0〜10で数値化する評価システム |
| **パッチ** | ぱっち | ソフトウェアの欠陥を修正するプログラム |
| **脆弱性** | ぜいじゃくせい | ソフトウェアやシステムのセキュリティ上の欠陥・弱点 |
| **エクスプロイト** | えくすぷろいと | 脆弱性を実際に攻撃するためのプログラム・手法 |
| **PoC** | ぴーおーしー | 「概念実証」。脆弱性が実際に悪用できることを示すサンプルコード |
| **EPSS** | いーぴーえすえす | 脆弱性が実際に悪用される確率を予測するスコアシステム |
| **KEV** | けーいーぶい | CISAが公開する「実際に攻撃に使われている脆弱性」のリスト |
| **CISA** | しーあいえすえー | アメリカのサイバーセキュリティ・インフラセキュリティ庁 |
| **ファイアウォール** | ふぁいあうぉーる | 不正な通信をブロックするネットワークの防御システム |
| **WAF** | わふ | Webアプリケーションへの攻撃を防ぐ専用ファイアウォール |
| **EDR** | いーでぃーあーる | コンピューターへの不審な操作を検知・対応するセキュリティツール |
| **ゼロデイ脆弱性** | ぜろでいぜいじゃくせい | 修正パッチが存在しない、発見されたばかりの脆弱性 |
| **RBVM** | あーるびーぶいえむ | リスクベースで脆弱性を管理・優先順位付けするアプローチ |

> 💬 **まとめ**: セキュリティの世界では「点数が高い＝今すぐ対応」という単純な考え方は危険です。限られた人員と時間を最大限活かすために、「実際に攻撃者が使えるかどうか」を考えた賢い優先順位付けが重要です。これは家の防犯対策と同じで、「すべての窓に鍵をつける」より「泥棒が実際に狙いやすい場所から対策する」方が効果的なのです。
