# n8nのトークン交換の欠陥により、別の発行者のユーザーとしてログインできてしまう問題

**元記事**: [n8n Token Exchange Flaw Could Let Attackers Log In as Users From Another Issuer](https://inl03.netline.com/ltr6/?_m=3n.009a.4032.sp0ao46r89.336c)
**解説日**: 2025年7月17日

---

## 背景知識

まず、この記事を理解するために必要な基本的な概念を説明します。

### n8nとは？
**n8n（エヌエイトエヌ）** は、さまざまなサービスやアプリを自動でつなぐ「ワークフロー自動化ツール」です。たとえば「Gmailにメールが来たら、自動でSlackに通知を送る」といったことができるツールです。企業向けの「Enterpriseプラン」も持っています。

### JWTとは？
**JWT（JSON Web Token、ジェイダブリューティー）** は、デジタルの「入場チケット」のようなものです。ログインするとサーバーから発行され、「あなたは〇〇さんです」という情報が電子的に署名されて入っています。このチケットを見せるだけで、次回からパスワードなしでサービスを利用できます。

### 「発行者（Issuer）」と「サブジェクト（sub）」って何？
JWTには様々な情報が入っています。

| 項目 | 説明 | 例え |
|------|------|------|
| `iss`（Issuer＝発行者） | このチケットを作った機関 | チケットを発行した「A社」 |
| `sub`（Subject＝対象者） | このチケットの持ち主のID | 「社員番号1234」 |

たとえると、**A社が発行した「社員番号1234」のチケット**と、**B社が発行した「社員番号1234」のチケット**は、番号が同じでも全く別の人を指しています。

### トークン交換（Token Exchange）とは？
**OEM（他社製品に組み込む形式）パートナー企業**が、自分のユーザーをn8nにシームレスにログインさせる仕組みです。パートナー企業が作ったチケット（JWT）をn8nに見せると、n8n側のアカウントに自動的にログインできます。2回ログインしなくて済む便利な機能です。

## 何が起きたのか

### 一言で言うと
**「別々の会社が偶然同じIDを使っていたとき、片方の会社のチケットで、もう片方の会社のユーザーとしてログインできてしまう」** というバグが発見されました。

### 経緯
- セキュリティ研究者（GitHubアカウント名：bearsyankees）が発見
- AIを使った侵入テストツールを作る「Strix」という会社の研究者が報告
- **2025年6月24日**にn8nが修正版をリリース
- **2025年7月9日**に脆弱性情報が公開（CVE番号：CVE-2026-59208）

## 技術的な詳細

### バグの仕組みをわかりやすく説明

#### 正しい照合方法（あるべき姿）

```
チケットの確認 = 「発行者(iss)」 + 「社員番号(sub)」の両方で確認
例：「A社が発行した社員番号1234」→ Aさんのアカウントにログイン
　　「B社が発行した社員番号1234」→ Bさんのアカウントにログイン
```

#### n8nが実際にやっていたこと（バグのある状態）

```
チケットの確認 = 「社員番号(sub)」だけで確認！（発行者を無視）
例：「A社が発行した社員番号1234」→ 社員番号1234のアカウントにログイン
　　「B社が発行した社員番号1234」→ 同じく社員番号1234のアカウントにログイン ← 本来別人！
```

#### 具体的なシナリオ

1. 会社AのユーザーとしてID「user001」が存在する
2. 別の会社BでもたまたまID「user001」が使われている
3. 悪意のある攻撃者が会社Bの「user001」チケットを入手
4. **そのチケットで会社Aの「user001」アカウントにログインできてしまう！** 😱

> 🔑 **ポイント**: 会社Aのユーザーのパスワードがわからなくてもログインできてしまいます

### 参考規格（RFC 7519）が定めること

国際的な標準規格（RFC 7519）では、JWTの`sub`（社員番号）は **「同じ発行者の中でユニークであればよい」** と定めています。つまり、A社とB社が同じ番号を使っても規格違反ではないのです。だからこそ、**発行者と番号のセットで確認しなければならない**のに、n8nは番号だけを見ていました。

## なぜ重要なのか

### 影響を受ける条件

以下の**すべて**に当てはまる場合のみ影響があります：

- ✅ n8n Enterpriseプランを使っている
- ✅ トークン交換（Token Exchange）機能が有効になっている
- ✅ **2つ以上の外部発行者（Issuer）を信頼する設定**にしている

### 影響の規模

```
全n8nユーザー
    └─ Enterpriseユーザー（少数）
            └─ トークン交換を使っているユーザー（さらに少数）
                    └─ 複数の発行者を設定しているユーザー（さらに少数）← ここだけが対象
```

n8n自身も「影響範囲は小さく限定的」と述べています。また、この機能はまだ「プレビュー（試験提供中）」の段階です。

### 深刻度の評価

| 評価機関 | スコア | 評価 |
|---------|--------|------|
| GitHub（CVSS 4.0） | **7.6 / 10** | 🔴 高（High） |
| NVD（CVSS 3.1） | **6.8 / 10** | 🟡 中（Medium） |
| CISA（実際の悪用） | なし | ✅ 現時点で悪用の報告なし |

> 2025年7月16日時点で、**実際に攻撃に悪用されたという報告や、攻撃方法を示す公開情報はありません。**

## 対策・今後の展望

### 今すぐできる対策

#### 方法①【最優先】アップデートする
n8n **2.27.4以上** または **2.28.1以上** にアップデートしてください。

```
影響あるバージョン: 2.27.4 未満 & 2.28.0
安全なバージョン: 2.27.4以上、2.28.1以上
2025年7月16日時点の最新版: 2.30.6（latestおよびstableタグ）
```

#### 方法②【すぐにアップデートできない場合】設定を変更する

以下のどちらかを実施してください：

- `N8N_TOKEN_EXCHANGE_TRUSTED_KEYS` の設定で、**信頼する発行者を1つだけにする**
- または、**トークン交換機能を完全にオフにする**

> ⚠️ n8n公式は「これらは一時的な緩和策であり、完全な解決ではない」と述べています。最終的にはアップデートが必要です。

### 今後の展望

n8nは週1回程度の頻度で新バージョンをリリースしています。今後も積極的なアップデートが続く見込みです。The Hacker Newsがn8nに詳細を問い合わせており、続報が出る可能性があります。

> 💡 **まとめ**: n8nという自動化ツールで、「ログインチケットを確認するとき、チケットの番号（sub）だけ見て、誰が発行したか（iss）を無視していた」という見落としがありました。影響範囲は限定的で、現時点で実際の攻撃は確認されていませんが、該当するn8n Enterpriseユーザーは早急なアップデートが必要です。
