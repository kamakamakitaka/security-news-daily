# WordPressの重大な欠陥「wp2shell」：ログイン不要でサーバーを乗っ取れる脆弱性が発見された

**元記事**: [New wp2shell WordPress Core Flaw Lets Unauthenticated Attackers Run Code](https://inl03.netline.com/ltr6/?_m=3n.009a.4033.sp0ao46r89.336k)
**解説日**: 2026年7月18日

---

## 背景知識

まず、このニュースを理解するための基礎知識を整理しましょう。

### WordPressって何？

**WordPress（ワードプレス）** は、世界中のウェブサイトを作るために使われる、最も人気のある「ウェブサイト作成ツール」です。ブログ、企業サイト、ネットショップなど、**世界中のウェブサイトの約40〜43%がWordPressで動いている**と言われています。記事によれば5億以上のサイトが使っているとのことです。

> 🏠 **例え話**: WordPressは「家を建てるための定番の設計図と道具セット」のようなものです。多くの人が同じ設計図を使っているからこそ、1つの欠陥が膨大な数の家に同時に影響してしまいます。

### 脆弱性（ぜいじゃくせい）って何？

ソフトウェアの「バグ（プログラムの誤り）」や「設計ミス」によって、攻撃者に悪用される穴のことです。今回はWordPress本体（コア）に2つの脆弱性が見つかりました。

### 知っておくべき基礎用語（詳細は後述の用語解説も参照）

| 用語 | 簡単な説明 |
|------|-----------|
| SQLインジェクション | データベースに不正な命令を送り込む攻撃 |
| RCE（リモートコード実行） | 遠隔からサーバー上で好き勝手なプログラムを動かす攻撃 |
| REST API | ウェブサービス同士が通信するための仕組み |
| CVE | 脆弱性に付けられる世界共通の識別番号 |

## 何が起きたのか

### 事件の概要

2026年7月、WordPressの本体（コア）に**2つの重大な脆弱性**が発見・公開されました。この2つを組み合わせると、**ログイン不要・プラグインなし**の状態でも、攻撃者がサーバー上で自由にプログラムを実行できてしまいます。

この脆弱性セットは **「wp2shell（ダブルピーツーシェル）」** と名付けられました。

### 2つの脆弱性の識別番号

- **CVE-2026-60137**：SQLインジェクション（データベースへの不正命令）
- **CVE-2026-63030**：REST APIのバッチルート混乱（通信経路の取り違え）

> ⚠️ **重要ポイント**: どちらか1つだけでは大きな被害にならないのですが、**2つを組み合わせる（チェーンする）** ことで、「ログインなしでサーバーを乗っ取れる」という最悪の事態になります。

### 発見者と公開の経緯

- **バッチルート混乱**：セキュリティ企業「Assetnote（アセットノート）」のAdam Kues氏が発見し、WordPressのバグ報告プログラム（HackerOne）を通じて報告
- **SQLインジェクション**：TF1T、dtro、haongoという別の研究者たちが別々に報告
- 2026年7月某日（金曜日）、WordPressは修正版をリリースし、同時に自動更新を強制実施
- その後、GitHubに**実際に攻撃できる実証コード（PoC）が公開**されてしまった

## 技術的な詳細

### 攻撃の仕組み（2段階の罠）

> 🔑 **例え話で全体像を掴もう**: マンションのセキュリティシステムに例えます。
> - **1段階目（バッチルート混乱）**: 受付の警備員が「こちらはAさんの対応です」と言いながら、実は「Bさんの権限」で動いてしまう取り違えミスが発生する
> - **2段階目（SQLインジェクション）**: その取り違えた権限を使って、マンションの管理システム（データベース）に不正命令を送り込む

#### ステップ1：バッチエンドポイントの「ズレ」を悪用

WordPressには `/wp-json/batch/v1` という機能があります。これは「複数の通信リクエストをまとめて1回で処理できる便利な機能」で、2020年のWordPress 5.6から搭載されています。

この機能は内部で「2つの並列リスト（配列）」を使ってリクエストを管理しています。ところが、**1つのリクエストでエラーが起きると、2つのリストの数が1つズレてしまう**という設計ミスがありました。

```
通常時:
リストA: [リクエスト1, リクエスト2, リクエスト3]
リストB: [処理者1,   処理者2,   処理者3  ]
→ リクエスト1は処理者1が担当 ✅

エラー発生後:
リストA: [リクエスト1, リクエスト2]
リストB: [処理者1,   処理者2,   処理者3]
→ リクエスト2が処理者3の権限で動いてしまう ❌
```

このズレを利用すると、**本来は認証（ログイン）が必要なはずの処理を、ログインなしで実行**できてしまいます。

#### ステップ2：SQLインジェクションで命令を注入

WordPressのデータベース検索機能（`WP_Query`）の `author__not_in` というパラメータに問題がありました。

- 本来は「配列（リスト）」を受け取ることを想定した設計
- ところが「文字列（テキスト）」を渡すと、検査をすり抜けてしまう
- そのまま生の値がデータベースへの命令文に組み込まれてしまう

> 📝 **例え話**: 「受付で名前を書くフォームに、名前の代わりに『このフォームを提出した人に管理者権限を付与』と書いたら、そのまま実行されてしまった」ようなイメージです。

#### 2つを組み合わせると…

```
攻撃者（ログインなし）
    ↓ バッチエンドポイントに細工したリクエストを送信
    ↓ 「ズレ」によって認証チェックをバイパス（迂回）
    ↓ 不正な値がSQLインジェクションの脆弱部分に到達
    ↓ データベースに不正命令が実行される
    ↓ 🚨 サーバー上で任意のコードが実行される！
```

### 影響を受けるバージョン

| バージョン | 影響 | 修正版 |
|-----------|------|--------|
| 6.8.0〜6.8.5 | SQLインジェクションのみ（RCEなし） | **6.8.6** |
| 6.9.0〜6.9.4 | 完全なRCEチェーン（最も危険） | **6.9.5** |
| 7.0.0〜7.0.1 | 完全なRCEチェーン（最も危険） | **7.0.2** |
| 7.1 ベータ2 | 両方の修正が含まれる | — |

> 💡 **ポイント**: 「バッチルート混乱」はWordPress 6.9から登場した新機能に起因するため、**6.8はSQLインジェクションはあっても、サーバー乗っ取りには至らない**という状況です。

### 1つの「制限」：オブジェクトキャッシュが有効だと使えない

記事の最後に触れられていますが、**「パーシステントオブジェクトキャッシュ」という機能が有効になっているサイトでは、このRCE攻撃は機能しない**という条件があります。

大規模なサイトはキャッシュシステムを使っていることが多いため、全500億サイトが等しく危険というわけではありません。ただし、多くの小規模サイトやデフォルト設定のサイトではキャッシュが無効なので注意が必要です。

## なぜ重要なのか

### 規模感が圧倒的

- 世界5億以上のウェブサイトがWordPressを使用
- ただしRCEが可能なのはWordPress 6.9以降（2025年12月2日リリース）のサイトのみ
- それでも、**8ヶ月以内にリリースされた最新版を使っているサイト**が対象なので、アップデート意識の高いサイト運営者ほど危険にさらされていたという皮肉な状況

### 「ゼロ前提条件」の恐ろしさ

通常、重大な攻撃には何らかの「前提条件」が必要です（ログインが必要、特定のプラグインが必要など）。しかし今回は：

- ✅ ログイン不要
- ✅ プラグイン不要（WordPress本体のみ）
- ✅ 特別な設定不要

**何もしていない普通のWordPressサイトが攻撃対象**になり得ます。

### CVEのスコアが混乱を招いている

面白い（そして注意が必要な）点として、**スコアと危険度のギャップ**があります：

| 脆弱性 | 実際の危険度 | CVSSスコア |
|--------|------------|-----------|
| CVE-2026-63030（バッチ混乱） | 攻撃の「カギ」 | **7.5（High）** |
| CVE-2026-60137（SQLi） | 単体では限定的 | **9.1以上（Critical）** |

みんなが「危険！」と言っているRCEチェーンの「カギ」の方が、スコアでは低く出ています。これはスコアの計算方法の問題で、**数字だけ見ると本当の危険度を見誤る可能性があります**。

## 対策・今後の展望

### 今すぐやること

#### 1. WordPressのバージョンを確認・更新する 🔴最重要

WordPress管理画面にログインして、バージョンを確認してください。

```
管理画面 → ダッシュボード → 更新
```

- **6.8系を使っている人** → 6.8.6に更新
- **6.9系を使っている人** → 6.9.5に更新
- **7.0系を使っている人** → 7.0.2に更新

#### 2. 自動更新の設定を確認する

WordPressは今回「強制自動更新」を実施しましたが、**自動更新をオフにしていたサイトには届いていない可能性**があります。必ず手動で確認しましょう。

#### 3. wp2shell.comのチェッカーを使う

発見者のSearchlight Cyber社が `wp2shell.com` に診断ツールを公開しています。自分のサイトが影響を受けているか確認できます。

#### 4. WAFルールの確認（技術者向け）

CloudflareなどのWAF（ウェブアプリケーションファイアウォール）を使っている場合、対応するルールが既に配信されているので、有効になっているか確認しましょう。

### 今後の展望

- GitHubに実際に動く攻撃コード（PoC）が公開されてしまったため、**スクリプトキディ（技術力の低い攻撃者）でも攻撃できる状況**になっています
- WordPressコミュニティは被害状況の調査を継続中
- 今後、被害を受けたサイト数の報告が出てくると予想されます

## 過去記事との関連

今回は単独記事としての解説となりますが、この脆弱性は過去のWordPress関連の脆弱性とは一線を画します。従来のWordPress攻撃の多くは「プラグインやテーマの欠陥」を突くものでしたが、今回は**WordPress本体（コア）に存在する欠陥**である点が特に重大です。過去にプラグイン関連の脆弱性を学んだことがある方は、「本体が安全でもプラグインは危ない」と覚えていたかもしれませんが、今回はその逆の教訓として記憶しておきましょう。

## 用語解説

| 用語 | 解説 |
|------|------|
| **WordPress コア** | プラグインやテーマを除いた、WordPressの本体プログラム |
| **脆弱性（ぜいじゃくせい）** | ソフトウェアのバグや設計ミスによる、攻撃者に悪用される弱点 |
| **CVE（Common Vulnerabilities and Exposures）** | 脆弱性に付けられる世界共通の識別番号（例：CVE-2026-63030） |
| **CVSSスコア** | 脆弱性の危険度を0〜10で数値化したもの。7以上がHigh、9以上がCritical |
| **SQLインジェクション** | データベースへの問い合わせ文に不正な命令を混ぜ込む攻撃手法 |
| **RCE（Remote Code Execution）** | 遠隔からサーバー上で任意のプログラムを実行できる攻撃。最も危険な部類 |
| **REST API** | ウェブサービス同士が通信するための標準的な仕組み。WordPressも採用 |
| **バッチエンドポイント** | 複数の通信リクエストを1回にまとめて処理する機能 |
| **認証バイパス** | ログインなどの本人確認をすり抜けること |
| **PoC（Proof of Concept）** | 脆弱性が実際に悪用できることを示す実証コード。公開されると攻撃者も使える |
| **パーシステントオブジェクトキャッシュ** | サイトのデータを一時保存して高速化する仕組み。有効だと今回の攻撃が効かない |
| **WAF（Web Application Firewall）** | ウェブアプリへの不正アクセスを検知・遮断するセキュリティシステム |
| **HackerOne** | セキュリティ研究者がソフトウェアの脆弱性を開発者に報告するための公式プラットフォーム |
| **チェーン攻撃** | 複数の脆弱性を組み合わせて、それぞれ単独より大きな被害を生み出す攻撃手法 |
| **スクリプトキディ** | 自分でコードを書けないが、他人が作った攻撃ツールを使う初心者の攻撃者 |

---

> 📌 **まとめ**: WordPressの本体に「2つの脆弱性を組み合わせると、ログインなしでサーバーを乗っ取れる」という重大な欠陥が見つかりました。修正版は既にリリースされているので、**WordPressを使っているサイト運営者は今すぐバージョンを確認・更新することが最優先**です。「自動更新をオフにしていた」「まだ確認していない」という方は、特に急いで対応してください。
