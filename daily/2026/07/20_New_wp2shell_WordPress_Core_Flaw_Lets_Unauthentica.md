# WordPressの核心部分に重大な欠陥！ログインなしでサイトを乗っ取れる「wp2shell」脆弱性

**元記事**: [New wp2shell WordPress Core Flaw Lets Unauthenticated Attackers Run Code](https://inl03.netline.com/ltr6/?_m=3n.009a.4034.sp0ao46r89.3394)
**解説日**: 2026年7月21日

---

## 背景知識

まず、このニュースを理解するために必要な基礎知識を整理しましょう。

### WordPress（ワードプレス）とは？
ウェブサイトやブログを簡単に作れるソフトウェアです。世界中のウェブサイトの約40〜45%がWordPressで動いていると言われており、個人ブログから大企業のサイトまで幅広く使われています。「プラグイン」と呼ばれる追加機能を組み込んで機能を拡張できます。

### 「コア（Core）」って何？
WordPressの「コア」とは、プラグインや追加テーマを一切入れていない、素の状態のWordPress本体のことです。今回の問題は **このコア部分にある** ため、「プラグインを使っていないから安全」という言い訳が一切通用しません。

### 重要な専門用語（先に整理）

| 用語 | 一言で言うと |
|------|-------------|
| **脆弱性（ぜいじゃくせい）** | ソフトウェアの「穴」。攻撃者に悪用される可能性がある欠陥 |
| **RCE（Remote Code Execution）** | 遠隔からコードを実行すること。ネット越しに相手のサーバーを操作できる最も危険な攻撃のひとつ |
| **SQLインジェクション** | データベースに不正な命令を送り込む攻撃手法 |
| **認証なし（Unauthenticated）** | ログインやアカウントなしに攻撃できること |
| **CVE（Common Vulnerabilities and Exposures）** | 脆弱性に付けられる世界共通の識別番号（例：CVE-2026-63030） |
| **REST API** | ウェブサービス同士がデータをやり取りするための仕組み |
| **PoC（Proof of Concept）** | 脆弱性が実際に悪用できることを示す「実証コード」 |
| **自動アップデート（Auto-update）** | WordPressが自動的にバージョンを更新する仕組み |

## 何が起きたのか

### 事件の概要

2026年7月、WordPressの本体（コア）に **ログイン不要でサイトを乗っ取れる** 重大な脆弱性が発見・公開されました。この脆弱性は **「wp2shell」** という名前で呼ばれています。

**ポイントをひとことで言うと：**
> 🔴 **誰でも・何の準備もなく・WordPressサイトに侵入してコードを実行できる**

発見者はセキュリティ企業「Assetnote（アセットノート）」のAdam Kues氏で、WordPressの脆弱性報告プログラム（HackerOne）を通じて報告しました。

### タイムライン

```
2025年12月2日  ── WordPress 6.9 リリース（この時点でバグが混入）
      ↓
2026年7月某日  ── 脆弱性が発見・報告される
      ↓
2026年7月某金曜日 ── WordPress 6.9.5 / 7.0.2 として修正版リリース
                   ── 強制自動アップデートが発動
      ↓
2026年7月18日  ── CVE番号が正式付与、PoC（実証コード）がGitHubで公開
      ↓
現在           ── 攻撃者がPoCを使って攻撃可能な状態
```

## 技術的な詳細

### 「2つのバグを組み合わせた攻撃」という点が最大の特徴

wp2shellは **1つの欠陥ではなく、2つの欠陥を組み合わせた攻撃** です。2つを組み合わせることで初めて「ログインなしでコード実行」が可能になります。

```
【バグ①】CVE-2026-60137：SQLインジェクション
    ＋
【バグ②】CVE-2026-63030：REST APIバッチルートの混乱
    ↓
組み合わせると → 「ログインなしでのコード実行（RCE）」が成立！
```

### バグ①：SQLインジェクション（CVE-2026-60137）

> 🗄️ **例え話：図書館の司書に間違った指示を送る**

WordPressは記事や投稿者のデータを検索するとき、データベースに「命令文（SQLクエリ）」を送ります。

問題のある箇所は `WP_Query` という機能の `author__not_in`（この投稿者を除外する）というパラメータです。

本来はこのパラメータに「リスト形式（配列）」のデータを渡すべきところ、**文字列（テキスト）を渡してもチェックをスルーしてしまう**という欠陥がありました。

```
正常な使い方:  author__not_in = [1, 2, 3]  ← リスト形式 → チェックあり✅
攻撃的な使い方: author__not_in = "1 OR 1=1" ← 文字列   → チェックなし❌
                                                ↓
                                         不正なSQL命令がそのままデータベースへ！
```

このバグは **WordPress 6.8 以降** に存在します。

### バグ②：バッチエンドポイントの混乱（CVE-2026-63030）

> 📦 **例え話：宅配便の仕分けミス**

WordPressには `/wp-json/batch/v1` という「まとめてリクエストを処理する窓口（バッチエンドポイント）」があります（WordPress 5.6、2020年から存在）。

この窓口は複数のリクエストを一度に処理するため、内部で「2つの並列リスト（配列）」を使って処理を管理しています。

ここに問題が：
```
リクエストA → エラーが起きると...
               2つのリストが「1つずれる」バグが発生（6.9で新たに混入）
                    ↓
リクエストBが、リクエストAとして処理される
                    ↓
本来ログインが必要なリクエストが、別の（ログイン不要な）リクエストとして通過！
```

宅配便で言えば「あなた宛の荷物が、隣の家の名前で届いてしまった」ような状態です。

### 2つを組み合わせると…

```
攻撃者（ログインなし）
    ↓
バッチエンドポイントに細工したリクエストを送る（バグ②を利用）
    ↓
本来はアクセスできないはずの内部処理に潜り込む
    ↓
SQLインジェクションを発動（バグ①を利用）
    ↓
データベースを操作 → サーバー上でコードを実行（RCE完成！）
    ↓
🔴 サイトの完全乗っ取りへ
```

### 攻撃が成立しない条件（少し良いニュース）

記事によると、**「永続的なオブジェクトキャッシュ」を使っているサイトではコード実行の経路が機能しない** とのことです（Cloudflareが報告）。

> 💡 オブジェクトキャッシュとは：処理結果を一時保存して高速化する仕組み。RedisやMemcachedなどが該当します。

ただし、これは「完全に安全」を意味するものではなく、SQLインジェクション自体は依然として残っています。

## なぜ重要なのか

### 影響範囲が膨大

```
WordPressサイト全体：約5億サイト（推定）
            ↓
そのうちRCEが可能なバージョン（6.9〜7.0系）は
2025年12月以降にアップデートしたサイト = かなりの数
```

バージョン別の状況をまとめると：

| バージョン | リスク | 修正版 |
|-----------|--------|--------|
| 6.8.0〜6.8.5 | SQLインジェクションのみ（RCEなし） | **6.8.6** |
| 6.9.0〜6.9.4 | **RCE（完全乗っ取り）可能** | **6.9.5** |
| 7.0.0〜7.0.1 | **RCE（完全乗っ取り）可能** | **7.0.2** |
| 7.1 beta2 | 両方の修正を含む | ✅ |

### PoCが公開されてしまっている

**最も危険な状況のひとつ** は、実際に攻撃できる「実証コード（PoC）」がGitHubで公開されてしまっていることです。

これは「理論上危険」ではなく「今すぐ誰でも攻撃できる」ことを意味します。技術知識の低い攻撃者でも、コードをコピーするだけで攻撃が実行できる状態です。

### CVEスコアのちぐはぐ問題

記事で面白い指摘があります：

```
WordPress公式の評価：「クリティカル（最重大）」
CVEの数値スコア：7.5（High＝高、だがクリティカルではない）

→ なぜ？
  スコアリングの仕組みが、
  「データアクセスのみの影響」として計算しているため
  （コード実行による被害が正しく反映されていない）
```

つまり、**CVEの数字だけ見ていると危険性を過小評価する可能性がある**という教訓があります。数字のラベルだけを信じず、両方のCVE（CVE-2026-63030とCVE-2026-60137）を確認することが重要です。

## 対策・今後の展望

### ✅ 今すぐやるべきこと

#### 1. バージョンを確認する
WordPressの管理画面（ダッシュボード）にログインして、現在のバージョンを確認しましょう。

```
管理画面 → ダッシュボード → 「更新」メニューを確認
```

#### 2. 修正バージョンにアップデートする

| 使用中のバージョン | 更新先 |
|------------------|--------|
| 6.8系 | **6.8.6** |
| 6.9系 | **6.9.5** |
| 7.0系 | **7.0.2** |

#### 3. 自動アップデートを信用しすぎない
WordPressは今回「強制自動アップデート」を発動しましたが、**自動アップデートをオフにしているサイトには届かない可能性があります**。必ず手動でも確認してください。

#### 4. WAF（ウェブアプリケーションファイアウォール）を活用する
CloudflareはすでにWAFルール（攻撃をブロックするフィルター）を適用しています。CloudflareなどのCDN・WAFサービスを使っている場合は、最新のルールが適用されているか確認しましょう。

#### 5. ログを確認する
もしアップデートが遅れていた場合、サーバーのアクセスログを確認して不審なアクセスがなかったかチェックすることをお勧めします。

### 今後の展望

- PoCが公開されたことで、攻撃の増加が予想されます
- セキュリティ企業Searchlightは独自の詳細な技術解説を控えていましたが、パッチが公開された今、詳細情報がどんどん出てくると思われます
- `wp2shell.com` に診断チェッカーが用意されているので、自分のサイトが影響を受けているか確認できます

## 過去記事との関連

以前、**7-ZipのXZアーカイブ展開時のコード実行脆弱性**、**NGINXのクラッシュ・RCE脆弱性**、**SonicWallのゼロデイ攻撃**について解説しました。

今回のWordPress脆弱性も、これらと共通するパターンがあります：

> 🔗 **共通のテーマ：「広く使われているソフトウェアの核心部分を狙う攻撃」**

- 7-Zip → 世界中で使われるファイル解凍ソフトのコア処理
- NGINX → 世界中のウェブサーバーを支えるソフトウェア
- SonicWall → 企業のVPN機器（ゼロデイ＝パッチ前から攻撃）
- **今回のWordPress → 世界5億サイトを支えるCMSのコア部分**

特に今回は「**2つの欠陥を組み合わせて初めて成立する攻撃**」という点が技術的に興味深く、SonicWallのゼロデイと同様に「発見から悪用可能なコードの公開まで」が非常に速いという点でも、最近のセキュリティ事件の傾向を示しています。

## 用語解説

| 用語 | 解説 |
|------|------|
| **WordPress（ワードプレス）** | 世界で最も普及しているCMS（ウェブサイト管理ソフト）。世界の約40%超のサイトで使用されている |
| **コア（Core）** | ソフトウェアの本体部分。プラグインなどの追加機能を除いた基本部分 |
| **RCE（Remote Code Execution）** | 遠隔からコードを実行する攻撃。サーバーを外部から操作できる最も深刻な攻撃の一つ |
| **SQLインジェクション** | データベースへの問い合わせ文に不正な命令を混ぜ込む攻撃。データの盗取・改ざん・削除が可能になる |
| **REST API（レスト エーピーアイ）** | ウェブサービス間でデータをやり取りする仕組み。「/wp-json/」で始まるURLがWordPressのREST API |
| **バッチエンドポイント** | 複数のリクエストをまとめて一度に処理する「窓口」 |
| **CVE（シーブイイー）** | 脆弱性に付けられる世界共通の識別番号（例：CVE-2026-63030）。「CVE-年号-番号」の形式 |
| **PoC（ピーオーシー、Proof of Concept）** | 脆弱性が実際に悪用できることを示すサンプルコード。公開されると誰でも攻撃を試みられる |
| **認証なし（Unauthenticated）** | ログインやアカウント登録なしに攻撃できる状態。最も危険な条件の一つ |
| **WAF（ワフ、Web Application Firewall）** | ウェブアプリケーションへの攻撃をブロックするセキュリティツール |
| **永続的オブジェクトキャッシュ** | データベースへの問い合わせ結果を一時保存して高速化する仕組み（Redis、Memcachedなど）。今回の攻撃の一部を無効化する効果がある |
| **HackerOne（ハッカーワン）** | 企業が設置する「脆弱性報告の窓口」を提供するプラットフォーム。正直に報告した研究者に報奨金が支払われることもある |
| **強制自動アップデート** | ユーザーの操作なしに自動的にソフトウェアを更新する仕組み。WordPressはセキュリティパッチに限り強制適用することがある |
