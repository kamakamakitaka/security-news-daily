# 会社で最も監視されているデバイスが、まだ危険なアクセスを隠している

**元記事**: [The Most Monitored Device in the Company is Still Hiding Dangerous Access](https://inl03.netline.com/ltr6/?_m=3n.009a.4034.sp0ao46r89.338s)
**解説日**: 2025年7月10日

---

## 背景知識

この記事を理解するために、まずいくつかの基本的な概念を押さえておきましょう。

### 🔑 「クレデンシャル（認証情報）」って何？
コンピューターの世界で「クレデンシャル」とは、**「あなたが本人であることを証明するための情報」**のことです。身近な例で言えば、

- **パスワード** → SNSにログインするときのパスワード
- **APIキー** → アプリがサービスに「私は正規の利用者です」と証明するための特別な文字列（鍵のようなもの）
- **トークン** → 「一度ログインしたよ」という証明書代わりの文字列

これらが漏れると、**合鍵を盗まれたのと同じ状態**になります。

### 💻 「開発者ラップトップ（開発者のノートPC）」が狙われる理由
プログラマーやエンジニア（開発者）が使うPCには、仕事上の都合で大量のクレデンシャルが保存されています。クラウドサービス、プログラムの部品倉庫（パッケージマネージャー）、コードの保管庫（GitHubなど）…それぞれに接続するための「鍵」が必要なのです。

### 🤖 「AIコーディングエージェント」って？
最近普及している、プログラムを自動で書いてくれるAIツールのことです（GitHub CopilotやCursorなどが代表例）。便利な反面、AIが自動で設定ファイルを読み書きするため、**鍵が思わぬ場所に保存されてしまう**ことがあります。

## 何が起きたのか

### 📰 一言で言うと
> **「開発者のPCは厳しく監視されているはずなのに、大量の"使える鍵（クレデンシャル）"が見落とされたまま放置されており、攻撃者に悪用されている」**

という警告レポートです。

### 具体的に起きていること

1. **クレデンシャルが開発者PCに溜まり続けている**
   開発者はスピード重視で作業するため、クラウドや各種サービスへの接続情報がPCのあちこちに保存されます。「あとで消そう」と思っても、忘れられることがほとんどです。

2. **AIツールの普及でさらに深刻化**
   AIコーディングエージェントが設定ファイルを自動操作することで、クレデンシャルが落ちる場所が爆発的に増えました。セキュリティ企業GitGuardianの調査では、**2025年だけで24,008個もの固有のクレデンシャルが公開設定ファイルの中に発見**されました。

3. **古い鍵が何年も有効なまま残る**
   驚くべきことに、**2022年に漏洩したクレデンシャルの64%が、2026年時点でもまだ使える状態**だったと報告されています。一度作った鍵は、誰かが意識して無効化しない限り、ずっと有効なのです。

## 技術的な詳細

### 🚪 「不正侵入」より「正規ログイン」の方が簡単

攻撃者の視点で考えてみましょう。

```
【従来の攻撃イメージ】
攻撃者 → 脆弱性を探す → システムに穴を開ける → 侵入

【クレデンシャル悪用の攻撃イメージ】
攻撃者 → 開発者PCから鍵を盗む → 普通にログイン → 「正規ユーザー」として活動
```

鍵さえあれば、**壁をよじ登る必要はなく、正面玄関から堂々と入れる**のです。しかもシステム側から見ると「正規のログイン」に見えるため、検知が非常に難しくなります。

### 🛠️ 開発者PCにクレデンシャルが溜まる仕組み

開発者は日常的に以下のようなツールを使います：

| ツールの種類 | 具体例 | 必要な鍵 |
|---|---|---|
| クラウドCLI | AWS CLI、Google Cloud SDK | クラウドの接続キー |
| コンテナツール | Docker | レジストリのトークン |
| コード管理 | Git、GitHub CLI | SSHキー、アクセストークン |
| パッケージ管理 | npm、pip | 公開用のAPIキー |

これらがそれぞれ設定ファイルやキャッシュに保存されるため、**一台のPCに何十種類もの鍵が散在する**状態になります。まるで引き出しのあちこちに合鍵を置いているようなものです。

### 🦠 実際に起きた攻撃事例

記事では3つの実際の攻撃が紹介されています：

#### ① Shai-Hulud（シャイ＝フルード）攻撃
- **手口**: npm（JavaScriptのパッケージ管理サービス）に悪意のあるパッケージを混入
- **被害**: インストールしたPCから各種クレデンシャルを自動収集
- **その後**: 盗んだトークンを使って、さらに感染を広げた

#### ② Nx "s1ngularity"（エヌエックス・シンギュラリティ）攻撃
- **手口**: 人気のJavaScriptツール「Nx」に悪意のあるコードを混入
- **被害**: GitHubトークン、npmキー、SSHの秘密鍵、暗号資産ウォレットまで盗まれた
- **その後**: 盗んだアクセスで多数のリポジトリ（コード保管庫）を公開・漏洩

#### ③ GhostAction（ゴーストアクション）攻撃
- **手口**: GitHub Actions（自動テスト・デプロイのシステム）に悪意のある処理を組み込む
- **被害**: PyPI・npm・DockerHub・AWSのクレデンシャルをCI環境から盗み出した

**3つの攻撃に共通するパターン**：
```
①ソフトウェアのサプライチェーンに侵入
　↓
②開発者が普通に使うツールを汚染
　↓
③開発者が使うだけでクレデンシャルが盗まれる
　↓
④盗んだ鍵でさらに被害を拡大
```

### 🔍 「監視されているのになぜ見つからない？」

開発者のPCには通常、以下のセキュリティツールが入っています：

- **EDR（エンドポイント検知・対応）**: マルウェアや不審な動作を監視するツール
- **MDM（モバイルデバイス管理）**: PCの設定やポリシーが守られているか確認するツール

しかし、これらは**「危険なプログラムが動いていないか」を見るツール**です。

> **「設定ファイルの中に書いてある文字列（クレデンシャル）が危険かどうか」は、基本的にスルーしてしまう**

のです。完全に武装したお城でも、合鍵が城の中に転がっていたら意味がないのと同じです。

## なぜ重要なのか

### 📊 被害の規模感

- GitGuardianの調査で、**公開MCPの設定ファイルだけで24,008個のクレデンシャル**が見つかった（2025年）
- AIを使ったコードからのクレデンシャル漏洩率は、**GitHubの平均の約2倍**
- 2022年に漏洩した鍵の**64%が4年後もまだ有効**

### 🌐 影響が広がりやすい理由

開発者のPCは会社の中でも特別な存在です。開発者は：
- 本番環境（実際に動いているシステム）への接続権限を持つ
- クラウドサービスの管理者権限を持つことが多い
- 他の社員より多くのシステムにアクセスできる

つまり、**開発者PCのクレデンシャルが1つ漏れるだけで、会社全体のシステムが危険にさらされる可能性がある**のです。

### 🎯 「ソフトウェアサプライチェーン攻撃」の怖さ

自分が直接悪いサイトを踏まなくても、**普段使っている信頼できるツール自体が汚染されている**ため、気づかないうちに被害者になります。普通にnpmパッケージをインストールするだけで被害に遭う可能性があるのです。

## 対策・今後の展望

### ✅ 個人・開発者レベルでできること

1. **クレデンシャルを設定ファイルに直書きしない**
   - ❌ `config.yaml`に `api_key: "abcd1234"` と書く
   - ✅ 環境変数や専用の「シークレット管理ツール」を使う

2. **使わなくなったAPIキーはすぐに無効化（ローテーション）する**
   - 鍵を「作りっぱなし」にしない

3. **GitHubにコードをプッシュする前にクレデンシャルが含まれていないか確認する**
   - `git-secrets`や`gitleaks`などのツールが役立ちます

4. **AIコーディングツールが生成したコードのクレデンシャルを点検する**
   - AIは便利ですが、セキュリティ的に問題のあるコードを生成することがあります

### ✅ 会社・組織レベルでできること

1. **クレデンシャルスキャンツールの導入**
   - EDR・MDMだけでなく、ファイルの中身を検査して「鍵らしき文字列」を検出するツールを追加する

2. **シークレット管理の仕組みを整える**
   - HashiCorp VaultやAWS Secrets Managerなど、クレデンシャルを安全に一元管理するサービスを使う

3. **最小権限の原則を徹底する**
   - 「必要最低限の権限しか持たないキーを発行する」ことで、仮に漏洩しても被害を限定できる

4. **定期的なクレデンシャルの棚卸しと無効化**
   - 「どこにどんな鍵があるか」を定期的に確認し、不要なものを削除・無効化する

### 🔮 今後の展望

- AIエージェントの普及でこの問題はさらに深刻化する見込み
- クレデンシャル専用の検知・管理ツール市場が急成長中
- ソフトウェアサプライチェーンのセキュリティ対策が業界全体の課題に

## 用語解説

| 用語 | 読み方 | 意味 |
|---|---|---|
| **クレデンシャル** | くれでんしゃる | パスワード・APIキー・トークンなど、本人確認に使う情報の総称 |
| **APIキー** | えーぴーあい きー | アプリがサービスに接続する際の「合鍵」となる文字列 |
| **トークン** | とーくん | 「認証済み」を示す一時的または半永久的な証明書の文字列 |
| **EDR** | いーでぃーあーる | Endpoint Detection and Response。PCの不審な動作を検知するセキュリティツール |
| **MDM** | えむでぃーえむ | Mobile Device Management。会社のPCやスマホを一元管理するシステム |
| **MCP** | えむしーぴー | Model Context Protocol。AIエージェントがツールと連携するための仕組み |
| **npm** | えぬぴーえむ | JavaScriptのプログラム部品（パッケージ）を管理・共有するサービス |
| **CI/CD** | しーあい/しーでぃー | コードの自動テスト・自動デプロイの仕組み（GitHub Actionsなど） |
| **サプライチェーン攻撃** | さぷらいちぇーん こうげき | 目標のシステムを直接攻撃せず、そこが使うツールや部品を汚染して間接的に侵入する攻撃手法 |
| **シークレット** | しーくれっと | セキュリティ文脈では、APIキーや秘密鍵など「秘密にすべき情報」のこと |
| **ローテーション** | ろーてーしょん | クレデンシャルを定期的に新しいものに更新して、古いものを無効化すること |
| **最小権限の原則** | さいしょうけんげん のげんそく | 「必要最低限の権限だけを与える」セキュリティの基本原則 |

> 💡 **まとめ**: 「鍵（クレデンシャル）が落ちているのに、鍵専用の探知機がない」というのが今回の核心です。どんなに高性能なセキュリティカメラ（EDR）があっても、机の引き出しに合鍵が散乱していれば意味がありません。AIの普及でこの問題はさらに加速しており、「クレデンシャルの管理」が現代セキュリティの最重要課題の一つになっています。
