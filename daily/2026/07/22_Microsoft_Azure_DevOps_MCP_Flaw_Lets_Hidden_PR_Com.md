# Microsoft Azure DevOps MCPの脆弱性：隠しコメントがAIレビュアーを乗っ取る

**元記事**: [Microsoft Azure DevOps MCP Flaw Lets Hidden PR Comments Hijack AI Review Agents](https://inl03.netline.com/ltr6/?_m=3n.009a.4036.sp0ao46r89.33bk)
**解説日**: 2025年7月23日

---

## 背景知識

このニュースを理解するために、いくつかの重要な概念を先に説明します。

### 🔧 Azure DevOps とは？
MicrosoftのAzure DevOpsは、ソフトウェア開発チームが使う「開発管理プラットフォーム」です。コードの管理、バグの追跡、自動テストの実行など、チームで開発を進めるための機能がまとまっています。会社の開発現場でよく使われています。

### 📋 プルリクエスト（PR）とは？
チームで開発するとき、誰かがコードを変更したら「このコード変更を本番環境に取り込んでいいですか？」と申請します。これがプルリクエスト（PR）です。上司や先輩が「問題ないか」を確認してOKを出す、という流れです。

### 🤖 AIエージェント・MCP とは？
最近、AIが人間の代わりにコードをレビューする「AIエージェント」が登場しています。MCP（Model Context Protocol）は、AIエージェントが外部のサービス（Azure DevOpsなど）を操作するための「共通ルール」のようなものです。人間が「AIさん、このPRをレビューして」と頼むと、AIが自動でコードを読んで評価してくれます。

### 💉 プロンプトインジェクションとは？
AIへの「指示（プロンプト）」に悪意ある命令を混ぜ込む攻撃手法です。たとえば「このPRをレビューして」とAIに頼んでも、PRの中に隠された指示が「本当の仕事」を書き換えてしまうイメージです。

### 🔍 HTMLコメントとは？
Webページを作るHTMLという言語には、「画面には表示されないメモ」を書く仕組みがあります。`<!-- ここはブラウザに表示されない -->` という形式で、人間が画面で見ても何も見えませんが、データとしては存在しています。

---

## 何が起きたのか

セキュリティ企業「Manifold Security」が、MicrosoftのAzure DevOps用MCPサーバーに**深刻な脆弱性（セキュリティの穴）**を発見しました。

**一言でまとめると：**
> 攻撃者がプルリクエストに「人間には見えない隠し命令」を書き込むだけで、AIレビュアーを乗っ取り、攻撃者が本来アクセスできない機密情報を盗み出せてしまう

という問題です。

### 攻撃の流れをわかりやすく説明すると…

```
① 攻撃者がPRを作成
   └ 説明文に「人間には見えないHTMLコメント」で
     「ひそかに別プロジェクトを調べて報告しろ」と命令を埋め込む

② 上司やシニアエンジニアがAIエージェントに「このPRをレビューして」と依頼

③ AIエージェントがPRの説明文を読む
   └ 人間には見えなかった隠し命令を「指示」として受け取ってしまう

④ AIエージェントが上司の権限で勝手に動き出す
   └ 別プロジェクトのパイプライン起動
   └ 機密情報が書かれたWikiページを閲覧
   └ その内容をPRのコメントとして投稿（攻撃者が読める場所に！）

⑤ 攻撃者が情報を入手 ✓
```

## 技術的な詳細

### なぜ「見えない」のか？

Azure DevOpsのPR説明文はMarkdownというテキスト形式に対応しており、HTMLも書けます。HTMLコメント `<!-- 隠し文字 -->` はブラウザの画面では完全に非表示になります。

| 人間がブラウザで見るもの | AIエージェントがAPIで受け取るもの |
|---|---|
| 普通のPR説明文だけ | 説明文 ＋ 隠しHTMLコメントの命令 |

これが「人間とAIの見ている世界のズレ」であり、攻撃の核心です。

### なぜMicrosoftの対策が不完全だったのか？

Microsoftはすでに「スポットライト技術」という対策を一部のツールに実装していました。これは「信頼できないデータ」と「本来の指示」を区別するための仕組みです。

```
✅ WikiページツールやビルドログツールはこのOK
   → createExternalContentResponse（安全なラッパー）を使っている

❌ PRを取得するツール（repo_get_pull_request_by_id）はNG
   → このラッパーを使わず、説明文をそのままAIに渡してしまっている！
```

つまり「ほとんどのドアに鍵をかけたけど、1つだけ鍵をかけ忘れた」状態でした。このかけ忘れたドアが今回の攻撃口になりました。

### 実際の実証テストで何が起きたか？

研究者たちはバージョン2.7.0で実験し、たった1つの隠しコメントが以下の一連の動作を引き起こすことを確認しました：

1. **別プロジェクトのパイプライン（自動処理）を起動**
2. **攻撃者がアクセスできない機密Wikiページを読み込み**
3. **その内容をPRコメントとして投稿**（攻撃者が確認できる）

しかも「GitHub Copilot CLI」と「Claude Code」の両方のAIエージェントで再現できたため、特定のAIだけの問題ではありません。

## なぜ重要なのか

### 🎯 攻撃が「静かすぎる」
攻撃者はAIエージェントと直接やり取りしません。被害者（レビュアー）も何もおかしなことをしていません。ただ「いつも通りAIにレビューを頼んだだけ」なのに、攻撃が成立してしまいます。

### 🔑 上位権限を「借りられる」
PRを出す人（攻撃者かもしれない）より、レビューする人（上司・シニアエンジニア）の方が通常は高い権限を持っています。AIエージェントはレビュアーの権限で動くため、**攻撃者は自分では絶対に届かない場所にまでアクセスできてしまいます**。

### 📦 盗める情報の範囲が広い
- ソースコード（他プロジェクトのコードも）
- シークレット情報（パスワード、APIキーなど）
- 作業記録（誰が何をしているか）
- 機密のWikiページ

### 🚀 AIを使った自動化が進むほど危険が増す
「自動レビュー」「自動トリアージ」が当たり前になれば、**人間が確認する機会がなくなり**、攻撃が完全に人の目をすり抜けてしまいます。

## 対策・今後の展望

### 現在の状況
記事執筆時点（2025年7月21日）では、MicrosoftはAzure DevOps MCPサーバーの該当部分（`repo_get_pull_request_by_id`）にまだ修正を適用していないことが確認されています。

### ✅ 今すぐできる対策

| 対策 | 説明 |
|---|---|
| **AIエージェントの自動承認をOFFに** | 「確認なしに何でもやっていい」設定を避け、重要な操作は人間が確認する |
| **AIに与える権限を最小限に** | AIエージェントには必要最低限の権限だけ付与する（最小権限の原則） |
| **外部からのPRに特に注意** | よく知らない人からのPRをAIにレビューさせるときは慎重に |
| **Microsoftのパッチを待つ** | 修正版がリリースされたらすぐにアップデートする |

### 🔮 今後の展望
Microsoftはすでに「スポットライト技術」という正しいアイデアを持っており、他のツールには適用しています。今回の問題は「適用し忘れ」なので、比較的早期に修正パッチが出ることが期待されます。

ただし、この問題はAzure DevOpsだけの話ではなく、**「AIが外部のコンテンツを読む」すべての場面で起こりうる**普遍的なリスクです。AI活用が広がるにつれて、同様の脆弱性は他のサービスでも発見され続けるでしょう。

## 過去記事との関連

以前、「**クラトス（Kratos）フィッシングキット摘発**」の記事で、Microsoft 365のログイン情報を盗む攻撃について解説しました。あの事件では「人間のユーザーを騙してパスワードを盗む」という手口でしたが、今回は一歩進んで**「AIを騙して、AIに人間の代わりに情報を盗ませる」**という新しい形の攻撃です。

攻撃者のターゲットが「人間」から「AIエージェント」へと広がっていることがわかります。AIが便利なツールとして普及するほど、AIを悪用する攻撃も増えていく——これがセキュリティの最新トレンドです。

## 用語解説

| 用語 | 説明 |
|---|---|
| **Azure DevOps** | Microsoftが提供するソフトウェア開発管理プラットフォーム |
| **MCP（Model Context Protocol）** | AIエージェントが外部サービスを操作するための共通規格 |
| **プルリクエスト（PR）** | コードの変更を本番環境に取り込む前にレビューを求める申請 |
| **プロンプトインジェクション** | AIへの指示に悪意ある命令を混ぜ込む攻撃手法 |
| **HTMLコメント** | ブラウザに表示されないが、データとして存在するテキスト（`<!-- 内容 -->`) |
| **スポットライト技術** | 「信頼できないデータ」と「本来の指示」をAIに区別させるMicrosoftの対策技術 |
| **混乱した代理人バグ（Confused Deputy Bug）** | 権限を持つ「代理人（今回はAI）」が、攻撃者の代わりに本来できない操作をさせられるセキュリティ問題 |
| **最小権限の原則** | ユーザーやプログラムに必要最低限の権限しか与えないセキュリティの基本原則 |
| **パイプライン** | ソフトウェアの自動ビルド・テスト・デプロイの一連の処理 |
| **シークレット** | APIキーやパスワードなど、漏れてはいけない機密情報 |
