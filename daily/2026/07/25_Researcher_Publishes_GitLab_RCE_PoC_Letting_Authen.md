# 認証済みユーザーがGitサーバー上でコマンドを実行できるGitLabの深刻な脆弱性が公開された

**元記事**: [Researcher Publishes GitLab RCE PoC Letting Authenticated Users Run Commands as Git](https://inl03.netline.com/ltr6/?_m=3n.009a.4039.sp0ao46r89.33ew)
**解説日**: 2025年7月25日

---

## 背景知識

このニュースを理解するために、まずいくつかの基本的な概念を押さえておきましょう。

### GitLabとは？
**GitLab（ギットラボ）** は、ソフトウェアのソースコード（プログラムの設計図）を管理・共有するためのサービスです。チームでプログラムを開発するときに「誰がいつどこを変更したか」を記録できる、いわば「チーム開発の共有ノート」のようなものです。GitHubと似たサービスで、企業が自社のサーバー上に設置して使う「セルフホスト型」もあります。

### RCE（リモートコード実行）とは？
**RCE（Remote Code Execution）** は、攻撃者がインターネット越しに、他人のサーバー上で好き勝手な命令（コマンド）を実行できてしまう、最も危険な脆弱性の一つです。家に例えると「玄関を通らずに、外から勝手に家の中の電気やガスを操作できてしまう」ようなイメージです。

### PoC（概念実証コード）とは？
**PoC（Proof of Concept）** とは、「この脆弱性は本当に悪用できますよ」と実際に動くコードで証明したものです。研究者が公開することで世間に危険性を知らせる目的がありますが、悪用される危険もあります。

### Jupyter Notebook（ジュピター・ノートブック）とは？
データ分析やプログラミングの学習によく使われるファイル形式です。コードと実行結果を一緒に記録できる「インタラクティブなメモ帳」のようなもので、`.ipynb`という拡張子を持ちます。GitLabはこのファイルを画面上でプレビュー表示する機能を持っています。

### メモリ（コンピュータの作業机）について
コンピュータは処理中のデータを「メモリ（RAM）」という場所に一時保存します。このメモリには「ヒープ」という領域があり、プログラムが動的にデータを保存する場所です。メモリの管理を間違えると、関係ない場所を上書きしてしまう「メモリ破壊」というバグが生まれます。

## 何が起きたのか

2025年7月24日、**depthfirst** というセキュリティ研究チームが、GitLabに対する深刻な攻撃コード（PoC）を公開しました。

### 時系列で整理すると

| 日付 | 出来事 |
|------|-------|
| 5月21日 | depthfirstがバグの報告をGitLabに連絡 |
| 5月27日 | バグの修正がマージ（統合）される |
| 6月4日 | 関連ライブラリ「Oj 3.17.3」がリリース |
| 6月5日 | GitLabへの攻撃チェーンを報告 |
| 6月8日 | GitLabが脆弱性を確認 |
| **6月10日** | **GitLabがパッチ（修正版）をリリース** |
| **7月24日** | **depthfirstが動作する攻撃コードを公開** |

つまり、**修正版が出てから約6週間後に攻撃コードが公開**されたという状況です。

### 特に問題なのはここ！
GitLabはこの修正を「**セキュリティ修正ではなくバグ修正**」として分類しました。そのため、CVE番号（脆弱性に付けられる世界共通のID番号）もなく、深刻度を示すCVSSスコアもありませんでした。管理者が「緊急のセキュリティパッチだ」と気づきにくい状態で公開されたのです。

## 技術的な詳細

少し難しいですが、できるだけわかりやすく説明します。

### 攻撃の流れ（全体像）

```
攻撃者（プロジェクトにアクセスできる一般ユーザー）
    ↓
① 細工したJupyter Notebookファイルをプロジェクトにアップロード
    ↓
② GitLabがファイルをプレビュー表示する際に、
   Ojというライブラリがファイルの内容を処理
    ↓
③ メモリの「住所情報」が画面に漏れ出す（情報漏洩）
    ↓
④ 漏れた情報を使って、サーバーの内部構造を把握
    ↓
⑤ 別の細工したファイルで攻撃コードを実行
    ↓
⑥ サーバー上で任意のコマンドを「git」ユーザーとして実行！
```

### 使われた2つのバグ（Ojライブラリの脆弱性）

**Oj（オージェイ）** というのは、Ruby言語でJSON（データの記述形式）を高速に処理するためのライブラリ（部品集）です。C言語という低レベルな言語で書かれているため、メモリ管理のミスが起きやすい環境です。

**バグ①：スタックオーバーフロー（バッファオーバーライト）**
- プログラムは「入れ子（ネスト）」の深さを1,024段まで記録できる棚を持っていました
- 攻撃者が1,024段を超えるデータを送ると、棚からはみ出して関係ない場所（コールバック関数のポインタ）を上書きできてしまいます
- 家の本棚に本を詰め込みすぎて、隣の棚の大事な書類が押し出されるイメージです

**バグ②：ヒープポインタの漏洩（情報漏洩）**
- 65,565バイトのキー文字列の長さを保存する変数が、本来は16ビット符号付き整数で管理されていました
- これにより長さが29という誤った値になり、その結果としてメモリの「住所（ポインタ）」が画面に表示されてしまいます
- 「秘密の倉庫の住所が、レシートに誤って印刷されて渡された」ようなイメージです

### この2つを組み合わせると
1. バグ②でサーバーのメモリ上のlibc（基本ライブラリ）の位置を特定
2. バグ①で、プログラムが次に呼ぶ関数の「電話番号」を書き換えて、`system()`（OSコマンドを実行する関数）を指すようにする
3. 結果として攻撃者が好きなコマンドを実行できる

## なぜ重要なのか

### 影響の広さ
- **対象バージョン**: GitLab 18.11.3（自社サーバーで運用しているもの）
- **対象エディション**: 無料版（CE）・有料版（EE）すべて、全プランが対象
- **攻撃に必要な条件**: プロジェクトにコードをアップロードできる「一般ユーザー」権限があれば十分

> 🚨 **管理者権限不要！** 普通のユーザーアカウントさえあれば攻撃できます

### 攻撃が成功した場合に奪われる可能性があるもの
- **ソースコード**（プログラムの設計図）
- **Railsシークレット**（Webアプリの暗号化キーなど）
- **サービスの認証情報**（データベースのパスワードなど）
- **CI/CDパイプラインのデータ**（自動ビルド・デプロイの設定）
- **内部ネットワークサービスへのアクセス**

### 「gitユーザーとして実行」とは？
攻撃コードは `git` というOSユーザーの権限で動きます。これはGitLabアプリを動かしているユーザーで、GitLabが触れるデータには基本的にすべてアクセスできます。どこまで被害が広がるかは、そのサーバーがどれほど適切に「隔離・権限分離」されているかに依存します。

### 発見が遅れた理由
- GitLabが「セキュリティパッチ」ではなく「バグ修正」として分類したため
- CVE番号がなく、脆弱性管理ツールが検知しにくかった
- 管理者がパッチを「緊急度が低い」と判断してしまいやすかった

## 対策・今後の展望

### 今すぐやること（優先度：高）

✅ **以下のいずれかのバージョンにアップグレードしてください**

| 現在のバージョン | アップグレード先 |
|--------------|--------------|
| 18.10.x | **18.10.8** |
| 18.11.x | **18.11.5** |
| 19.0.x | **19.0.2** |

> ⚠️ **注意**: 15.2〜18.9のバージョンはサポート対象外のため、バックポート（古いバージョンへの修正の移植）が提供されません。これらを使っている場合はサポートされているバージョンへの移行が必要です。

### Kubernetes（Helm/Operator）環境を使っている場合
チャートやオペレーターのバージョンではなく、**Puma（プーマ）を動かしているWebserviceイメージのGitLabバージョン**を確認してください。バージョン表示が異なる場合があるので注意が必要です。

### ワークアラウンド（一時的な回避策）は？
残念ながら、**depthfirstもGitLabも、アップグレード以外の回避策を提供していません**。パッチ適用が唯一の対策です。

### 今後の動向
- The Hacker Newsがなぜ「セキュリティ修正」と分類されなかったのかをGitLabに問い合わせ中
- CVE番号が今後付与される可能性あり
- 現時点では実際の攻撃（野生での悪用）は確認されていないとのことですが、攻撃コードが公開されているため油断できません

## 過去記事との関連

今回は関連する過去記事はありませんが、**GitLabに対する脆弱性は過去にも繰り返し発見されています**。GitLabはソースコードを管理するという性質上、攻撃者にとって非常に「おいしい」ターゲットです。開発者のコードや企業の機密データが集中しているため、攻撃が成功すると被害が甚大になります。

「パッチをセキュリティ修正と分類しなかった」という今回のケースは、**脆弱性の開示・分類のあり方**について業界全体に問題提起をしています。

## 用語解説

| 用語 | 意味 |
|------|------|
| **GitLab** | ソースコードをチームで管理・共有するためのサービス（自社サーバー設置型あり） |
| **RCE（リモートコード実行）** | 攻撃者がネット越しにサーバーで任意のコマンドを実行できる最も危険な脆弱性 |
| **PoC（概念実証）** | 脆弱性が実際に悪用できることを示す動作するサンプルコード |
| **Jupyter Notebook** | `.ipynb`形式のファイル。データ分析などに使うインタラクティブなノート |
| **Oj** | RubyでJSONを処理するためのライブラリ（C言語で実装） |
| **ヒープポインタ** | プログラムのメモリ上のデータの「住所」を示す値 |
| **スタックオーバーフロー** | プログラムが用意した記憶領域の限界を超えてデータが書き込まれるバグ |
| **CVE** | 脆弱性に付けられる世界共通のID番号（例：CVE-2024-XXXX） |
| **CVSSスコア** | 脆弱性の深刻度を0〜10で示すスコア |
| **Puma** | RubyのWebアプリケーションサーバー（GitLabもこれを使用） |
| **libc** | LinuxのCプログラムが使う基本ライブラリ |
| **CI/CD** | コードの自動テスト・自動デプロイの仕組み |
| **セルフマネージド** | クラウドサービスではなく、自社サーバーで自分たちで運用する形態 |
| **バックポート** | 新しいバージョンで作った修正を、古いバージョンに移植すること |
