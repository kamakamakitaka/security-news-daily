# Hugging Face Diffusersの欠陥：AIモデルのリポジトリが勝手にコードを実行できる脆弱性

**元記事**: [Hugging Face Diffusers Flaws Could Let Model Repositories Execute Arbitrary Code](https://inl03.netline.com/ltr6/?_m=3n.009a.4046.sp0ao46r89.33pm)
**解説日**: 2026年8月4日

---

## 背景知識

このニュースを理解するために、まずいくつかの基本的な概念を押さえておきましょう。

### 🤗 Hugging Face（ハギング・フェイス）とは？

「Hugging Face」は、AIの世界における**GitHub（ギットハブ）のような存在**です。GitHubが「プログラマーがコードを共有・管理する場所」であるように、Hugging FaceはAI研究者や開発者が**AIモデル（学習済みのAIプログラム）を共有・公開する場所**です。世界中の企業や研究機関が利用しており、AIの世界では非常に重要なプラットフォームです。

### 🎨 Diffusers（ディフューザーズ）とは？

Hugging Faceが提供する**Pythonライブラリ（便利な機能の集まり）**のひとつです。画像・動画・音声を生成するAI（いわゆる「画像生成AI」）を簡単に利用するためのツールです。Stable DiffusionなどのAIモデルをプログラムから使いたいときに使われます。2026年7月だけで**810万回以上ダウンロード**されているほどの人気ツールです。

### 🔒 「trust_remote_code」とは？

AIモデルを読み込む際に、そのモデルに付随する「カスタムコード（特別なプログラム）」を実行するかどうかを制御する**安全スイッチ**です。

- `True`（オン）にすると → カスタムコードを実行する（便利だが危険）
- `False`（オフ）にすると → カスタムコードを実行しない（安全）
- 何も設定しない（デフォルト）→ 本来は`False`と同じ安全な動作のはず

このスイッチを「False」にしているから安全だ、と多くの人が信じていました。ところが今回、その信頼が根底から崩れる脆弱性が見つかりました。

### 🐛 任意コード実行（RCE）とは？

「**Remote Code Execution（リモートコード実行）**」の略で、攻撃者が**本来は実行されてはいけない悪意あるプログラムを、被害者のコンピューターで勝手に動かせる**攻撃です。これが起きると、データの盗難・システムの破壊・不正操作など何でもできてしまう、非常に危険な状態になります。

## 何が起きたのか

セキュリティ企業「Zafran Labs」の研究者たちが、Hugging FaceのDiffusersライブラリに**3つの深刻な脆弱性（セキュリティ上の欠陥）**を発見しました。

この脆弱性群は「**FaceHugger（フェイスハガー）**」と名付けられました（映画「エイリアン」に登場する顔に貼りつく生き物から取ったと思われる、インパクトのある名前です）。

> 💡 **簡単に言うと：**
> 「安全スイッチをオフにしているのに、攻撃者が細工したAIモデルを読み込むだけで、あなたのパソコンで悪意あるプログラムが勝手に実行されてしまう」という問題です。

具体的には、AIの開発者や研究者が悪意を持ったモデルリポジトリ（モデルの公開ページ）を作成・改ざんすることで、そのモデルをダウンロードして使おうとした人のコンピューターに侵入できてしまいます。

## 技術的な詳細

### 🔍 問題の根本原因：「チェックのタイミングのズレ」

この脆弱性の核心は「**TOCTOU（トクトゥー）問題**」と呼ばれる古典的なセキュリティ問題です。

> 🏪 **例え話で理解しよう：**
> あなたがコンビニで年齢確認が必要なお酒を買おうとしているとします。
> 1. レジの店員さんがIDを確認します → **「この人は成人だ」と判断（チェック）**
> 2. 商品を袋に入れる間に、こっそり別の未成年の人と入れ替わります
> 3. 袋を受け取るのは未成年の人です → **チェックした人と受け取る人が違う！（使用）**
>
> これが「Time-of-Check to Time-of-Use（チェック時と使用時のズレ）」問題です。

Diffusersでも同じことが起きていました：

```
【通常の流れ（安全のつもり）】
① モデルの設定ファイルをダウンロード → 安全チェック実施 ✅
② モデルの残りのファイルをダウンロード
③ コードを実行

【攻撃者の悪用方法】
① モデルの設定ファイルをダウンロード → 安全チェック実施 ✅（この時点では無害）
   ↑ ここで攻撃者がサーバー上のファイルをこっそり悪意あるものに差し替え！
② 差し替えられた悪意あるファイルをダウンロード ⚠️
③ 悪意あるコードが実行される 💥
```

つまり、「安全かどうかの確認」と「実際にダウンロード・実行されるもの」が**同一のものではない可能性**があったのです。

### 📋 発見された3つの脆弱性

| 脆弱性ID | 危険度スコア | 内容 |
|----------|-------------|------|
| **CVE-2026-44827** | 8.8 / 10（高） | `None.py`という特殊な名前のパイプラインを使って、安全スイッチを無効化してコードを実行 |
| **CVE-2026-45804** | 7.5 / 10（高） | ダウンロード中にサーバー上のファイルをすり替えることで悪意あるコードを実行（競合状態） |
| **CVE-2026-44513** | 8.8 / 10（高） | カスタムパイプラインの読み込み処理を通じて、安全スイッチを無視してコードを実行 |

> 💡 **CVSSスコアとは？**
> 脆弱性の危険度を0〜10で表したスコアです。7.0以上は「高（High）」、9.0以上は「緊急（Critical）」に分類されます。今回の2つは8.8という非常に高いスコアです。

## なぜ重要なのか

### 🏢 企業への影響が甚大

Hugging Faceは今やAIの世界の「GitHub」とも呼ばれるほど普及しており、世界中の企業がDiffusersを使っています。特に以下の場面で広く使われているため、被害が広がりやすい状況です：

- **CI/CDシステム**（自動でプログラムをビルド・テストする仕組み）
- **本番環境のパイプライン**（実際のサービスを動かすシステム）
- **コンテナイメージ**（クラウドで動くアプリのパッケージ）

### 🎭 「AIモデル」という盲点

研究者たちが特に警告しているのは、**「AIモデルはただのデータだ」という誤解**です。

> 🧠 **例え話：**
> 料理レシピ本（データ）だと思って本棚に置いていたら、実はその本を開くだけで仕掛けが動いて金庫が開いてしまう、トラップ入りの本だったようなものです。

AIモデルのリポジトリには、設定ファイル・ローダー（読み込み処理）・カスタムコードが含まれており、これらは**実行可能なコードに変わりうる**のです。なのに多くの人は「データをダウンロードしているだけ」と油断してしまいます。

### 🌐 AIサプライチェーン攻撃の脅威

今回の問題は「**AIサプライチェーン攻撃**」の一例でもあります。

> 💡 **サプライチェーン攻撃とは？**
> 直接ターゲットを攻撃するのではなく、**ターゲットが使っているツールや部品（=サプライチェーン）に悪意あるものを混入させる**攻撃です。企業が何気なく使っているライブラリやモデルを踏み台にすることで、大量の被害を一気に引き起こせる危険な手法です。

## 対策・今後の展望

### ✅ まずアップデートを！

最も重要な対策は**Diffusersを最新バージョンにアップデートすること**です。

- **修正済みバージョン**：Diffusers **0.38.0以降**（2026年5月初旬にリリース）
- 確認方法：`pip show diffusers` でバージョンを確認できます

### 🛡️ すぐにアップデートできない場合の回避策

プロジェクト開発元が推奨する一時的な対策は以下の通りです：

1. **信頼できるソースのみ使用する**
   `from_pretrained()`を呼び出す際は、十分に審査・確認済みのモデルのみを使う

2. **異なるリポジトリへのカスタムパイプライン指定を避ける**
   メインのモデルとは別のHubリポジトリを`custom_pipeline=`で指定しない

3. **公開されているモデルを常に確認する習慣をつける**
   AIモデルを「ただのデータ」として扱わず、コードのレビューと同じ慎重さで扱う

### 🔮 今後の動向

AIの普及に伴い、今後もこうした「AIサプライチェーンへの攻撃」は増加すると予想されます。AIモデルを安全に扱うためのセキュリティ標準や検証ツールの整備が、業界全体の課題となっていくでしょう。

## 過去記事との関連

以前、**N-ableのN-centralサーバーが乗っ取られた事件**（「最初の修正では不十分だった」という話）を解説しました。あの事件でも「一度修正したはずなのに、まだ問題が残っていた」という状況が起きましたね。

今回のFaceHugger脆弱性も、共通するテーマがあります。それは「**信頼していた安全策が実は穴だらけだった**」という点です。

- N-ableの事件：「パッチを当てたから安全」→ でも完全ではなかった
- 今回の事件：「`trust_remote_code=False`にしたから安全」→ でも実は回避できた

セキュリティの世界では「〜だから安全なはず」という思い込みが、最も危険な状態を生み出すことがよくあります。**「信頼してもゼロで検証（Zero Trust）」**の考え方がいかに大切かを、改めて示す2つの事件と言えるでしょう。

## 用語解説

| 用語 | 解説 |
|------|------|
| **Hugging Face** | AIモデルを共有・公開するプラットフォーム。「AIのGitHub」とも呼ばれる |
| **Diffusers** | 画像・動画・音声生成AIを使うためのPythonライブラリ |
| **脆弱性（ぜいじゃくせい）** | ソフトウェアのセキュリティ上の欠陥・弱点 |
| **RCE（任意コード実行）** | 攻撃者が被害者のコンピューターで好きなプログラムを実行できる状態 |
| **trust_remote_code** | 外部コードの実行を制御するDiffusersの安全スイッチ |
| **TOCTOU** | 「確認した時点」と「実際に使う時点」がズレることで生じるセキュリティ問題 |
| **CVSSスコア** | 脆弱性の危険度を0〜10で数値化したもの。7以上は「高リスク」 |
| **サプライチェーン攻撃** | 使っているツールや部品に悪意あるものを混入させる間接的な攻撃手法 |
| **CI/CDシステム** | ソフトウェアを自動的にテスト・リリースする仕組み |
| **リポジトリ** | ファイルやコードを保管・管理する場所（GitHubのプロジェクトページのようなもの） |
| **パイプライン** | データや処理を順番につなげた一連の処理フロー |
