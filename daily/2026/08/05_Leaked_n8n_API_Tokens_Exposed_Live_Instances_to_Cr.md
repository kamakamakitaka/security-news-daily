# 流出したn8n APIトークンにより、稼働中のシステムが認証情報盗難の危機に

**元記事**: [Leaked n8n API Tokens Exposed Live Instances to Credential Theft](https://inl03.netline.com/ltr6/?_m=3n.009a.4048.sp0ao46r89.33s2)
**解説日**: 2026年8月6日

---

## 背景知識

### n8n（エヌエイトエヌ）って何？

「n8n」は、**いろんなサービスやシステムを自動でつなぐための業務自動化ツール**です。

たとえばこんなことができます：
- 「新しい注文が入ったら、Slackに通知して、データベースに記録して、請求書を自動発行する」
- 「毎朝9時に天気APIからデータを取得して、社内ツールに送る」

これを「**ワークフロー**」と呼び、プログラミングが苦手な人でも画面上でパーツを組み合わせて作れます（ローコードツール）。GitHubで約20万スター（お気に入り登録）がついているほど人気のツールです。

### APIトークンって何？

**APIトークン**とは、「**このサービスへのアクセスを許可された証明書（鍵）**」のようなものです。

> 🔑 例え話：ホテルのカードキーを想像してください。そのカードを持っている人は誰でも部屋に入れます。カードを拾った人も同じく入れてしまいます。

### GitHubとは？

**GitHub**は、プログラマーがソースコード（プログラムの設計図）を公開・共有できるサービスです。「公開リポジトリ」に上げたコードは世界中から見られます。

### GitGuardianって何？

**GitGuardian**は、GitHubなどに誤って公開されてしまった秘密の情報（パスワード、APIキーなど）を自動で探し出すセキュリティ企業です。

## 何が起きたのか

GitGuardianのセキュリティ研究者が、公開されているGitHubのコードを調べたところ、**n8nへのアクセスキー（APIトークン）が大量に誤って公開されている**ことを発見しました。

調査の結果：

| 項目 | 数値 |
|------|------|
| 発見したAPIトークン（ユニーク） | **4,576個** |
| 関連するサーバーアドレス（ホスト名） | **1,255件** |
| 実際に接続できたサーバー | **896件** |
| 流出トークンでログインできたサーバー | **321件（約36%）** |

つまり、**「鍵が外に落ちていて、その鍵で実際にドアが開いてしまう」状態のサーバーが321台あった**ということです。

## 技術的な詳細

### なぜ鍵（トークン）が公開されてしまうの？

開発者がコードを書くとき、テスト用に本物のAPIトークンをコードに書いてしまい、そのままGitHubに公開してしまうことがよくあります。

```
# 悪い例（こんなコードをGitHubに公開してしまうと危険）
N8N_API_TOKEN = "n8n_abc123xyz789..."  ← これが流出する！
```

### 攻撃者は何ができるの？

研究者たちは実際に4種類の攻撃手法を実演しました。特別な攻撃ツールは一切不要で、**公式の機能だけを使って**以下が可能でした：

1. **📋 ワークフロー定義の閲覧**
   業務の自動化フローをすべて見ることができる（どんな処理をしているかバレる）

2. **🔑 保存された認証情報の悪用**
   n8nには他サービス（データベース、クラウド、AIサービスなど）へのID・パスワードが保存されています。攻撃者はそれを「自分のために動かす」ことができます

3. **📂 実行データの取得**
   過去に実行されたワークフローのデータ（顧客情報なども含む可能性）を取得できる

4. **🗝️ 認証情報の値そのものを抜き取る**
   設定によっては、暗号化して保存されているパスワードやAPIキーの「生の値」を取り出せてしまう

> 🏠 例え話：n8nのサーバーに入ることは、会社のマスターキーを手に入れるようなもの。倉庫のカギも、社長室のカギも、全部そこから開けられてしまう、という状態です。

### 既知の脆弱性も深刻

さらに記事では、n8n自体にも深刻なセキュリティ問題があることが報告されています：

- 2026年1月以降だけで**50件以上**のセキュリティ警告が発表されている
- スキャンしたサーバーの**58%**が既知の脆弱性を持つバージョンを使用中
- **CVE-2025-68613**（深刻度スコア：9.9/10！）という脆弱性は、すでに実際に攻撃に使われたとして米国政府機関（CISA）のリストに掲載された

## なぜ重要なのか

### 「連鎖的な被害」が怖い

n8nは業務の「ハブ（中継点）」です。n8nに侵入されると、そこにつながっている**すべてのサービスへの扉が開く**可能性があります。

```
攻撃者
  ↓ n8nのトークン1つで侵入
n8n（ハブ）
  ├── データベース（顧客情報）
  ├── GitHubリポジトリ（ソースコード）
  ├── クラウド（AWS/GCPなど）
  ├── AIサービス
  └── カスタマーサポートシステム
```

### 「脆弱性を突かなくても」侵入できる

通常のハッキングは、ソフトウェアのバグ（脆弱性）を使います。しかし今回の問題は**「正しいパスワードを持っているだけで入れてしまう」**という点で、より検知が難しく、対処も異なります。

> 💡 ポイント：鍵穴を壊すのではなく、合鍵を作って堂々と入ってくる攻撃です。セキュリティシステムが「正規のアクセス」と判断してしまうため、気づきにくいのです。

## 対策・今後の展望

### 企業・開発者が取るべき対策

**🚨 今すぐやること**

1. **流出したトークンを今すぐ無効化・再発行する**
   GitHubに誤って公開したAPIトークンは、すでに誰かに見られている可能性があります

2. **GitHubのコードをチェックする**
   自分のリポジトリにAPIトークンやパスワードが含まれていないか確認する

**🔒 継続的な対策**

3. **シークレット管理ツールを使う**
   APIキーやパスワードはコードに直接書かず、専用の管理ツール（`.env`ファイルや、AWS Secrets Managerなど）を使う

4. **n8nを最新バージョンに更新する**
   既知の脆弱性の58%は、アップデートすれば防げます

5. **アクセス権限を最小限にする**
   n8nのAPIトークンには「読み取り専用」など、必要最低限の権限だけを与える

6. **GitGuardianなどのシークレットスキャンツールを導入する**
   コードをGitHubに公開する前に、自動で秘密情報が含まれていないかチェックする仕組みを作る

## 過去記事との関連

以前「**あなたの会社はAIを導入した。でも、誰がそのAIを守っているの？**」という記事を解説しました。

あの記事では「AIツールを導入したはいいが、セキュリティ管理が追いついていない」という問題を取り上げました。今回のn8nの問題はまさにその続きです。

n8nはAIエージェント機能を持ち、AIサービスと連携して動作します。記事の中でも「MCP（Model Context Protocol）APIキー」という**AI連携用のキーも同様に流出していた**と報告されています。

つまり：
> 「AI機能を業務に組み込んだが、そのAIを動かすための鍵が丸見えになっていた」

という構図であり、**AIの導入が進むほど、セキュリティ管理の穴も広がる**というリスクが改めて示されました。

## 用語解説

| 用語 | 意味 |
|------|------|
| **n8n（エヌエイトエヌ）** | 複数のサービスをつなぐ業務自動化ツール。オープンソースで無料から使える |
| **APIトークン** | サービスへのアクセス許可証。これを知っていれば本人確認なしに操作できる |
| **GitHub（ギットハブ）** | プログラマーがコードを公開・共有するサービス。世界最大のコードホスティングサービス |
| **GitGuardian** | GitHubなどに誤って公開された秘密情報を自動検出するセキュリティサービス |
| **ワークフロー** | 「○○したら○○する」という自動処理の流れ |
| **脆弱性（CVE）** | ソフトウェアのセキュリティ上の欠陥。CVEは世界共通の脆弱性識別番号 |
| **CVSS スコア** | 脆弱性の深刻度を0〜10で表した数値。9.9は最高レベルに近い危険度 |
| **CISA** | 米国のサイバーセキュリティ・インフラセキュリティ庁。日本のIPAに相当 |
| **Shodan（ショーダン）** | インターネットに公開されているサーバーやデバイスを検索できる特殊な検索エンジン |
| **ローコード** | プログラミングの知識が少なくても使えるツール |
| **MCP（Model Context Protocol）** | AIアシスタントがツールやデータと連携するための標準的な仕組み |
| **ブラストラディウス** | 爆発の被害半径→セキュリティ用語で「攻撃が及ぶ影響範囲」のこと |
