**元記事**: [Attackers Compile khunt Inside Oracle to Turn SQL Injection Into Windows SYSTEM Access](https://inl03.netline.com/ltr6/?_m=3n.009a.4049.sp0ao46r89.33tg)
**解説日**: 2026年8月7日

---

## 背景知識

まず、このニュースを理解するための基礎知識を整理しましょう。

### 🗄️ データベースって何？
「データベース」とは、情報を整理して保管する「巨大なデジタル棚」です。例えば、ネットショップであれば「商品名・価格・在庫数」などが整理されて入っています。今回の話に登場する **Oracle Database（オラクル・データベース）** は、特に企業や政府機関などが使う、世界的にメジャーな高性能データベースです。

### 💉 SQLインジェクションって何？
**SQL（エスキューエル）** とは、データベースに「これを調べて」「これを追加して」と命令するための言語です。

**SQLインジェクション**とは、入力欄（検索ボックスなど）に普通の文字の代わりに「不正な命令文」を入力して、データベースを操る攻撃のことです。

> 🍵 **わかりやすい例え話**
> コーヒーショップの注文票に「名前：田中; 全員のコーヒーを無料にする」と書いたら、その命令まで処理されてしまった…というイメージです。入力欄の内容をちゃんとチェックしていないと起こります。

### 🖥️ Windowsの「SYSTEM権限」って何？
Windowsには「誰が何をできるか」を管理する権限の仕組みがあります。**SYSTEM権限**はその最上位で、「パソコン上でなんでもできる神様アカウント」です。普段は人間が使うものではなく、OSの中枢が使うレベルです。

## 何が起きたのか

2026年7月27日、セキュリティ企業 **Huntress（ハントレス）** が、ある組織のシステムで不審な動きを検知しました。

調査の結果、以下のような攻撃の流れが明らかになりました：

```
①  ウェブアプリの検索ボックス
        ↓ SQLインジェクション攻撃
②  Oracleデータベースに侵入
        ↓ データベースの中にプログラムを作成・実行
③  Windowsサーバーの「SYSTEM権限」を取得
        ↓ やりたい放題の状態に
④  パスワード情報などを盗み出そうとした
```

特に怖いのは、攻撃者が**ファイルを一切ディスク（ハードドライブ）に保存しなかった**ことです。これにより、多くのウイルス検出ソフトが気づけませんでした。

## 技術的な詳細

### 🔍 どこから侵入したの？

ウェブアプリの「オートコンプリート検索フィールド（検索ボックスに文字を入れると候補が出てくる機能）」が入口でした。

この検索ボックスは、入力された文字をそのままデータベースへの命令に使っていました（＝チェックをしていなかった）。そして、その命令を送るデータベースアカウントが**過剰な権限**を持っていたため、攻撃者はデータベースの中にプログラムを作れてしまいました。

### 🧩 「khunt（ケーハント）」ツールキットとは？

攻撃者はデータベースの中に**6つのJavaプログラム**と複数のSQLラッパーを作り込みました。これがHuntressが「khunt」と名付けたツールキットです：

| ツール名 | 役割 |
|---|---|
| **KhuntCmd** | Windowsのコマンドを実行する（最も危険） |
| **KhuntHash** | Oracleユーザーのパスワードハッシュを盗む |
| **KhuntFS / KhuntFS2** | ファイルを一覧・読み取り・検索する |
| **KhuntT** | ツールキットが動いているか確認する |
| **KhuntUnzip** | 圧縮ファイルを解凍する |

### 🤔 なぜ検知されにくかったの？

> 🏠 **わかりやすい例え話**
> 普通の空き巣は「窓を割って家に入り込む」のでわかりやすいですが、この攻撃は「すでに家にある家電（データベース）の中にロボットを仕込んで、そのロボットに泥棒仕事をさせた」ようなものです。

Javaプログラムをデータベースの**スキーマオブジェクト（データベース内部の構成要素）**として保存したため：
- ハードディスクに「ファイル」として残らない
- 「プロセス（動いているプログラム）」として見えない
- 一般的なウイルス対策ソフトはOracleの内部をチェックしない

### 😱 何をされたの？

`KhuntCmd`を使って`whoami`（「お前は誰だ」とシステムに聞くコマンド）を実行したところ、**「SYSTEM」**と返ってきました。これで完全制御を確認した攻撃者は：

1. **PowerShell** と **reg.exe** を使って、WindowsのSECURITYとSYSTEMのレジストリ（設定情報の宝庫）をコピー
2. **tasklist /svc** でどんなプログラムが動いているか一覧を取得
3. **esentutl.exe** でSAMハイブ（ユーザーのパスワード情報が入ったファイル）をコピー

これらのデータが外部に持ち出されたかどうかは確認されていませんが、盗もうとした痕跡は明確です。

### 📅 実は20年前からある手法だった

この攻撃の技術自体は新しいものではありません。**Marco Ivaldiという研究者が2006年に公開した`raptor_oraexec.sql`**という同様のツールがすでに存在していました。つまり約20年間「理論的には可能」とわかっていながら、実際の攻撃事例としてほとんど記録されてこなかった、という点が今回注目されています。

## なぜ重要なのか

### 🎯 攻撃のポイントは「既存の機能の悪用」

今回の攻撃で使われた機能（JavaをOracleの中でコンパイルして実行する仕組み）は、**Oracleの正規の機能**です。バグや脆弱性ではなく、本来の機能を悪用しているため、Oracleからのパッチ（修正プログラム）では解決できません。

### 🛡️ セキュリティ製品が機能しなかった

一般的なEDR（エンドポイント検出・対応）製品はOracleの内部を監視しないため、この攻撃を見逃しました。Huntressはこれを次のように表現しています：

> 「データベースは攻撃者が**クエリを送る対象**ではなくなり、**攻撃を仕掛ける拠点（ビーチヘッド）**になった」

### 🌐 影響を受ける可能性があるシステム

- Oracleデータベースをウェブアプリと連携して使っている企業・組織
- 特に、**一般公開されているウェブアプリ**がOracleと接続している場合
- データベースアカウントに必要以上の権限を与えている場合

## 対策・今後の展望

### ✅ 今すぐできる確認事項

**攻撃の痕跡を探すには：**
- Oracleのインストール内に `Khunt` で始まるオブジェクト名を検索
- SQLログで `KHUNT%` というパターンを検索

> ⚠️ ただし、これは「khuntツールキット」特有の痕跡です。同じ技術を使った別のツールは見つかりません。

### 🔧 根本的な対策

| 対策 | 説明 |
|---|---|
| **パラメータ化クエリの使用** | SQLインジェクションを防ぐコードの書き方。入力値を命令と分離する |
| **入力バリデーション** | 検索ボックスなどへの入力を事前にチェックして、不正な文字を弾く |
| **最小権限の原則** | データベースアカウントに「必要最低限の権限だけ」を与える。Javaオブジェクトを作る権限は一般的なウェブアプリには不要 |
| **Oracleの内部監視** | データベース内部のオブジェクト変更を監視する仕組みを整える |

> 🔑 **一番大切なメッセージ**
> 「外部に公開しているウェブアプリに接続するデータベースアカウントは、絶対に必要な権限だけを持たせる」これが今回の教訓です。

以前、「**脆弱性管理の重要性**（Mythos Hype関連記事）」について触れましたが、今回の記事はまさにその具体例と言えます。

あの記事では「自社のセキュリティの弱点を把握し、修正することの重要性」を解説しました。今回の攻撃は：
- **弱点1**: アプリのSQLインジェクション脆弱性（入力チェック不足）
- **弱点2**: データベースアカウントへの過剰な権限付与

という**2つの「よく知られた弱点」**が組み合わさって起きています。脆弱性管理の文脈で言えば、どちらも「発見・修正できたはずのリスク」でした。セキュリティは一つ一つの対策の積み重ねが大切です。
