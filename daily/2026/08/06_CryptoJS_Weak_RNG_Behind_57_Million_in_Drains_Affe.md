# CryptoJSの欠陥ある乱数生成機能が原因で570万ドルが盗まれた——5つの暗号資産ウォレットアプリに影響

**元記事**: [CryptoJS Weak RNG Behind $5.7 Million in Drains Affects Five Crypto Wallet Apps](https://inl03.netline.com/ltr6/?_m=3n.009a.4049.sp0ao46r89.33ss)
**解説日**: 2025年8月上旬

---

## 背景知識

このニュースを理解するために、まずいくつかの重要な概念を説明します。

### 🎰 乱数生成とは？
コンピューターは「ランダムな数字」を生成するのが実は苦手です。人間が「1〜10でランダムに！」と言われてすぐ答えられるように見えても、コンピューターは計算によって「ランダムっぽい数字」を作ります。この仕組みを **乱数生成器（RNG: Random Number Generator）** と呼びます。

> 🔑 **なぜ乱数がセキュリティに重要なの？**
> 暗号や鍵の生成には「予測できないランダムさ」が命です。予測できる乱数を使うと、攻撃者が「次に出る数」を計算できてしまいます。これは「予測できるサイコロ」で賭け事をするようなもの——出目がバレていたら勝てませんよね。

### 🪙 暗号資産ウォレットと「リカバリーフレーズ」
暗号資産（ビットコインなど）を管理するウォレット（財布アプリ）を初めてセットアップするとき、**リカバリーフレーズ**（12〜24個の英単語の組み合わせ）が表示されます。

- このフレーズはウォレットの「マスターキー」です
- なくすとお金にアクセスできなくなります
- **逆に言えば、誰かにこのフレーズを知られると、全財産を盗まれます**

このリカバリーフレーズを作るときに「乱数」が使われています。乱数が弱いと、フレーズが予測できてしまうのです。

### 📚 CryptoJSとは？
JavaScriptで動くウェブ・アプリ用の「暗号化ライブラリ（道具箱）」です。多くのアプリが暗号処理にこのツールを借用していました。

セキュリティ調査会社 **Coinspect** が、**「Operation Ill Bloom（イル・ブルーム作戦）」** と名付けた一連の暗号資産盗難事件の原因を特定しました。

| **第2波** | 2025年5月30日〜7月13日 約2.55億円相当 |

## 技術的な詳細

### 🎲 弱い乱数生成の仕組み

CryptoJSの `WordArray.random()` という関数が問題でした。この関数は内部でJavaScriptの `Math.random()` を使っていましたが、これはセキュリティ用途には「弱すぎる」乱数です。

> 🏠 **わかりやすいたとえ話**
> 「安全な金庫の鍵番号を生成するとき、サイコロ（予測困難）ではなく、時計の秒数（予測しやすい）を使ってしまった」ようなイメージです。

### 🔢 探索空間の激減（これが核心です！）

本来、128ビットの乱数は **2の128乗（天文学的な数）** 通りあるはずです。これを全パターン試すのは現実的に不可能です。

しかし、欠陥のある乱数生成器では…

```
本来あるべき組み合わせ数:
  128ビット → 2の128乗通り（340兆兆兆以上）
  256ビット → 2の256乗通り（さらに天文学的）

実際の脆弱な状態:
  128ビット → 2の39乗通り（約5500億）
  256ビット → 2の47乗通り（約140兆）
         ↑
   普通のパソコンで全パターン試せる！
```

> 💡 **もっと身近な例えで**
> 「100桁の暗証番号」が実は「4桁に相当する強度しかなかった」というイメージです。4桁なら0000〜9999の1万通り——頑張れば全部試せますよね。

### 🔍 攻撃者がどうやって盗んだか

攻撃者は以下の手順を自動的に繰り返しました：

```
① 弱い乱数の全パターンを列挙（コンピューターで総当たり）
      ↓
② それぞれをBIP39形式のリカバリーフレーズに変換
      ↓
③ そのフレーズから暗号資産ウォレットのアドレスを計算
      ↓
④ そのアドレスに残高があるか公開ブロックチェーンで確認
      ↓
⑤ 残高があれば、フレーズを使って資産を盗み出す
```

### ⏳ ライブラリの修正の歴史（悲劇的な経緯）

```
2013年頃   CryptoJSに弱い乱数生成器が導入（Math.random()使用）
     ↓
2014年6月  「Multiply-With-Carry」方式に変更（でもまだMath.random()ベース）
     ↓
3.2.0/3.2.1 「ネイティブ暗号乱数」に修正 ✅ ← 一度は直した！
     ↓
3.3.0      「互換性が壊れる」として修正を取り消し ❌ ← 元に戻してしまった！
     ↓
2020年2月  バージョン4.0.0でようやく恒久的に修正 ✅
```

> 😱 **なんと！** 一度修正したのに「他のアプリが動かなくなる」という理由で元の欠陥コードに戻してしまったのです。バージョン3.x系内でアップデートすると、「直ったバージョン」から「欠陥のあるバージョン」に戻ることもありました。

## なぜ重要なのか

### 💸 被害の深刻さ

- **約570万ドル（約8億円）** が盗まれました
- 一度盗まれたら取り戻す手段がほぼありません（暗号資産の特性）

### 🔄 「アプリを更新しても意味がない」という怖い事実

> ⚠️ **超重要ポイント**
> アプリを最新版に更新しても、**過去に欠陥版で生成されたリカバリーフレーズは脆弱なままです！**

リカバリーフレーズ自体が「弱い乱数から作られた弱い鍵」なので、後からどれだけ処理を加えても強くなりません。

> 🏠 **たとえ話**
> 「最初に弱い材料で家の鍵を作ってしまったら、後でいくらドアを強化しても、鍵のコピーはすでに作られている」ようなものです。

### 🔗 ハードウェアウォレットでも危険！

「ソフトウェアウォレットより安全」とされるハードウェアウォレット（物理デバイス）でも、**欠陥版アプリで作ったフレーズをインポートすれば同様に危険**です。

### 📦 依存関係の落とし穴

`ferrumnet/bip39` という別のライブラリが、安全な乱数生成を CryptoJS の弱い実装で上書きしていたことも判明。**アプリ開発者が気づかないうちに脆弱なコードを取り込んでいた**可能性があります。

## 対策・今後の展望

### ✅ 今すぐ確認すべきこと（ウォレットユーザー向け）

**1. 自分が使っているウォレットアプリを確認する**
- RRWallet、Bexo Wallet、NanChat、Bitcoin Libre、Miloを使っていた？
- 特に古いバージョン（修正前）を使っていた時期はないか？

**2. 影響を受けていた場合は「今すぐ移行」**

```
やること:
① 安全なウォレットアプリ（ハードウェアウォレット等）で
  「新しいリカバリーフレーズ」を生成する
      ↓
② 古いウォレットから新しいウォレットへ資産を移す
      ↓
③ 古いリカバリーフレーズは二度と使わない
```

> 🆗 **安全なもの（影響なし）**
> - ハードウェアウォレット（Ledger、Trezorなど）で**新規に**生成したフレーズ
> - 最近の主要ソフトウェアウォレット（MetaMaskなど）で生成したフレーズ

### 👨‍💻 開発者向け対策

- CryptoJSは**バージョン4.0.0以上**を使う
- セキュリティが必要な乱数には `Math.random()` を**絶対に使わない**
- 外部ライブラリの依存関係を定期的に監査する

### 📢 今後の展望

- CryptoJSのメンテナーが2025年8月5日に**CVSSスコア9.0（Critical）** の重大脆弱性として正式発表（GHSA-rg76-677x-56q9）
- 他にも影響を受けたウォレットアプリが存在する可能性があり、Coinspectは「すべてを特定できたとは確認できない」と警告

## 用語解説

| 用語 | 説明 |
|------|------|
| **RNG（乱数生成器）** | ランダムな数字を生成するプログラム。セキュリティの基盤 |
| **エントロピー** | 「予測しにくさ」の度合い。高いほど安全 |
| **リカバリーフレーズ** | ウォレットの復元に使う12〜24個の英単語。マスターキー |
| **CryptoJS** | JavaScript用の暗号化ライブラリ（道具箱） |
| **BIP39** | リカバリーフレーズの国際標準規格 |
| **ブロックチェーン** | 暗号資産の取引記録を管理する公開台帳 |
| **CVSS** | 脆弱性の深刻度を示すスコア（最大10点） |
| **PBKDF2** | パスワードを強化する暗号処理。ただし今回は焼け石に水 |
| **総当たり攻撃（ブルートフォース）** | すべての組み合わせを試す攻撃手法 |
| **ハードウェアウォレット** | 秘密鍵をオフラインで管理する物理デバイス |
| **依存関係（ライブラリ）** | アプリが借用している外部の部品・ツール群 |
