# AIのスピードで開発すると、セキュリティはどうなる？10〜50倍のコード量に立ち向かう方法

**解説日**: 2025年7月10日

---

## 背景知識

まず、この記事を理解するための基本的な知識を整理しましょう。

### ソフトウェア開発の流れ（普通の場合）

```
開発者がコードを書く
　　↓
自動ツールで脆弱性（セキュリティの穴）を探す
　　↓
セキュリティチームが「どれが危険か」を判断する
　　↓
開発者が問題を修正する
　　↓
ソフトウェアをリリース
```

これが従来の「当たり前の流れ」でした。

### AIコーディングツールの登場

最近、**GitHub Copilot**や**ChatGPT**などのAIツールを使うと、プログラマーがコードを書く速度が劇的に上がりました。今まで1週間かかっていた作業が、数時間で終わることもあります。

「10〜50倍」というのは、**AIを使った開発チームが生み出すコードの量が、以前の10倍から50倍になることがある**、という意味です。

セキュリティ企業「**Chainguard（チェーンガード）**」が、AIを使った開発のセキュリティリスクについてウェビナー（オンラインセミナー）を開催しました。タイトルは「**マシンスピードで開発することの本当のコスト**」です。

このウェビナーが伝えるメッセージを一言でまとめると：

> 🚨 **「AIでコードを爆速で作れるようになったけど、セキュリティチェックは人間がやっている。このままでは追いつかない！」**

## 技術的な詳細

### 問題を「ラーメン屋」で例えてみると

```
【以前のラーメン屋】
ラーメンを作る人（開発者）：1日100杯
検品する人（セキュリティ）：1日100杯チェックできる
→ ちゃんど追いつく！✅

【AIが来たラーメン屋】
ラーメンを作る人（開発者）：1日5000杯（AIのおかげ！）
検品する人（セキュリティ）：まだ1日100杯しかチェックできない
→ 全然追いつかない！😱
```

### 具体的に何が増えるのか

AIでコードが大量に作られると、以下のものも比例して増えます：

| 増えるもの | 説明 |
|---|---|
| **コンポーネント** | ソフトウェアの部品。数が増えると管理が大変 |
| **依存関係** | 「このプログラムを動かすには、別のプログラムAとBも必要」という関係。増えると複雑に |
| **脆弱性（セキュリティの穴）** | コードが多いほど、バグやセキュリティの穴も増える可能性がある |
| **修正すべき箇所** | 発見された問題の数が増えれば、直す箇所も増える |

### 「スキャンを増やせばいいじゃない？」では解決しない

スキャンツール（自動で脆弱性を探すプログラム）を増やしても、**問題の「発見数」が増えるだけ**で、修正が追いつかない「積み残し（バックログ）」がどんどん溜まってしまいます。

```
問題発見ツールを増やす
　↓
「要修正リスト」が1000件 → 5000件 → 10000件に…
　↓
セキュリティチームがパンク 😵
```

### 攻撃者側も同じAIを使っている

ここが怖いポイントです。

```
【開発者側】AIを使ってコードを大量・高速に作る
【攻撃者側】AIを使って攻撃コードを大量・高速に作る
```

つまり、**セキュリティチームは「増えるコードのチェック」と「巧妙化する攻撃への対応」の両方から同時に圧力をかけられている**状態です。

## なぜ重要なのか

### 🏢 企業・組織への影響

- **セキュリティが開発の「ボトルネック（詰まり）」になるリスク**
  　→ 開発はAI速度、チェックは人間速度 → リリースが詰まる
  
- **「誰が責任を持つのか」が不明確になるリスク**
  　→ AIが書いたコードの脆弱性は誰の責任？開発者？AIの提供会社？

- **経営層への説明責任**
  　→ 社長や役員に「うちのAI開発、どのくらいリスクがありますか？」と聞かれても答えられない状態になる

### 👤 私たちユーザーへの影響

セキュリティチェックが追いつかないまま、バグや脆弱性のあるソフトウェアがリリースされると：

- **個人情報漏洩のリスク増加**
- **スマホアプリや Webサービスの乗っ取りリスク増加**
- **私たちが使うサービスの信頼性低下**

## 対策・今後の展望

### 記事が提唱する「新しいセキュリティの考え方」

#### ❌ 古いアプローチ（もう通用しない）
```
「コードが完成してから、脆弱性を探して修正する」
= CVE駆動の事後対応
```

> 💡 **CVE（シーブイイー）**とは：発見されたセキュリティの脆弱性につけられる番号（例：CVE-2024-1234）。これを元に修正するのが従来の方法。

#### ✅ 新しいアプローチ（目指すべき姿）
```
「最初から安全なコードしか生まれない環境を作る」
= セキュア・バイ・デフォルト（デフォルトで安全）
```

### 具体的な対策の方向性

| 対策 | 内容 |
|---|---|
| **ガードレールの設置** | コードが本番環境に出る前に、自動的に危険なものをブロックする仕組みを作る |
| **AIツール自体の管理** | どのAIツールを使ってよいか、組織でルールを決める |
| **セキュリティの自動化** | セキュリティチェックもAI・自動化で対応できる部分を増やす |
| **責任の明確化** | AI開発のリスクを「誰が」「どこまで」持つか、ルールを作る |

### 🔑 一番大切なメッセージ

> **「開発スピードを落とすのではなく、セキュリティもAIスピードに追いつかせる」**

開発者を遅くするのは現実的ではありません。企業はAIを使いたいからです。だから、**セキュリティの仕組み自体を「今の開発スタイル」に合わせてアップデートする**必要があります。

## 過去記事との関連

今回は過去記事との直接の関連はありませんが、この問題は以下のような流れで理解できます：

```
① AIコーディングツールの普及
　　（GitHub Copilotなどが一般化）
　　　↓
② 開発速度が劇的に向上（今ここ）
　　↓
③ セキュリティが追いつかなくなる問題が表面化（今回の記事）
　　↓
④ セキュリティの仕組み自体をAI対応に変える動き（今後の課題）
```

AI関連のセキュリティは、2024〜2025年にかけて業界全体で最も注目されているテーマの一つです。今後もこのシリーズで関連ニュースを解説していきます！

## 用語解説

| 用語 | 読み方 | 説明 |
|---|---|---|
| **脆弱性** | ぜいじゃくせい | ソフトウェアにあるセキュリティの穴。攻撃者に悪用される可能性がある |
| **CVE** | シーブイイー | 発見された脆弱性に割り当てられる識別番号 |
| **依存関係（ディペンデンシー）** | いぞんかんけい | あるプログラムが動くために必要な他のプログラムやライブラリ |
| **バックログ** | ばっくろぐ | やるべきことの積み残しリスト |
| **ボトルネック** | ぼとるねっく | 全体の流れを詰まらせている部分。瓶（ボトル）の首（ネック）が細くて液体が出にくい様子から |
| **スキャンツール** | すきゃんつーる | コードを自動でチェックして脆弱性を探すプログラム |
| **アタックサーフェス** | あたっくさーふぇす | 攻撃者に狙われる可能性がある箇所の総面積（多いほど危険） |
| **セキュア・バイ・デフォルト** | せきゅあばいでふぉると | 最初から（デフォルトで）安全な状態になっている設計思想 |
| **ガードレール** | がーどれーる | 危険なことが起きないように自動的に制限する仕組み |
| **ウェビナー** | うぇびなー | Web + Seminar。インターネットで開催するオンラインセミナー |
| **ガバナンス** | がばなんす | 組織がルールや責任体制を持って適切に管理・運営すること |
| **Chainguard** | ちぇーんがーど | ソフトウェアサプライチェーンのセキュリティを専門とするアメリカのセキュリティ企業 |
